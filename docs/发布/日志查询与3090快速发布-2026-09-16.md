# 日志查询与 3090 快速发布手册

> 状态：当前操作手册（2026-09-16）。本手册对应提交 `beabcd35`，只描述日志查询和服务端发布工具；不代表医保、微信、HIS 或真机业务已经验收。

## 目的和边界

本项目将“单笔排障”和“正式生产审计”分成两条路径：

- 单笔排障先查短时间窗口的安全元数据，再按 `traceId`、`requestId` 或 Provider 请求号还原原始请求/返回。
- 3090 联调发布只构建和上传受影响的 API/Worker 运行面，未变化的运行面和 Java SDK 从旧 release 复用。
- 完整原始报文始终只在受控服务器或权限 `600` 的导出目录中保存；聊天、Git、普通文档只保存路径、大小、SHA-256 和完整性结论。
- 快速路径不取消原始日志、chunk 校验、checksum、原子切换、readiness、8001 共存或回滚。

## 一、最快的日志查询方式

### 1. 先查元数据

在 3090 的当前 release 上执行，默认只查最近 15 分钟，不读取原始 Body：

```bash
/home/ps/.bun/bin/bun \
  /home/ps/code/hospital-platform/current/apps/worker/dist/provider-trace-export.js \
  --latest --minutes 15
```

如果当前 release 尚未包含该 bundle，可在仓库工作区执行：

```bash
pnpm provider:trace --latest --minutes 15
```

输出只包含时间、事件、服务、操作和关联号。根据输出选出目标订单对应的 `traceId`、`requestId` 或
`providerRequestId`，不要使用 token、openid、医保凭证号或完整请求体作为检索条件。

### 2. 只还原这一笔原始报文

```bash
/home/ps/.bun/bin/bun \
  /home/ps/code/hospital-platform/current/apps/worker/dist/provider-trace-export.js \
  --id '<traceId-or-providerRequestId>' \
  --since '2026-09-16T08:00:00Z' \
  --until '2026-09-16T08:15:00Z'
```

工具会在服务器端完成以下工作：

1. 固定使用 `journalctl --all -o json`，同时检查 API 和 Worker journald。
2. 兼容 `MESSAGE` 为字符串或 UTF-8 字节数组的情况。
3. 按事件、方向、trace/request/Provider 请求号和 chunk 序号分组。
4. 拼接 `plain`，对 `json-string-v1` 只执行一次 JSON 解码。
5. 检查 chunk 数量、缺失/重复序号、UTF-8 字节数和摘要。
6. 将每个请求/返回写入权限 `600` 的文件，并生成 `manifest.json`。

标准输出只返回导出目录、条目数量、完整条目数量、匹配块数量和时间窗口，不回显原始 Body。`manifest.json`
中 `complete` 不为真或存在错误时，必须标记为 `INCOMPLETE`，不能把半包报文当成完整日志交付。

### 3. 什么时候使用全量聚合

`p0-log-aggregate` 只用于整段业务审计或发布后窗口统计。查询“最后一笔支付”时，不要先扫 24 小时日志，
也不要先把完整日志通过 SSH 传回本地；这会把网络传输和无关 raw chunk 解析变成主要耗时。

管理端 `/admin/logs` 只提供有界安全元数据，不是原始报文仓库。点击详情时默认前后查 15 分钟，无匹配块才回退到 30 分钟。

## 二、3090 快速发布方式

脚本：[`tools/publish-3090.sh`](../../tools/publish-3090.sh)。它只上传本机已有的构建产物，不在 3090 安装依赖、
构建 TypeScript 或直接读取真实 env。

### 1. 先做本地 dry-run

```bash
tools/publish-3090.sh <candidate-sha> --surface api --dry-run
```

dry-run 只解析提交、检查对应产物，不连接服务器、不切换 `current`、不重启服务。

### 2. 按修改面发布

```bash
# API 和 Worker 都修改
tools/publish-3090.sh <candidate-sha> --surface both

# 只有 API 修改：复用 current 的 Worker 和 Java SDK
tools/publish-3090.sh <candidate-sha> --surface api

# 只有 Worker 修改：复用 current 的 API 和 Java SDK
tools/publish-3090.sh <candidate-sha> --surface worker
```

需要本机定向构建时才增加 `--build`；脚本不会在远端执行 `bun install`、`bun build` 或数据库 migration。

默认 SSH 目标为 `3090-local`。如果需要跳板机或密钥，通过环境变量提供，不要把凭据写入脚本、release 或文档：

```bash
RELEASE_HOST='3090-local' \
SSH_OPTIONS='-J <jump-host> -i <key-path>' \
tools/publish-3090.sh <candidate-sha> --surface api
```

发布脚本默认等待 readiness 30 次、每次间隔 1 秒；需要适配较慢的启动环境时，可以只调整等待窗口：

```bash
RELEASE_READINESS_ATTEMPTS=60 \
RELEASE_READINESS_INTERVAL_SECONDS=1 \
tools/publish-3090.sh <candidate-sha> --surface both
```

每次检查都会输出低敏诊断摘要，包括 curl 结果、HTTP 状态、健康状态、database/redis/schema 和
`18081`/`8001` 监听状态；不会输出环境变量、令牌或业务报文。

### 3. 发布脚本保留的安全门禁

脚本会自动执行：

- 候选 SHA 和受影响 dist 校验；
- 远端 `shared/api.env` 权限 `600` 和 `PROVIDER_RAW_LOGGING=true` 检查；
- release 目录上传和 SHA-256 对照；
- `current.next` 同文件系统原子切换；
- 只重启 `hospital-platform-api-v2.service`；
- 15 秒内轮询 readiness、database/redis/schema 和 `18081`；
- 确认旧 Python `8001` 仍监听；
- readiness 或重启失败时回滚到切换前 release。

这些步骤不是冗余，不能为了速度删除。脚本不会启动 Worker，也不会修改旧 Python、数据库、Redis 或支付数据。

```text
新 current：

```

当前工作区如果还有未提交的医保、小程序或其他业务改动，快速发布脚本只上传构建产物，不会自动把这些源码改动
混入候选；正式发布前仍需单独确认提交范围和线上 release 基线。

## 四、常见误区

- macOS 本机没有 `journalctl` 时，不能据此判断 3090 日志不可用；日志查询工具应在 3090 或具备 journald 的环境执行。
- 不要直接 `. shared/api.env` 做预检，多行私钥可能被 shell 误解析；使用 systemd 环境或受控 wrapper。
- `systemctl restart` 成功只表示 systemd 接受命令，必须等待 readiness 通过后才能认为发布完成。
- HTTP 200、页面显示成功或 `ordStas=6` 都不能单独证明医保、微信、HIS 业务已完成。
