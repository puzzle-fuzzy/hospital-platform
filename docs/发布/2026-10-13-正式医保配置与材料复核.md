## 授权查询 partnerSecret

正式与测试 `partnerSecret` 是授权查询接口的合作方签名密钥，与医保反馈单数字密钥、SM2 密钥及微信商户 RSA 私钥分别配置。
正常浏览器只读查看微信官方引用的[用户授权接入协议](https://docs.qq.com/doc/DV3JYRG1xelhKTWdz)，
2.4.1 节要求三个请求头：`god-portal-timestamp`、`god-portal-request-id`、`god-portal-signature`。
签名为 HMAC-SHA256，密钥使用 `partnerSecret`，数据为 `partnerId + timestamp`；请求体仍是 `qrcode/openid`，
无需将 secret 明文放到请求体或小程序。

当前 TypeScript config/adapter 没有 partnerSecret 配置或上述签名头；两个实际服务进程也没有
任何值匹配所提供正式/测试 partnerSecret。外层 Bearer 仅认证中转服务，不能替代上游签名。
实际链路为 API/Worker → `gpsrmyy.meiyi.pro/forward` → 云机 7112 Java 中转 → 正式 receiver；
已进一步只读核对真正的中转运行处理链，确认不会补齐签名：

- 7112 由 Java 进程运行 `/home/admin/inter/interceptor_core-0.0.1-SNAPSHOT.jar`，Spring profile 为 `prod`。
- `WebMvcConfig.addInterceptors` 将 `/forward` 排除于 `GlobalInterceptor`。
- `ForwardController.forward` 字节码只设置 Content-Type/User-Agent，透传调用方 headers（过滤 host、connection、content-length），
  序列化 body 后执行请求，并直接返回响应 body；没有 partnerSecret、HMAC 或上述签名头的生成链。
- 中转业务 class 常量池、jar 配置、启动脚本和默认外部配置位置均未匹配所提供正式/测试 secret，进程也没有相关 partner 配置键。

因此，实际 userQuery 请求缺少官方协议要求的三个签名头。这是正式接入的未完成项，
不能把“正式域名、正式 PDF 密钥、渠道号相等、服务 active”视为授权查询已完整可用。
后续应在发起 userQuery 的服务端请求层配置正式 `partnerSecret` 并生成签名，
与配置完整性、API/Worker 配套装配及本地协议回归一起处理；不把 secret 放入小程序、请求 body 或本记录。
本次仅核对，未添加配置、修改签名代码或部署该修复，也未主动调用授权查询验证错误返回。

中转服务本次只读查看源码等价的 class 字节码及配置位置，未改 jar、Nginx、服务或上游配置。

四份反馈单未提供 `medicalOrgAppId`、授权小程序 AppID、网关地址，也未提供本次补充的合作方、城市和医院渠道资料。
当前包静态配置与源码一致；反馈单提供的机构字段、所有者确认的网关以及本次补充字段分别按各自来源核对。
