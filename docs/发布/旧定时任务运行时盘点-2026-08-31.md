# 旧服务动态任务运行记录只读盘点（2026-08-31）

本文补充 [`legacy-scheduled-task-inventory-2026-08-31.md`](旧定时任务盘点-2026-08-31.md) 的生产运行证据。
静态源码只能证明旧服务支持 `app_job`，不能证明数据库当前真的存在动态任务；本轮通过内网 SSH
在旧服务使用的数据库连接配置下执行只读聚合查询，未读取任务参数原文，也没有写入数据库、Redis 或服务进程。

## 1. 观察范围

| 项目 | 结果 |

| 查询内容 | 总记录数、`status=1` 启用记录数、`status=0` 停用记录数 |
| 敏感信息处理 | 环境变量值、任务参数、数据库连接串均未输出或写入仓库 |

## 2. 查询结果

本轮只执行以下等价查询：

```sql
SELECT
  COUNT(*) AS total_count,
  COALESCE(SUM(status = 1), 0) AS enabled_count,
  COALESCE(SUM(status = 0), 0) AS disabled_count
FROM app_job;
```

返回结果为：

```text
total_count  enabled_count  disabled_count
0            0              0
```

因此，本次观察窗口内没有可供“退休、保留在旧系统或改写到新 Worker”的动态
`app_job` 记录，也不存在需要逐条脱敏、指定负责人或安排切换时间的任务。

## 3. 结论与再次核对条件

- 旧服务当前没有从 `app_job` 表加载动态 APScheduler 任务；“后台任务管理不迁移到患者小程序”不能再被解释为“生产一定有任务”，本轮已取得反证。
- `plugin_payment_reconcile_loop` 是旧服务启动时独立创建的支付/HIS 恢复循环，不属于 `app_job`。本记录不把空表结果扩展为支付/HIS 恢复能力已迁移；该能力仍受支付批次 gate 约束。
- 正式切换前仍应在冻结窗口重复同一聚合查询，并将结果与本记录比较；如果出现任何记录，必须恢复逐条去向、负责人、切换时间和回滚方案后才能继续切换。
- 本轮没有启动旧服务、没有重启新旧服务、没有切换 release，也没有执行 schema migration。
