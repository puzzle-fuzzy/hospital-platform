## 修复行为

医保授权查询原来只向中转发送 `qrcode/openid`，实际中转没有自动签名。
现在 API/Worker 在发起 userQuery 前，按腾讯[用户授权接入协议](https://docs.qq.com/doc/DV3JYRG1xelhKTWdz)
生成 `god-portal-timestamp`、`god-portal-request-id`、`god-portal-signature` 三个下游请求头。

签名使用正式 partnerSecret 的 UTF-8 原文作为 HMAC-SHA256 key，数据为实际 URL 中的 partnerId
拼接 13 位毫秒时间戳，输出小写十六进制；request-id 为去掉连字符的随机 UUID。
partnerId 从实际 userQuery 路径提取，拒绝编码、额外路径、查询、片段和末尾换行歧义。

新增服务端环境变量 `MBS_USER_QUERY_PARTNER_SECRET`，与省医保 `MBS_APP_SECRET` 分开，
不回退到其他密钥。医保 gate 开启时缺少该变量，会关闭医保 adapter 或阻止 Worker 就绪。
API 和 Worker 两份环境文件均增加同一正式值，环境文件权限为 0600。
secret 不进入请求 body、小程序、公共契约、授权持久化上下文或本记录。
1101、其他 FSI 和 HIS 请求不携带这些 userQuery 签名头；中转外层 Bearer 保持原逻辑。

## Worker 入口问题与切换保护

第一次切换的 Worker 退出门禁拦截后，自动恢复了原 current 和两份原环境文件。
只读复核发现原 Worker bundle 把两个被 re-export 的 smoke 工具误认为主入口，
启动配置错误会预设 `process.exitCode=1`，尽管 Worker 已正常运行并记录停止日志。
本次为两工具增加实际 `.ts/.js` 文件名检查，兼容 Windows/Linux，保留独立工具入口行为。
真实 Bun 打包回归证明 Worker index 不再执行独立 smoke 工具，也不预设退出码 1。

第二次门禁仍因原 Worker 完成停止后被 systemd 标为 failed 而恢复；随后明确限定旧产物的过渡检查：
仅接受已核对 SHA-256 的原 Worker、明确 exited/1、同 PID 的 service.stopped/ready、无超时或强杀、
无新增关闭错误，且停后所有有效 claim/在途计数为零。没有普遍放行其他失败码或删除 drain 检查。
最终新 Worker 正常启动，没有原两项配置错误。
