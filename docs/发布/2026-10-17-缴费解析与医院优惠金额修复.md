## 二、问题及解决方式

### 1. 门诊医保缴费在正常金额 95.25 元处失败

10 月 17 日 08:57 的费用上传中，医院 `2.6.65.1` 返回 HTTP 200、业务成功，`getAmount` 是 JSON number `95.25`。平台先用文本/标识解析器读取该字段；其 `Number.isSafeInteger` 检查把合法小数拒绝，导致 `provider-response-invalid`。请求停在医院结算主单响应解析阶段，未进入后续医保费用上传和微信支付。

修复位于 `packages/adapters/src/legacy-fsi-medical-insurance.ts`：金额使用独立的 `findAmountFenDeep` 读取并交给 `yuanToFen` 精确转换，数字和字符串 `95.25` 均得到 `9525` 分。ID、流水号等文本解析仍保留原有整数安全检查。负数、对象、非有限数、超过两位的小数金额、超安全范围等仍拒绝；错误继续按 Provider 响应异常归因，不改成未知 500。

### 2. 已缴记录中的药品单价 0.5536 元使整个列表失败

10 月 17 日 09:03 的医院已缴记录返回业务成功，但一条药品单价为 `0.5536` 元。旧逻辑把单价与费用总额共用“元转整数分、最多两位小数”的转换器，整批记录因此被拒绝。

修复引入可选 `priceYuan` 十进制字符串，精确保留单价；仅在单价能无损换算成整数分时才同时提供旧 `priceFen`。例如：

```json
{"priceYuan":"0.5536","amountFen":388}
```

这里不生成小数分，也不把 `0.5536` 四舍五入成 `0.55` 或 `0.56`。账单合计仍由医院明确返回的 `amount` 转换，不能以 `price × quantity` 重新计算。

涉及 adapter、domain 白名单、API contract、小程序 `dashboard-service` 与测试。旧客户端可忽略新字段并成功打开列表；若要显示精确单价，须更新小程序。

### 3. 医院优惠已经执行，但页面仍可能显示自付 2 元

当天两笔医保挂号均为：总费用 10 元、医保 8 元、医院现金减免 2 元、实际微信现金 0 元。微信原始请求包含 `HOSPITAL_REDUCE=200`，HIS 也返回 `isSettle=1`。但旧 API 只返回 6202 的原始 `cashFen=200`，客户端直接把它当成最终应付。

本次**不改** 6202 原始金额、优惠政策、真实支付请求、HIS 回写金额或状态机，而是增加三个可选展示字段：

| 字段 | 含义 |
| --- | --- |
| `hospitalPartFen` | 6202 医院负担；原来包含在 `insuranceFen` 内 |
| `hospitalReduceFen` | 从原始 `cashFen` 抵扣的医院现金减免 |
| `wechatCashFen` | 实际微信现金金额 |

业务恢复、订单/结算响应位于 `data.amounts` 内；医保微信支付读模型的相应字段位于 `data` 根部。典型响应：

```json
{
  "totalFen": 1000,
  "insuranceFen": 800,
  "cashFen": 200,
  "hospitalPartFen": 0,
  "hospitalReduceFen": 200,
  "wechatCashFen": 0
}
```

服务端从可信结算上下文读取真实地区，复用现有拆分规则。已完成订单优先使用已成功的记账分项；`payTypeId=50` 同时包含医院负担和现金减免，计算现金减免时先扣除医院负担，防止重复抵扣。历史终态订单缺少成功分项时省略新字段，不能仅凭混合订单号就把历史实付重新解释成 0 元。

客户端仅在三个展示字段完整、整数与金额勾稽通过时显示：

- 医保金额 = `insuranceFen - hospitalPartFen`。
- 医院优惠 = `hospitalPartFen + hospitalReduceFen`。
- 实际微信金额 = `wechatCashFen`。

这三项加总仍等于总费用。旧 API、缺少字段或拆分不合法时，保留原始金额并标为“医保结算后自费”，隐藏底部最终需付数字；不能把缺字段当成优惠 0 或微信应付 0。金额为 0 也不能作为支付成功依据。
