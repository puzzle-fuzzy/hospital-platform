## 报错阶段与可观测边界

客户端先取得支付授权上下文，再跳转腾讯授权小程序。服务端 userQuery 需要授权后返回的 authCode，
在后续服务端流程才调用；本次描述的错误发生在授权页出现前，因此当前没有证据指向查询签名、
1101/6201 目标或回包严格验签。本次没有改动这些配置或重启服务。

平台 API 日志没有客户端包 revision，也不会记录腾讯授权页内部的报错。
小程序冷启动 `app.launch` 实时日志可核对 `fields.revision=1241a72a2187115532ec013b428fcc40b6ab7e3b`；
`fields.mode=release` 是构建模式，不代表主小程序一定是微信正式发布版。
需要确认腾讯收到的最终授权参数及失败来源，应取腾讯该次授权请求的日志，而不能用平台健康检查代替。

## 仍需核实的正式授权配置

[用户授权接入协议](https://docs.qq.com/doc/DV3JYRG1xelhKTWdz)第 2.2.2、2.2.4 节已正常浏览器只读复核。
[官方报错排查指引](https://pay.wechatpay.cn/doc/v3/partner/4020401184)指出：小程序认证码不需要 encode，
不同环境需要分别配置页面参数和接口返回参数，参数正确后仍需检查省中台机构配置。
[测试及环境切换](https://pay.weixin.qq.com/doc/v3/partner/4021773695)第 6 节还明确腾讯需配置正式地址，
正式用户授权前省中台须已登记医院。正式 partnerSecret 的取得与加载不能独立证明这些配置已经生效。

1. 腾讯正式免密授权配置：按实际合作方、channel、sourceapp、cityCode，确认 release 请求使用的正式授权地址与参数映射。
2. 腾讯接收日志：比对本次请求接收到的完整 `orgChnlCrtfCodg`、`orgAppId`、`orgCodg`、`bizType`，
   包括认证码是否被内部转义/解码；提供原始返回码及信息，并说明错误由腾讯预校验还是省中台/国家局返回。
3. 省中台/国家局正式登记：核对机构码、微信、`04107`、正式认证码及新正式支付应用 ID 的有效登记与关联。
4. 如果日志中仍有旧测试 ID 或与反馈单不一致的码，结合该次手机冷启动 revision 和腾讯实际接收值定位；
   如果接收值全部一致，以正式系统登记及返回码继续排查。

正式身份单回复日期为 2024-06-11，正式支付应用单回复日期为 2026-10-13；机构名称一致，
