# 错误码速查表

数字错误码是排障定位索引：用户口头反馈"错误码 N"或页面展示"（错误码 N）"时，在本表反查原因和
grep 关键字，再结合遥测事件（route/method/errorKey/requestId）与微信实时日志的按码过滤还原链路。
服务端权威分配表在 [`apps/api/src/plugins/error-handler.ts`](../apps/api/src/plugins/error-handler.ts)
的 `ERROR_NUMERIC_CODES`；客户端镜像与本地段在
[`apps/miniprogram/src/services/error-registry.ts`](../apps/miniprogram/src/services/error-registry.ts)。
三处由 `pnpm error:contract:audit` 强制同步。

规则：

- 一个数字唯一对应一个原因；"哪个部分"由页面 surface 标题补充（见 `error-presentation.ts`）。
- 段位：10xxx 请求层/会话/运行时，20xxx 就诊人，30xxx 预约，40xxx 报告，50xxx 支付/缴费，
  60xxx 健康内容/资料，80xxx 客户端本地（服务端永不使用），10900/unknown 兼作未知回落。
- 客户端不得用数字码做程序分支；程序分支仍用稳定字符串码。
- `error.transformed` 遥测事件记录"转换/替换/吞没前"的原始数字码：用户看到的码指向替换后原因时，
  先查同一时间点的 error.transformed 事件。

## 排障路径

1. 用户反馈错误码 N → 本表定位原因与来源段。
2. 微信公众平台"运维中心 → 实时日志"按 N 过滤（失败事件自动 `addFilterMsg`），
   拿到 route/method/errorKey/requestId。
3. `errorKey`（字符串码）grep 源码定位抛出点；`requestId` 对齐服务端 Pino 的
   `http.request.*` 与业务事件。
4. 若码是 80310（session-changed）等转换后原因，同窗口查 `error.transformed` 事件取原始码。

## 维护注意事项

以下事项是本轮落地时的决策与边界，后续会话改动错误体系前先读这一节。

### 部署顺序

`error.numericCode` 是对错误封套的加字段契约：**发布时服务端必须先上线，再发小程序**。
旧服务端 + 新客户端的窗口内，`ApiError` 按 `error-registry.ts` 镜像表由字符串码回退数字码，
不会崩溃，展示的码来自镜像而非响应原文。反向（新服务端 + 旧客户端）多出的字段会被旧客户端忽略，
同样安全；但排查该窗口的日志时要知道客户端报的码可能来自镜像。

### 页面接线状态（2026-09-03）

错误横幅已接 `errorMessageWithCode`（文案后追加"（错误码 N）"）的页面：
appointment-records、report-directory、report-detail、missed-appointments、
outpatient-payment、patient-select、profile、index、my。
其中 appointment-records、report-directory、profile 三个页的 WXML 错误卡已改为动态渲染 `{{error}}`。

**待接页面**（错误文案不变，横幅暂无码后缀）：appointment-directory、appointment-schedule、
timeslot-source、consult、health-encyclopedia、health-knowledge-detail、health-knowledge-search、
便民四页（patient-signature、patient-express、patient-subscription、blood-appointment）。

接法是每页一处一行式改动：页面 `showError` 写入 `data.error` 前包一层
`errorMessageWithCode(error, 原文案)`（import 自 `services/error-presentation`）；
错误卡的静态文案改为渲染 `{{error}}`（参考 `appointment-records.wxml` 的 clinical-query-state-title）。

### toast 不带码

瞬时提示（`wx.showToast`）保持纯文案，数字码只进遥测事件；错误横幅与错误卡才展示
"（错误码 N）"。不要为了形式统一把码塞进 toast——用户来不及读，反而干扰文案。

### 新增错误码的固定流程

1. 服务端 `ERROR_NUMERIC_CODES`（error-handler.ts）在对应段位分配新数字；段内按 10 递增预留。
2. 客户端 `SERVER_ERROR_NUMERIC_CODES` 镜像同步同一数字；客户端本地新码只能用 80xxx 段。
3. `docs/公共API-v2.md` 错误表加行（HTTP | 数字码 | code | 含义）。
4. 本文件速查表加行（数字码 | code | 来源 | 开发者说明）。
5. 若需要新文案：`CLIENT_ERROR_MESSAGES` 与 `error-presentation.ts` 的 surface 覆盖表。
6. 跑 `pnpm error:contract:audit`；三处不同步会直接红。

未登记的字符串码在服务端和客户端都固定回落 10900（unknown），不猜测、不透传任意数字。

### error.transformed 的登记义务

任何新增的"转换/替换/吞没"错误位置（把具体错误换成通用文案、替换成 session-changed、
catch 后不再抛出等）必须调用 `logClientErrorTransformed(stage, error)`，并把 stage 名
登记到 `docs/日志规范.md` 客户端遥测事件表；否则用户看到的码永远指向替换后的泛化原因，
原始故障无从追溯。当前已登记的 stage 见该表。

### 数字码不做程序分支

客户端与服务端的程序逻辑分支继续使用稳定字符串码；数字码只用于展示与检索。
不要写 `if (numericCode === 30210)` 这类代码——数字是排障索引，不是业务语义。
