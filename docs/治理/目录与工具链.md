# 目录与工具链治理

本轮以 `30fc7015` 的提交内容为整理起点，日期为 2026-10-28。原工作区的未提交业务改动独立保留。本页区分当前目录、此次整理和后续设计；源码位置或本地测试不能证明生产、Provider 或设备验收通过。

## 当前目录职责

| 目录 | 职责 | 管理原则 |
| --- | --- | --- |
| `apps/api` | Bun / Elysia HTTP API、鉴权、业务模块和运行时组装 | 路由处理、应用服务、Provider 与持久化边界各自明确 |
| `apps/worker` | 查单、补偿、outbox 和运行检查命令 | 独立启动；不能由 API 启动或本地构建推断线上运行状态 |
| `apps/miniprogram` | 微信原生页面、平台 API 客户端及运行包构建 | 唯一开发者工具入口为该应用的 `dist/` |
| `apps/admin2/apps/web-antd` | 当前 Vue / Vben 管理端界面 | 浏览器仅访问同源 `/api`，不直接持有内部服务令牌 |
| `apps/admin2/packages`、`internal` | 固定版本的 Vben 上游核心 | 按 `UPSTREAM.json` 的 SHA-256 验证，不因精简模板而改写 |
| `packages/contracts` | HTTP 契约和响应 schema | 不混入数据库、Provider 或客户端状态 |
| `packages/domain` | 领域规则、状态机与端口 | 保持业务规则可独立验证 |
| `packages/adapters` | 外部系统协议、HTTP / 加密适配 | `legacy` 命名不代表不再使用，应沿组合根核实 |
| `packages/persistence` | migration、事务和 repository 实现 | 保留历史 migration，禁止用目录整理替代数据库迁移 |
| `packages/config`、`observability`、`ai-runtime` | 配置、日志和 AI 运行时能力 | 与应用启动入口分离 |
| `tools` | 当前仓库审计、Provider 材料研究、证据导出和部分运维命令 | 现状混有不同职责，下一阶段按影响范围迁移 |
| `infra` | 当前本地 Compose、Nginx、systemd 模板及运维手册 | 目前实际承担部署配置职责，不能只按名称搬走 |
| `docs` | 当前设计、操作手册、契约、迁移与历史证据 | 入口页导航，历史记录按状态归档 |

用户明确要求删除 `apps/admin`，并明确指出 Admin 2.0 已可用，旧日志功能是之后特地删除的。本轮仅移除旧应用，不将其服务、日志、trace 模块或测试迁入 Admin 2.0，不恢复已删除能力。Admin 2.0 的功能范围以当前界面与实际源码为准。

## 工具链与安装边界

根工作区继续使用 `pnpm@11.9.0`、`pnpm-lock.yaml` 和 Turbo；运行时声明为 Bun `1.4.0`、Node `24.12.0`。这里记录仓库声明，不表示本机可执行文件已匹配版本。根 CI 依据 `.bun-version`、`.node-version` 和根 lock 安装并运行候选门禁。

Admin 2.0 是根 `pnpm-workspace.yaml` 显式排除的独立 Vben workspace，保留 `pnpm@10.33.4`、自己的 `pnpm-lock.yaml` 及 Node `22.22.0` 声明。这是已有隔离边界；不能删除第二份 lock 后用根安装覆盖。`tools/run.mjs` 固定工作目录和命令，`tools/verify-upstream.mjs` 校验官方 revision、package manager 和核心文件指纹。

不新增 `admin-server` 包或第三套安装链，不把旧应用代码纳入 Admin 2.0。管理端的交付与部署职责需沿其当前实现单独核实，本页不因目录整理决定部署架构或恢复旧能力。

`tools/zhongyang-docs` 是 Node 文档采集工具，根脚本通过 Node 的类型擦除功能启动。`packages/adapters/java-sdk` 是医保官方加密 SDK 的构建输入；JAR 文件被 adapters build 和发布手册显式使用，不能当作偶然提交的生成物删除。

## 后续目录设计

以下为目标结构，尚未批量执行目录迁移：

```text
apps/                   可独立运行或交付的应用
packages/               共享契约、领域和运行能力
scripts/
  verify/               仓库质量和结构审计
  db/                   数据库维护入口
  deploy/               受控部署与回滚
  release/              发布材料与版本一致性检查
  backup/               明确目标的备份维护
tools/                  Provider 文档研究和只读证据工具
deploy/
  compose/              本地容器依赖
  nginx/                反向代理模板
  systemd/              服务与权限模板
docs/                   设计、手册、契约和历史索引
```

目录移动必须以职责和依赖为单位；迁移完成就删除旧入口，不长期维护两套路径。

### 先整理自动化入口

`tools` 在整理起点有 79 个已跟踪文件，包含 CLI、共享 catalog、测试、文档采集和生产脚本。按依赖一起移动审计实现、catalog 和测试，不按文件名逐个搬运。

需要同步检查的真实引用包括：

- 根 `package.json` 的直接脚本和候选门禁顺序。
- `tools` 中依赖 `import.meta.dirname` / `import.meta.url` 计算仓库根的代码。
- `apps/worker/package.json` 对三个 `tools` 文件的打包路径。
- `turbo.json` 对日志汇总、业务证据审计和 Provider trace 导出文件的全局输入声明。
- `tools/publish-3090.sh` 从脚本位置计算仓库根的逻辑、服务面选择和发布手册。
- `tools/production/switch-api-persistence-to-wireguard.sh` 的固定服务、环境路径与回滚语义。

最后两类涉及真实远程状态，整理仅修改受控源码与引用，不能通过执行脚本来“验证能用”。

### 再统一部署配置

`infra` 当前没有独立 IaC 项目，主要是本地 Compose 与部署模板，可规划迁入 `deploy`。迁移前必须同时覆盖 `infra:up/down`、Compose 相对路径、systemd / Nginx 手册、文档链接与 env 模板审计。

当前根 `.env.example` 是开发模板，`infra/systemd/api.env.example` 是生产 API 模板，差异由 `tools/env-template-audit.mjs` 固定检查。不能把两份模板简单合并或把开发默认值用于生产。若将样例统一移到根目录，应保留开发、API、管理端各自职责，并同步变量清单、占位符和默认值门禁。真实 env 和用户数据不参与此目录迁移。
