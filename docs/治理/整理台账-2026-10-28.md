## 文件处置结论

| 类别 | 结论 | 后续条件 |
| --- | --- | --- |
| 当前应用、共享包、已发布 SQL migration | 保留 | 拆分需保持契约、事务、幂等、租约和发布顺序 |
| `apps/admin` 旧 React 界面 | 本轮删除 | 不复制旧服务或日志功能，Admin 2.0 当前页面保持原样 |
| Vben `packages/`、`internal/` | 保留 | 受上游核心 SHA 清单约束，精简须有升级与兼容证据 |
| Java FSI SDK/JAR | 保留 | 是适配器构建和医保协议输入，不能按二进制后缀删除 |
| Provider 快照中的相同图片/无扩展资源 | 保留 | 被资源 manifest 和来源清单登记；去重需要同步来源映射和校验 |
| 三份 HIS 退费 DOCX | 暂保留 | 版本与文件指纹不同；先核实交付版本与外部引用，再归档旧交付物 |
| 受机器审计引用的迁移与发布资料 | 暂原位保留 | 先解除不必要的复制事实与路径耦合，再按业务/观察日期归档 |
| `dist/`、`node_modules/`、`.codegraph/`、发布暂存 | 不纳入本轮磁盘删除 | 与源码清理分开，核对复现方式、实际用途和锁定状态 |
| 真实配置、生产导出、日志和本机证据 | 保持受控存储 | 不通过“整理”改变保留语义或扩大访问范围 |

“无入链”“命名 legacy”“文件很旧”“内容相同”都是调查线索，均不能单独作为删除依据。删除候选至少需要核实源码引用、动态加载、构建复制、workspace、脚本、CI、部署和外部交付。

## 后续架构批次

1. 按业务组拆分 API/Worker 组合根，将依赖创建、生命周期与应用服务组装分开，保持默认 gate 和依赖注入行为。
2. 按领域拆分持久化仓储工厂，保护订单与 Outbox 同事务、owner 范围、锁、版本与唯一键。

4. 在各 Provider 内分离传输、签名、协议与业务能力；拆分小程序传输/会话和领域 API，保留现有 facade。
5. 成组迁移工程自动化到 `scripts/`、部署声明到 `deploy/`，同时更新路径计算、CI、Turbo、环境审计与运维手册。
6. 已完成四份一般说明与标准 Provider 接收记录的分类；继续清理其余过时发布导航，核实 DOCX 交付版本和模板依赖闭包。

每批必须有独立 diff、适当的类型/单元/构建验证和明确回滚点。目录计划不会在本轮被描述为已经实施。
