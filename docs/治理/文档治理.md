# 文档治理

## 范围与事实基线

本文约束项目文档的归属、导航、证据保留和清理方式。架构职责及代码整理次序见[系统设计](../架构/系统设计.md)。

2026-10-28 以整理分支起点 `30fc7015` 的 Git 跟踪文件盘点：`docs/` 共 380 个文件，其中 292 个 Markdown；根层有 29 个文件（26 个 Markdown、3 个 DOCX）。`迁移/` 145 个文件，`发布/` 99 个文件，`提供商接入/` 91 个文件（包含来源快照资产）。这些数字是整理前快照，不包含被忽略的本机资料，也不是今后的固定配额。

已确认的问题是入口混杂、事实复制和机器路径耦合：

- 旧文档导航有 348 行，混有多个日期的候选、运行包和“当前”说明，读者难以确定有效执行入口。
- 发布版本在导航、候选文档、机器索引、真机清单和运行包中重复登记，已经存在不一致；文档刷新不能代替实际发布。
- 整理起点的 Provider 接收目录混入实现说明、环境对照和申请资料。统一接收审计把它们当成标准材料，导致结构检查失败。
- `miniprogram-pay` 业务代码已退役；其流程资料仍有历史用途，应退出现行业务导航。

## 文档职责与归属

| 类别 | 入口和位置 | 维护方式 |
| --- | --- | --- |
| 项目入口 | 根 `README.md`、[文档导航](../README.md) | 简短介绍、命令和稳定链接，不堆积发布日志 |
| 产品与任务 | 根 `PRODUCT.md`、`TODO.md` | 记录产品边界和待办；实施前核对源码、契约与证据 |
| 总体设计与流程 | `docs/架构/`、[架构说明](../架构说明.md) | 总体职责由系统设计维护，具体业务流程作为补充；区分现状和目标 |
| 架构决策 | `docs/架构决策/` | 记录选择、理由、约束和替代决策；旧决策被替代时保留追溯 |
| 领域与外部契约 | 既有 `*契约*.md`、`docs/提供商接入/` | 真实来源与确认状态必须可追溯；材料存在不等于业务准入 |
| 专项实现 | `docs/实现说明/` | 记录已实现行为、代码位置、限制与验证窗口，不混入外部材料接收目录 |
| 运维与恢复 | `docs/操作手册/`、`infra/` 中的部署说明 | 维护可执行的前提、操作、验证和回滚；历史操作窗口单独留证 |
| 发布证据 | `docs/发布/` | 以观察日期、候选或发布批次界定范围，不把历史成功当作当前结果 |
| 迁移证据与台账 | `docs/迁移/` | 保留旧新能力映射及缺口；机器读取的台账按实际门禁同步 |
| 退役资料 | `docs/归档/` | 仅用于追溯，通过退役说明进入；不再是开发或验收入口 |
| 治理规则 | `docs/治理/` | 维护目录归属、清理规则和已知治理债务 |
| 本机运行和敏感材料 | `.local/`、`outputs/`、已忽略来源资料等约定位置 | 不转成源码归档，不在导航或审计输出中复制正文和秘密 |

本轮沿用既有中文目录，不批量把全部契约、迁移台账和发布记录重命名。后续迁移以一类资料为一个变更批次，并同时修改读者与机器入口。

## 单一事实入口

| 事实 | 优先核对的位置 | 导航中的处理 |
| --- | --- | --- |
| 当前代码行为 | 对应源码、契约和实际测试结果 | 链接实现说明，不复制“全部完成”结论 |
| Workspace 与任务命令 | `pnpm-workspace.yaml`、各 `package.json`、`turbo.json` | 命令示例随任务入口更新 |
| 原生页面注册 | `apps/miniprogram/src/app.json` | 不手写页面总数 |
| 仓库登记发布指纹 | [当前基线 JSON](../发布/当前基线.json)及[候选配套记录](../发布/候选-5738a71-服务端发布-2026-08-31.md) | 只链接，不复制 hash；不一致时保留审计失败并调查 |
| 构建来源 | 各应用实际构建元数据及同次构建日志 | 构建证明与线上、真机证据分开 |
| 线上实际状态 | 经授权取得的远端 release、进程、readiness 与业务证据 | 写明采集时间与范围，不由本地 Git 或文档推断 |
| Provider 材料 | 稳定 `documentId`、来源、版本、适用环境、SHA-256 与人工确认记录 | 不伪造指纹，不自动提升为 `confirmed` |

修改导航无需复制候选指纹。发布门禁继续检查导航是否提供机器索引和候选唯一入口；候选、索引、真机清单和实际运行证据之间的一致性仍单独验证。

## 保留、归档与删除

| 处理 | 必须具备的依据 |
| --- | --- |
| 保留 | 仍被代码、审计、发布、恢复、契约或外部交付使用；或保留历史来源是业务审计的必要条件 |
| 合并 | 多份文档维护同一现行事实；明确保留的唯一正文，更新所有入口并保留必要的历史说明 |
| 归档 | 对应应用、流程或候选已退役，但来源、交付和故障恢复仍有追溯价值；归档时更新链接和工具路径 |
| 删除 | 已确认被替代或是可再生成产物，且没有未迁移的源码/工具/清单/交付依赖；在变更记录中给出精确路径与依据 |
| 暂缓 | 用途、所属版本、引用方、资料敏感性或恢复需求尚未核实；登记缺口后继续调查 |

“没有被 Markdown 链接引用”“文件很旧”“内容相似”“已经有新版本”均不能单独证明可删。目录名也不能证明全部内容同类；应确认其中的源码、资产、构建和交付角色。

清理步骤：

1. 用 Git 跟踪清单确定候选集合，区分源码资料与本机数据；保留并行工作。
2. 查找 Markdown、源码字符串、配置、JSON manifest、测试、CI 和发布入口的引用。跨模块影响先用 CodeGraph 导航，再读源码确认。
3. 为每项记录用途、证据、保留/合并/归档/删除决定及未解决条件。
4. 在独立分支中移动或删除精确路径，更新所有受影响入口；需要保留的历史内容通过 Git 和原始证据追溯，不复制成另一份现行正文。
5. 运行本地链接与相应专项门禁，检查完整 diff。存在原有失败时记录基线及本轮变化，不填充虚假事实使其通过。

## 校验与完成标准

| 变更 | 必需验证 |
| --- | --- |
| 新增、移动、删除 Markdown | `pnpm docs:audit`，检查差异及全部本地引用 |
| Provider 接收入口 | `pnpm provider:audit`；众阳采集工具的插入锚点与注册流程继续可用 |
| 发布索引与候选导航 | `pnpm release:baseline:index:audit`、相应工具测试；实际发布时再执行完整基线和运行检查 |
| 架构、模块与业务变更 | `pnpm architecture:audit` 及受影响领域的测试、类型检查和构建 |

`docs/README.md` 保留 `医保契约-v1.md` 表格行作为 `tools/zhongyang-docs/cli.ts` 的插入锚点；若调整该结构，应在同一变更中更新工具及验证。

治理完成意味着读者能找到唯一现行入口，历史证据仍可追溯，机器检查未被削弱，清理依据可复核。文档数量减少本身不是完成标准。
