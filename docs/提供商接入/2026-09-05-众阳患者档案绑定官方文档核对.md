## 2. 与原适配器的差异

原适配器在 gate 关闭时不会发出请求，但代码合同存在以下问题，本轮已修正：

1. `patInfosFind` 查询现在发送服务端配置的 `org-id`，不再遗漏文档要求的机构上下文；
2. 创建档案现在发送数值类型的 `idCardType=0`、`sex`、`cardType`、`hospitalId` 和 `orgId`；
3. 不再把身份证号复制到 `cardNo`；档案查询或创建响应必须返回真实 `cardNo`，否则停止在响应校验阶段；
4. `patId` 按官方整数合同校验，绑卡请求使用真实数值 `patId` 和 provider 返回的 `cardNo`；
5. 查档、建档、绑卡使用不同的日志 `operation`，共享同一个平台 `traceId/idempotencyKey`，最终 trace 保留各阶段的 provider request ID，便于定位是哪一步失败。

## 3. 配置闸门

以下变量已加入 `.env.example` 和 systemd 示例：

```text
ZHONGYANG_PATIENT_ORG_ID=
ZHONGYANG_PATIENT_HOSPITAL_ID=
ZHONGYANG_PATIENT_CARD_TYPE_ID=
```

它们不从医保的 `MBS_INSURANCE_ORG_CODE`、`MBS_HOSPITAL_ID` 推导。即使 `ZHONGYANG_PATIENT_BINDING_READY=true`，只要三项缺失，启动诊断仍为 `incomplete`，API 不注入患者绑定 gateway。

当前没有打开 `ZHONGYANG_PATIENT_BINDING_READY`，也没有改动线上环境变量、数据库或旧服务。

## 4. 尚未确认的事实

- 2.1.55 当前机构实际返回的 `cardTypeId` 及其含义；
- 2.1.51 的 `cardNo` 省略后是否在当前环境稳定生成默认就诊卡；页面的字段表与说明存在差异；
- 2.1.52 是否允许患者端自助调用，还是必须由院内 HIS/工作人员操作；
- 查档无记录、重复记录、超时和 provider 业务失败的逐类响应；
- 建档/绑卡超时后的最终确认接口、幂等键和跨 owner 冲突规则。

在这些事实到达前，页面只开放旧端的姓名、手机号、身份证号手动录入和协议确认；真实查档、建档、绑卡仍由服务端 gate 控制，不能为了“可点击”而在小程序端直接打开 Provider 写入。
