# 国家局微信医保移动支付时序图与当前实现对照

来源：腾讯文档《基于省中台医保移动支付医院接入指引》的预览层图片
[AgAABdlcCDaNjaxUrB5IX7ZIL5EY-KS_.png](./assets/AgAABdlcCDaNjaxUrB5IX7ZIL5EY-KS_.png)。

## 结论

当前挂号支付 demo 与图片展示的“授权 → 费用明细 → 医保下单 → 微信收银台 → 结果查询/通知”主链路一致，但不是接口级 1:1 实现。当前代码采用医院/众阳业务适配器承接医院侧业务，再通过医保适配器处理 1101、6201、6202、6301 和 6302；不能把图片中的每一条消息都等同为当前已有的一个 HTTP 路由。

## 逐段对照

| 图片中的环节 | 当前实现情况 | 代码依据 |
| --- | --- | --- |
| 免密授权：`authCode` 查询并得到 `payAuthNo` | 已接入。服务端解析授权结果、调用 1101 获取参保上下文，并加密保存授权凭证。 | `packages/adapters/src/legacy-fsi-medical-insurance.ts` 的 `resolveAuthorization` |
| `[1101]` 人员基本信息查询 | 已接入，由医保适配器发送实名和 `payAuthNo` 相关字段。 | `packages/adapters/src/legacy-fsi-medical-insurance.ts` |
| `[2201]` 门诊挂号并取得 `mdtrtId` | 当前没有独立的 2201 调用。挂号记录先由预约/挂号服务写入，医保费用链路使用已有就诊上下文；这与图片的显式 2201 步骤不完全相同。 | `apps/api/src/modules/medical-insurance/registration-service.ts`、`apps/api/src/modules/appointments/service.ts` |
| `[6201]` 费用明细上传 | 已接入。费用明细、患者、科室、医生、诊断和金额由服务端组装，不能由小程序直接提交医保凭证。 | `packages/adapters/src/legacy-fsi-medical-insurance.ts`、`packages/adapters/src/legacy-fsi-contract.ts` |
| `[6202]` 医保支付下单 | 已接入，服务端从 6201 保存的上下文取 `payOrdId`、`payToken` 等凭证，完成金额和订单校验后下单。 | `apps/api/src/modules/medical-insurance/payment-core.ts`、`packages/adapters/src/legacy-fsi-medical-insurance.ts` |
| 微信统一下单/医保混合支付 | 已接入混合支付入口；服务端创建微信医保订单，小程序调用医保支付能力，支付后再由服务端查单收敛。 | `packages/adapters/src/wechat-pay.ts`、`apps/api/src/modules/medical-insurance/wechat-payment-service.ts`、`apps/miniprogram-pay/src/services/medical-insurance.ts` |
| `[6302]` 医保结算结果通知 | 已接入服务端通知入口，验签解密、订单匹配、金额校验和幂等状态更新均在服务端完成。 | `apps/api/src/modules/medical-insurance/service.ts` |
| `[6301]` 主动查询医保订单结果 | 已接入；非终态结果持久化并进入后续查单处理，避免只依赖客户端回调。 | `apps/api/src/modules/medical-insurance/payment-core.ts`、`packages/adapters/src/legacy-fsi-medical-insurance.ts` |
| 线下扫码退款、线上授权退款 | 当前 demo 没有对应的公开退款页面和完整退款业务入口；适配器中只有 6203/6401 等底层合同校验，不能宣称图片中的退款流程已经完整实现。 | `packages/adapters/src/legacy-fsi-contract.ts` |

## 对当前挂号支付 demo 的影响

1. 现有“挂号支付”页面在授权前的选择、预约写入和支付入口可以继续保留。
2. 看到图片中的 `[2201]` 不应直接在小程序端补一个调用；如果众阳的新合同要求由平台显式完成 2201，应先在服务端适配器中取得正式字段和响应合同，再接入统一支付核心。
3. 6201/6202 的失败需要以服务端结构化日志和外部请求证据为准，小程序只展示可理解的业务提示；不能依据客户端的“外部服务拒绝”判断具体字段缺失。
4. 本对照文档只记录已确认的实现和差异，不用相似文档推测缺失接口，也不改变原始资源清单。
