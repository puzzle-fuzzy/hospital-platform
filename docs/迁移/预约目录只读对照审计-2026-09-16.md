# 预约目录只读链路对照审计（2026-09-16）

## 结论

预约目录的小程序页面、平台 API、众阳 adapter 和短期排班快照代码已经形成只读链路，但 P1-04 不能据此关闭。当前静态证据能够证明“代码路径存在”和“公共响应做了白名单投影”，不能证明当前候选版本已经和 Provider、旧服务运行行为以及真机结果一致。

本审计只覆盖医院/科室/医生/排班/时段号源的读取；预约占位、预约写入、取消、收费、支付、医保和 HIS 支付回写不在本审计范围内。

## 字段和状态核对

### 已由源码支持的安全收口

- 新端 API 路由在 `apps/api/src/modules/appointments/index.ts:84-98,162-232`，小程序调用在 `apps/miniprogram/src/services/api-client.ts:2413-2451,2720-2783`；页面不会直接请求旧 Provider。
- 日期由服务端按 `Asia/Shanghai` 生成：`apps/api/src/modules/appointments/service.ts:463-494`；排班结果还会复核落在请求窗口内并匹配科室/医生筛选。该实现比旧页面直接使用运行环境本地 `Date` 更可审计，但不等于 Provider 的日期合同已经确认。
- 排班快照使用一次时钟采样、60 秒 TTL、最多 4 路并发写入：`apps/api/src/modules/appointments/service.ts:879-948`。号源读取要求 opaque `scheduleId` 对应未过期快照，不接受客户端提交 Provider 排班号。
- `AppointmentScheduleDetails` 和 `AppointmentScheduleSource` 只保留患者端展示字段：`packages/domain/src/appointments.ts:27-50,87-98`；`mapSource` 不把 `sourceId` 带出 adapter，`mapSchedule` 不把 `hisScheduleId` 带出公共 contract。
- 当前 adapter 对空结果使用统一 response envelope 校验，并对重复 ID、日期格式、数量上限和 `availableSlots > totalSlots` fail-closed；这只能证明代码行为，不能替代 Provider 空结果和停诊样例。

### 仍不能从源码推断的事实

1. **渠道冲突**：旧页面对 `scheduling-depts`、`scheduling-doctors`、`schedulings`、`sources/{hisScheduleId}` 都实际传 `4`（见上表）；新 adapter 的 `REQUEST_CHANNEL` 在 `packages/adapters/src/zhongyang-appointments.ts:31-45` 固定为 `3`，且 `docs/Provider契约-v1.md:64-73` 以门户核对为依据声明门诊微信使用 `3`。在拿到当前 Provider 逐端点请求/响应或院方书面确认前，不能把任一侧当成最终事实，也不能盲改为 4。
2. **医生来源**：旧端独立请求 `scheduling-doctors`；新端从 `schedulings` 聚合医生卡片。需要当前响应证明两种链路的字段和筛选语义等价。
3. **停诊状态**：旧端用 `remainingNumber`（为空时回退 `totalNum-currentNumber`）和 `scheduleStatus===2` 决定开放，见 `department_select.vue:341-363,386-408`。新端只接受已确认的 `usableSourceNum`，公共模型没有 `scheduleStatus`，不能凭空把缺失状态映射成“停诊”或“可预约”。
4. **自然日和实时性**：新端使用服务端 `Asia/Shanghai` 和短期快照，但 Provider `endDate` 是否包含、跨日边界、号源读到的时刻以及停诊/余号刷新延迟，均没有当前候选的真实样例。
5. **历史文档不是当前验收**：`docs/迁移/旧接口清单.md:40-67` 与 `docs/迁移/原生页面迁移状态.md:51-54` 已明确列出部分接口/契约和真实证据待补，不能因为测试通过或页面能打开就改成完成。

## 关闭 P1-04 所需最小证据

在不触发写入的受控环境中，至少需要以下同一候选版本的证据；缺任何一项都保持 P1-04 未完成：

1. 分别取得 `first-depts`、`scheduling-depts`、`schedulings`、`scheduling-doctors`（若 Provider 仍要求）和 `sources/{hisScheduleId}` 的请求与响应，明确 request channel、日期窗口、空结果、错误 envelope 和 `endDate` 规则；请求/响应原文应按项目日志规范放入权限受控文件，不提交 Git。
2. 对排班响应核对 `totalNum`、`usableSourceNum`、旧 `remainingNumber/currentNumber`、`scheduleStatus`、医生资料和日期；对号源响应核对 `sourceId` 存在但不出公共响应、序号唯一、时间点/时间段和停诊/过期行为。
3. 在当前 API 候选版本观察一次目录请求、快照 `persisted/unavailable`、过期引用和 Provider 错误，并能以 trace/request ID 对齐，不把 HTTP 200 或空数组当业务成功。
4. 用当前生成的小程序包在开发者工具和真机完成科室→门诊→医生/日期→排班→时段的只读路径，验证空结果、停诊和过期重试；不得产生锁号、预约或任何费用动作。
