# 基础设施与运维能力迁移边界

本文记录旧 Python 服务中“不一定对应患者页面”的基础设施、任务、文件、实时连接和管理端能力，
以及它们在新 Bun/Elysia 项目中的真实迁移状态。本文的目标是防止把“连接探针通过”、
“有一个替代实现”误判为“旧能力已经兼容迁移”。

本文只描述已经从源码、目标项目代码、部署配置或运行门禁中确认的事实。生产 Redis 是否与旧服务共用实例、
旧 MongoDB 是否有历史集合数据、旧任务是否仍在运行，必须通过部署配置和只读运行证据确认，不能从源码推断。

## 1. 审计范围与结论

### 1.1 旧服务已确认的基础设施

| 能力 | 旧服务证据 | 真实语义 | 新服务状态 |
| --- | --- | --- | --- |
| MySQL | `G:\\fuck\\hospital\\app\\core\\database.py`、SQLAlchemy async/sync engine | 旧业务主库、管理端表、患者和 provider 相关表 | 部分迁移；新服务只写 `hp_*` 目标表，不能据此宣称旧表已替代 |
| Redis 会话与缓存 | `app/common/enums.py`、`module_system/auth`、`module_monitor`、`module_intelligent` | token、验证码、系统配置、字典、在线用户、AI 对话历史等多种语义 | 部分迁移；新服务只使用 `hospital:session:` 会话前缀，旧 namespace 未迁移 |
| MongoDB | `app/core/database.py`、`app/core/mongo_crud.py`、`mongo_getter` | 创建 Motor client、注入 database 和通用 CRUD 端口 | 暂缓；静态扫描未找到当前业务模块的 collection 读写消费者，历史数据和运行使用仍未证明 |
| 定时任务 | `app/core/ap_scheduler.py`、`module_application/job` | APScheduler + MemoryJobStore/RedisJobStore、任务管理 API、任务日志和暂停/恢复 | 部分迁移；新 worker 只承载 outbox 与支付查单，不是通用任务管理替代 |
| 文件与静态资源 | `app/utils/upload_util.py`、`module_common/file`、`module_monitor/resource` | 本地 `static/upload` 上传、下载、删除、目录管理和头像资源 | 未迁移；新服务没有文件上传/下载 API，不能把本地路径或旧 `file_url` 当生产资源事实 |
| WebSocket 与 AI 会话 | `module_intelligent/controller.py`、`get_current_user_ws.py`、`ollama/data_history.py` | query token 鉴权、陪诊实时 WebSocket、文本/音频 AI 会话、Redis 对话历史 | 未迁移；新 API 没有 WebSocket 路由或 AI 会话实现 |
| 管理端 RBAC 与运维 | `module_system`、`module_monitor`、`module_application` | 用户/角色/菜单/字典/参数/通知/日志、在线用户、缓存、服务器资源、文件和任务管理 | 未迁移；患者 token 不得承担 Admin/Operations 权限 |

### 1.2 结论

当前新项目完成的是患者端纵向切片和可恢复支付基础，不是旧 Python 服务的全量基础设施替换。
在文件、实时 AI、管理端、通用任务和 MongoDB 的来源/消费关系没有冻结前，不开放对应新路由，
也不删除旧服务、旧 Redis key、旧静态目录或旧表。

## 2. Redis：前缀、DB 和 ACL 必须共同形成边界

### 2.1 旧 Redis key 语义

旧 `RedisInitKeyConfig` 已确认的前缀包括：

| 前缀 | 旧用途 | 风险 |
| --- | --- | --- |
| `access_token:{sessionId}` | 旧 access token 在线态和 JWT 关联 | 旧管理端/患者端会话，不能由新服务解码或删除 |
| `refresh_token:{sessionId}` | 旧 refresh token | 不能与新平台会话续期逻辑混用 |
| `captcha_codes:{key}` | 验证码和短期过期 | 过期、限流和消费语义尚未迁移 |
| `system_config:{configKey}` | 管理端系统参数缓存 | 可能影响旧服务运行配置，禁止新服务清理 |
| `system_dict:{dictType}` | 管理端字典缓存 | 业务含义、版本和失效策略尚未迁移 |
| `ticket:{ticket}` | 外部页面短期票据；旧实现曾保存原始 access token | 不能复制旧实现；必须重新定义 audience、scope、一次性消费和 owner |
| `{conversationId}` | 旧 AI 会话历史 | key 没有统一业务前缀，存在碰撞、越权和清理风险 |

旧在线用户管理还会扫描和删除 `access_token:*`/`refresh_token:*`，旧缓存管理会扫描 key。
新服务不得执行这些全库扫描或删除动作。

### 2.2 新 Redis 语义

新 `packages/persistence/src/redis-session.ts` 当前只定义：

- `hospital:session:{accessToken}`：保存内部 `userId`，使用 Redis TTL；
- 业务层只依赖 `get` 和带 `EX` 参数的 `set` 最小端口；当前会话存储没有全库扫描、删除或管理命令；
- 不记录 token/用户身份日志，不读取旧 `access_token:*`；
- Redis 未配置或探针失败时，登录和依赖 Redis 的能力必须 fail-closed；不能退回内存会话冒充生产可用。

### 2.3 共用 Redis 实例时的硬门禁

如果旧服务和新服务暂时共用 Redis 实例，发布前必须同时证明：

1. 新服务使用独立 Redis database 或经评审的全局前缀；当前已知新前缀是 `hospital:session:`，
   不能只凭这个前缀推断旧 key 不会冲突；
2. 旧服务全部 key 前缀、TTL、容量和清理动作已经做只读盘点；
3. 新服务的 Redis ACL 只允许访问自身前缀，禁止 `SCAN`、`FLUSHDB`、`FLUSHALL` 和旧前缀删除；
4. 旧服务的在线用户/缓存管理操作不会误删新会话；必要时拆分 Redis database、实例或 ACL 用户；
5. 发生新服务回滚时，只删除新前缀，不能清理整库；发生旧服务回滚时同样不能影响新前缀；
6. 会话迁移不采用“读取旧 JWT/旧 Redis token 并直接换发”的兼容捷径。旧会话失效后重新微信登录，
   这是更容易审计的边界。

生产验收必须保存 Redis endpoint/database/ACL 的脱敏配置摘要、只读 key 盘点结果和隔离验证结果，
不能只保存 `PING=ok`。

2026-08-16 的生产只读快照先证明旧/新服务共用 Redis DB1；随后已完成新 API 的生产会话隔离：
新 API 使用独立 DB3、专用用户 `hospital_v2`，ACL 命令白名单为 `PING/SELECT/GET/SET`，key pattern 为
`hospital:session:*`，TTL 探针和跨前缀 `NOPERM` 探针均通过。旧 Python 服务继续使用 DB1 的 `admin` 全权限账号，
因此当前是“新 API 会话隔离完成、旧基础设施仍未完成整体隔离”，而不是整个 Redis 实例迁移完成。详细证据见
``../release/production-coexistence-readonly-audit-2026-08-16.md``。

## 3. MongoDB：先证明数据，再决定是否迁移

旧服务启动时会创建 `AsyncIOMotorClient`、`app.state.mongo_client` 和 `app.state.mongo`，并提供通用
`MongoCURD` 与 `mongo_getter`。但对当前旧源码中 `request.app.state.mongo`、`app.state.mongo`、
`MongoCURD` 的静态引用盘点，只发现连接、依赖和通用 CRUD 定义，未发现已挂载业务模块的 collection
读写消费者。

这只能得出“当前源码没有证明业务使用 MongoDB”，不能得出“线上 MongoDB 没有数据”。在决定关闭或迁移前，
必须由有权限的运维人员执行只读确认：

- 数据库名、集合名、文档数量、近 30 天读写时间和索引；
- 应用日志、定时任务或人工脚本是否使用 Mongo；
- 是否存有报告原文、AI 历史、审计附件等不能直接丢弃的数据；
- 数据 owner、保留周期、脱敏导出和恢复方式。

未完成上述确认前，新服务不新增 Mongo 依赖，也不让 Mongo 连接探针成为患者 API 的隐式必需依赖。
若最终确认没有业务数据，应形成“无业务消费者 + 线上集合为空/已归档 + 可恢复备份”的关闭证据。

## 4. 调度器与 Worker：运行机制不能冒充任务管理

### 4.1 旧调度器行为

旧 `ap_scheduler.py` 使用 `AsyncIOScheduler`，配置了 `MemoryJobStore` 和 Redis job store，支持 date、
interval、cron 触发，默认 `max_instances=1`、`coalesce=False`，并把任务事件写入旧数据库日志。
`module_application/job` 还提供任务新增、修改、删除、暂停、恢复、重调度、导入导出和任务日志 API，
并由 `AuthPermission` 保护。

这意味着旧任务不仅是一个定时循环，还包含：任务定义、触发器、管理权限、执行状态、失败记录和运维操作。

### 4.2 新 Worker 当前边界

新 `apps/worker` 当前只有两类明确运行能力：

- 消费 MySQL `hp_outbox_events`，按 lease、attempts、availableAt 和错误状态重试；
- 执行支付查单计划，并通过持久化事实和 provider 查单推进可恢复状态。

它没有通用 job definition、cron 编辑、暂停/恢复、任务日志查询或 Admin API。因此：

- 不能把旧 APScheduler job store 直接指向新 worker；
- 不能把旧任务表/Redis job 数据未经逐项映射就导入；
- 不能让 worker 进程内存成为唯一任务状态；
- 同一任务必须有持久化唯一标识、租约/并发约束、幂等执行和最终事实查询；
- provider 超时不能被 worker 直接解释为业务成功，必须进入待确认或可重试状态。

未来若迁移通用任务，顺序应为：任务目录与权限 contract → 持久化任务/运行实例 → lease/并发策略 →
审计日志 → 管理端只读 → 管理端写操作 → 逐任务灰度切换。旧调度器在每个任务有替代证据前保持运行。

## 5. 文件、报告和静态资源：本地路径不是资源授权

旧服务的上传配置指向 `static/upload`，上传工具按扩展名、大小、日期目录和随机文件名写本地文件；
`module_common/file` 提供本地上传/下载，`module_monitor/resource` 还提供管理端目录浏览、上传、下载、
删除、移动、复制和重命名等能力。旧头像、报告和静态资源因此不能只按页面上的 `file_url` 迁移。

新项目当前没有文件上传/下载模块，报告详情也不返回未经授权的文件 URL。这是有意保持的安全边界，
不是功能遗漏可以忽略。后续资源模块必须先冻结：

1. 资源 `resourceId`、owner、业务类型、内容摘要、MIME、大小、版本和保留期限；
2. 对象存储/私有桶、服务端签名 URL、下载次数/TTL 和撤销机制；
3. MIME 与内容双重校验、扩展名白名单、病毒/恶意内容检测和图片元数据处理；
4. 报告/头像/用户附件的访问授权、审计、删除和备份恢复；
5. 旧本地文件的只读清点、哈希去重、脱敏导入、失败重试和回滚。

在此之前，不把服务器本地路径、旧 `file_url`、永久公网 URL 或客户端传入的 `fullUrl` 写入新业务事实。

## 6. WebSocket、AI 和会话历史：需要独立的业务协议

旧 `module_intelligent/controller.py` 提供陪诊实时 WebSocket，并通过 query token 检查旧 Redis access token；
文本/音频导诊、客服会话使用 `conversation_id`，历史直接按会话 ID 写入 Redis，并带消息数量上限和过期时间。
旧客户端还存在携带 token、`patId` 并自行重连的 WebSocket helper。

新 API 当前没有 WebSocket 路由，也没有 AI/陪诊实现。后续不能只把旧路由和 Redis history 原样搬过来，至少要先冻结：

- 握手鉴权、audience、scope、患者 owner 和会话有效期；
- 消息 schema、版本、序列号、最终事实查询和断线补偿；
- 文本/音频是否落盘、内容安全、模型版本、知识版本和免责声明；
- 单用户/单患者并发、限流、重放、重复消息和服务端主动关闭语义；
- 会话历史的持久化边界、隐私保留期限和删除机制；
- WebSocket 日志中的 `sessionId`、`messageId`、结果状态和错误类型，禁止 token、患者号和对话正文。

正式迁移时，使用已鉴权 HTTP 握手换取短期连接引用或受控 cookie，不把 access token、provider 患者号或
完整 `patId` 放入 URL；断线重连不能只重放客户端最后一条消息，必须可以查询服务端最终状态。

## 7. 管理端、RBAC、监控和日志边界

旧 `module_system` 已包含用户、角色、菜单、部门、岗位、字典、参数、通知和操作日志；旧 `module_monitor`
包含缓存、在线用户、服务器资源和文件资源管理；这些接口依赖 `AuthPermission` 权限节点。新服务当前没有
Admin API、RBAC、在线用户管理、服务器资源管理或后台日志查询实现。

因此当前发布边界是：

- 旧管理端继续由旧 Python 服务提供，新服务不复用旧 Admin token；
- 患者 API 的 Redis 会话只表达患者身份，不表达 `system:*`、`monitor:*` 或 `app:job:*` 权限；
- 新增管理端必须使用独立 audience、权限模型、管理员 MFA/网络边界（按部署要求）和审计事件；
- 运维指标进入部署/日志平台，不把服务器资源、Redis 全库管理和文件目录管理暴露给患者 API；
- 新服务的 Pino 日志只记录诊断元数据，不能把旧操作日志表当作新服务日志唯一落点。

## 8. 新旧服务共存发布顺序

```text
旧服务保持运行
    |
    v
只读确认 MySQL / Redis / Mongo / 旧任务 / 文件目录的真实来源
    |
    v
新服务只使用 hp_*、hospital:session:* 和已冻结的 worker 事件
    |
    v
按业务域分别完成 contract、迁移、日志、回滚和真实路径验收
    |
    v
新旧流量灰度与指标对比
    |
    v
逐项停用旧能力，最后才评估旧服务、旧 Redis namespace 和旧资源的下线
```

任何单项迁移都必须同时留下以下证据：

1. 旧行为与数据来源快照；
2. 新 contract、状态机、owner/权限和错误映射；
3. persistence migration、索引、幂等和恢复方案；
4. 代码测试、本地真实依赖测试、staging provider 测试和公网/真机证据（适用时）；
5. 日志事件、告警指标、回滚步骤和旧服务影响评估。

## 9. 下一步优先级

1. 保留生产 Redis endpoint/database/ACL、旧 key 前缀/TTL 和旧任务实例的只读盘点；新 API 会话隔离已完成，后续只在旧服务替代/秘密轮换窗口收紧 DB1 的 `admin` 权限。
2. 对 MongoDB 和 `static/upload` 做只读资产清点，先得到“迁移、归档还是确认无业务使用”的结论。
3. 将新 worker 的 outbox/查单验收与通用任务管理明确分开，补齐 lease、重试、死信/人工处理和运行日志的运维手册。
4. 获取 AI/WebSocket、文件资源和管理端的正式 provider/产品 contract 后，再按独立领域设计，不从旧实现推断安全协议。
5. 业务迁移继续按患者端只读 → 写入 → 支付/医保/HIS 的顺序推进；本基础设施审计不打开支付、医保、HIS 或旧服务下线。
