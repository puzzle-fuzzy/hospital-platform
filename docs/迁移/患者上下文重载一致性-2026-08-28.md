# 患者卡片重读一致性记录

更新时间：2026-08-28

## 结论

本轮只修正患者上下文的展示一致性，没有新增 Provider 调用，也没有修改旧项目。

采血预约、我的快递、订阅消息三个原生页面在重读当前患者时，原先会先执行
`patient: null`，目录同步或会话恢复出现短暂异常时又会在错误态保留空患者。这样会让
患者姓名卡片闪退，并把“下游服务暂时失败”误导成“没有选择就诊人”。

现在的统一规则是：

1. 同一会话中重读患者目录时，保留上一份已经确认的患者卡片，避免页面高度和身份提示闪动。
2. 只有会话明确失效、会话代际变化或本地已经没有可用会话时，才清除旧患者上下文。
3. 用户换人后由统一选择页重新确认，不能把上一位患者的卡片带到新选择中。
4. 本轮页面仍然按照迁移准入显示业务状态，不会因为保留患者卡片而伪造快递、采血或订阅能力已经接通。

## 新旧实现对照

### 旧项目

- `patient-express` 对应的旧页面只有快递入口和静态占位，没有发现可迁移的真实物流查询合同。
- 采血预约页面使用固定患者和固定院区信息，项目列表为空，没有发现可直接迁移的预约写入流程。
- 订阅消息页面只维护页面内存开关，没有发现微信订阅消息授权和服务端保存接口。

因此本轮没有为了“看起来可用”而接入未经确认的 Provider 写入或外部服务。

### 新项目

以下页面现在都复用患者选择服务的同一组上下文边界：

- `apps/miniprogram/src/pages/blood-appointment/blood-appointment.ts`
- `apps/miniprogram/src/pages/patient-express/patient-express.ts`
- `apps/miniprogram/src/pages/patient-subscription/patient-subscription.ts`

页面加载期间使用 `preservedPatientForReload` 保留已经确认的患者；错误分支使用
`shouldClearPatientContextAfterError` 判断是否真的需要清除。实现中的中文注释说明了
“视觉上下文保留”和“业务权限重新确认”是两件事，后续不能把前者当成绕过患者目录校验。

## 尚未完成的业务

这次修复不代表三个页面的真实业务已经迁移完成。真实快递查询、采血预约写入、订阅消息授权/保存仍需各自的旧端接口事实和 Provider 合同；在合同确认前继续保持迁移状态页是正确边界。
