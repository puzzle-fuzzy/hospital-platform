> 不把旧 provider 字段直接升级为新公共 contract。

## 1. 本次审计结论

当前新端已经有报告目录，但报告不是门诊病历；二者不能因为页面都叫“查询”就共用一个路由或数据模型。
本次已修正新小程序“我的”页和首页顶部入口：`门诊病历` 使用明确的 `medical-record` 动作，
在 provider/HIS contract 完成前展示迁移提示，不再误用 `reports` 或通用建设中分支。
门诊就诊记录目录的字段差异和待确认问题另见 [`medical-record-directory-contract-draft.md`](病案目录契约草案.md)；
该草案不是可调用接口文档。

## 2. 旧端实际调用与字段风险

### 2.1 门诊病历页面

旧页面 `pagesB/health/electronic_record.vue` 实际只调用：

```text
POST /msun-middle-aggregate-clinic/v1/out-visit-records
startDate = 最近 30 天 00:00:00
endDate   = 当前日期 23:59:59
type      = "5"
patId     = 选择器返回的 provider 患者号
```

页面直接读取 `regId`、`deptName`、`doctorName/docName`、`visitTime/visitDate`、`hospitalName`、
`clinicTypeName`、`chargeClassName`、`patName`、`sexName`、`patAge`、`maritalStatusName`、
`diagnosisName/diagnosis` 等原始字段。这里同时混有患者身份、诊断和 provider 记录号，不能直接进入
新 API response。

旧 `medicalRecord.ts` 还定义了：

- `GET /msun-middle-aggregate-clinic/v1/out-emrs?out-visit-record-id=...`：病历内容；
- `POST /msun-middle-aggregate-zyemr/v1/m-records/mr-menus`：住院病历目录；
- `GET /msun-middle-aggregate-zyemr/v1/m-records/mr-contents`：住院病历内容；
- `GET /msun-middle-aggregate-zyemr/v1/m-records/mr-content-structs`：住院结构化内容。

当前旧门诊病历页面没有调用 `out-emrs`，因此“列表已展示”也不能宣称病历正文已经迁移。

### 2.2 住院页面

旧 `pagesB/health/inpatient_center.vue` 先按 `patId` 查询住院患者信息，再用返回的 `patInHosId`
查询日费用。返回数据包含住院号、床位、病区、入出院状态、医生/护士、诊断、婴儿信息、身份证和卡号等
大量敏感字段；旧页面还使用选择器传来的医院、日期区间和 provider 患者号。

页面真实顺序是：选择器变更后调用 `GET /msun-middle-aggregate-hsz/v1/patients?patId=...`；
切换到“费用”页签时，取第一条住院患者结果的 `patInHosId`，再调用
`GET /msun-middle-open-settlepay/v1/inpatient-settle-singles/inpatient-in-day-singles`，并把页面选择的时间范围
格式化为 `startTime/endTime`。旧页面还把 `patInHosId` 的第一条结果当作当前住院 episode，没有定义多次住院、多个 episode、
空结果和并发切换时的最终一致性。这些行为不能直接复制到新端。

住院费用响应同时包含明细、诊断、医生、住院号和总额等字段；金额单位、时间窗口、总额是否含医保以及结算状态在旧页面
没有形成可审计的公共 contract。新端必须先确认 episode 的权威性和 owner 关系，再允许查询费用；不能因为患者有一条住院
记录就默认允许读取第一条费用，也不能把 provider 返回的敏感字段原样写入日志或小程序缓存。

新端不能接受 `patId`、`patInHosId`、住院号或医院内部 ID 作为小程序输入。正确顺序应是：

```text
平台 session + 内部 patientId
  -> owner-scoped 患者临床映射
  -> 服务端取得当前允许访问的住院 episode
  -> 公开脱敏住院摘要 / 短期住院记录引用
  -> 按引用查询病历或住院费用
```

住院费用也不是门诊费用：不能把住院日费用明细复用 `OutpatientPaymentRecord`，不能让客户端提交金额、
医保金额或结算状态。

### 2.3 医院列表和院内导航

旧 `hospitalList.vue` 只渲染一张固定医院图片、医院名称、地址和“去挂号/查看路线”文案，没有请求医院列表
接口；它本质是静态入口，不应为了“补齐接口”虚构 provider。新端已迁移到
`pages/hospital-list/hospital-list`，图片改为受控本地资源，卡片进入既有预约目录，路线按钮只提示“路线服务暂未开放”，
不猜测坐标或调用地图。旧 `navigation.vue` 也只有本地地图图片、`aspectFit` 和点击预览，新端已按同样边界迁移到
`pages/hospital-navigation`。

## 3. 新 contract 必须先冻结的规则

在取得新的 provider/HIS 文档前，只允许完成 contract 草案、字段差异表和测试 fixture，不注册真实业务路由：

1. 门诊就诊记录目录、病历正文、住院 episode、住院病历和住院费用必须拆分端口，不能由报告或门诊费用接口顺手扩展。
2. 小程序只传内部 `patientId`；外部 `patId`、`out-visit-record-id`、`patInHosId`、住院号和原始医院 ID 只能在服务端 owner 校验后使用。
3. 门诊记录和病历详情要分成目录与内容两个权限层；详情应使用服务端生成的短期 opaque 引用，并做 owner、患者和过期校验。
4. 正文 XML/JSON、结构化病历、诊断、身份证、卡号、联系方式和文件 URL 默认不进入公共 contract；缺少脱敏清单时 fail-closed。
5. 住院状态必须定义在院、出院、取消入院、结算中等枚举及未知值策略；HTTP 200 不能推导住院或结算成功。
6. 住院费用必须明确元/分单位、账单时间时区、分页/排序、总额守恒和最终结算状态；不复用门诊费用查询窗口。

## 4. 下一步顺序

1. 先取得新 provider 文档，按 [`Provider文档接入流程.md`](../Provider文档接入流程.md) 登记来源、版本、请求/响应/错误/权限/脱敏和真实证据，再逐项填写 [`medical-record-directory-contract-draft.md`](病案目录契约草案.md)；旧代码只作为差异线索。
2. 优先做“门诊就诊记录目录”只读闭环：contract → owner-scoped patient mapping → adapter → API → 原生页面 → 分页/竞态测试 → 公网和真机验收。
3. 目录真实证据稳定后，再做 `out-emrs` 病历内容短期引用；正文下载、结构化内容和报告解读分别设计。
4. 住院信息与住院费用另开阶段，先确认住院 episode 的权威来源和金额/结算边界，再实现页面。
5. 医院列表的单院区静态配置页面已经迁移；后续若要支持机构/院区动态目录、多院区选择或真实路线，必须先取得机构 ID、院区版本、坐标来源、路线授权和错误语义。互联网医院跳转必须等外部小程序/域名白名单和授权协议，不通过万能 webview 或旧 provider 直连替代。

## 5. 当前验收与禁止项

- 新小程序“门诊病历”入口只能显示明确迁移提示；报告目录仍从独立报告入口进入。
- 不以旧页面字段存在、旧接口返回 200 或本地 mock 患者数据宣称病历/住院已迁移。
- 不把病历正文、诊断、住院号、身份证、卡号或 provider 记录号写入 Pino 日志或小程序本地缓存。
- 动态院内导航、动态医院列表、住院和病历在新文档到达前继续保持未注册、可回滚和旧服务不受影响；当前已迁移的静态医院卡片不代表机构服务已完成。
