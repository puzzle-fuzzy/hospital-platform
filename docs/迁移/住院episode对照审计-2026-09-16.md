# 住院 episode 对照审计（2026-09-16）

## 结论

P1-10 当前不能直接实现为可查询 API。旧服务确实存在住院患者查询，但它返回 Provider 住院登记数组，旧页面把第一条记录当作当前住院 episode，并没有形成可直接公开给小程序的授权、字段、状态和多次住院 contract。新端目前只有住院信息页面外壳，未实现住院 API、adapter、domain 或持久化链路；保持关闭态是当前安全且与旧服务证据一致的结果。

本审计只覆盖住院患者信息 / episode 只读查询。住院日费用、住院预缴、医保、结算、退费和任何支付/HIS 支付回写均不在本项范围内，也不以本审计作为放行依据。

## 1. 旧服务真实行为

### 1.1 Provider 接口和响应语义

旧 API 模块声明住院查询参数只有 Provider 患者号 `patId`，接口为：

```text
GET /msun-middle-aggregate-hsz/v1/patients?patId=...
```

证据：`/Users/yxswy/Documents/GitHub/hospital/hospital-app/src/api/modules/medicalRecord.ts:129-132,233-241`。

旧类型 `InpatientPatientItem` 直接暴露以下几组高敏感 / 高风险字段：

- 住院登记标识：`patId`、`patInHosId`、`patInHosCode`（同文件 `:159-164`）；
- 身份和联系方式：姓名、身份证、就诊卡、电话、地址（`:165-175`）；
- episode 状态：入院/出院时间、`patInStatus`、`patStatus`、`patInBedStatus`（`:177-187`）；
- 病区、床位和科室：病区 ID/名称、床 ID/床号、病房号、科室 ID/名称（`:189-202`）；
- 医护、诊断、护理和病情：医生/护士、入出院诊断、诊断数组、护理等级、病情（`:204-226`）；
- 婴儿信息：住院号、姓名、母亲、性别、出生日期、身高和体重（`:227-228`）。

这些是旧端 TypeScript 的开放类型，不等于已经确认的新端公共响应白名单，也不等于 Provider 对所有字段都有稳定返回保证。

### 1.2 旧页面的查询流程

旧页面选择器回调携带患者、医院、日期区间等信息，但住院基本信息请求实际只取 `payload.patient.patId`，随后调用 `getInpatientPatientApi({ patId })`；证据：`/Users/yxswy/Documents/GitHub/hospital/hospital-app/src/pagesB/health/inpatient_center.vue:396-413,415-439`。

旧页面将响应仅按“是否为数组”处理，数组中的每一条都直接渲染为住院信息；证据：同文件 `:66-238,423-426`。页面展示了姓名、住院号、性别、年龄、入出院时间、状态、病区、科室、床位、医护、诊断、护理、病情和婴儿信息等字段。

旧页面没有定义以下业务规则：

1. 多次住院 / 多个 episode 的选择或排序规则；
2. `patInStatus`、`patStatus`、`patInBedStatus` 的完整枚举、未知值策略和状态转换；
3. Provider `patId` 与平台内部患者的 owner 映射和授权撤回；
4. 空结果、重复结果、字段异常、Provider 拒绝、超时和患者快速切换时的最终一致性；
5. 哪些住院号、诊断、床位、医护、联系方式和婴儿字段可以向小程序公开。

旧页面确实把第一条结果的 `patInHosId` 用于后续日费用请求，证据：同文件 `:377-383,425-429`。该后续调用属于住院费用范围，本项不迁移、不复用、不验证，也不能反过来证明 episode 查询已经完成。

## 2. 新端当前实现

### 2.1 页面只是关闭态外壳

当前原生页面只有注册统一临床状态外壳的代码：

- `apps/miniprogram/src/pages/inpatient-center/inpatient-center.ts:1-4`：只调用 `registerClinicalSurfacePage("inpatient-center")`，并明确真实 episode 查询等待独立 Provider contract；
- `apps/miniprogram/src/pages/inpatient-center/inpatient-center.wxml:1-56`：展示当前就诊人上下文、服务状态、迁移说明和返回入口，没有住院数据字段或住院请求；
- `apps/miniprogram/src/services/clinical-entry-surface.ts:51-90`：统一外壳只读取已确认的患者目录上下文，不把患者选择结果假装成病历或住院数据。

当前 feature 状态也明确保持关闭：`apps/miniprogram/src/services/feature-navigation.ts:333-338` 标记为 `待 provider contract`，并注明不会复用门诊患者标识查询住院数据；`apps/miniprogram/src/services/legacy-page-catalog.ts:205-210` 仅登记页面外壳和独立 episode 提示。

### 2.2 未发现可迁移的住院业务链路

截至本审计，当前仓库没有住院信息的 API route、Provider adapter、domain contract、repository 或小程序数据客户端。`inpatient-center` 只被归入 `provider-read-only` / `C-clinical-readonly-contracts`：

- `apps/miniprogram/src/services/migration-coverage.ts:113-125,184-190`；
- 当前 `apps/api/src/modules`、`packages/adapters/src`、`packages/domain/src`、`packages/contracts/src` 中没有对应住院信息实现。

因此不能把已有门诊病历 `patientId`、门诊报告、患者目录快照或任何住院费用标识拼接成住院 episode，也不能因为页面可以进入、患者目录可以加载或状态页显示“迁移中”就宣称住院信息已迁移。

## 3. 必须先冻结的 contract

在实现任何 API 或打开 gate 前，至少需要同一候选版本的以下材料：

1. Provider 正式住院查询 contract：请求字段、响应样例、分页/排序、超时和拒绝错误；
2. 平台患者 owner 映射：平台 session / 内部 `patientId` 如何映射 Provider 患者，禁止由小程序提交 `patId`、`patInHosId`、住院号或医院内部 ID；
3. episode 规则：多个 episode 的返回顺序、当前 episode 选择、历史 episode 是否可查、已出院/取消/结算中/未知状态枚举；
4. 公开字段白名单：住院号、姓名、时间、状态、病区、床位、科室、医护、诊断、护理、病情和婴儿信息逐字段确认脱敏策略；
5. 安全边界样例：未登录、非 owner、合法空、Provider 拒绝、超时、重复/乱序、字段类型异常和并发切换；
6. 运行验收材料：当前候选代码版本、生成的 DevTools 包、同版本公网请求、Provider 请求/响应关联、真机行为和生产灰度结果。

## 5. 处理决定

- P1-10 保持未完成，不新增住院 API、adapter、domain 或配置 gate；
- 继续保留 `inpatient-center` 关闭态，并保留“不得复用门诊患者标识”的用户可见边界；
- 只有 contract、owner 映射、脱敏字段、错误样例和同版本运行证据齐备后，才进入实现；
- 住院费用和住院支付另行处理，不能由本项解锁。
