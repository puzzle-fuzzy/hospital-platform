# 电子锦旗与表扬信反馈对照审计（2026-09-16）

## 结论

旧服务确实存在电子锦旗和表扬信的创建、用户列表和患者端展示页面，但旧客户端把患者、就诊记录、科室和医护人员的名称/ID快照直接放进请求体；旧服务只校验 `user_id` 与当前用户一致，没有证明患者归属、就诊记录归属或名称与 ID 一致，也没有内容审核、公开脱敏、撤回或幂等。

新端已经迁移当前就诊人上下文、加载/错误/未开放三态和固定入口，但没有注册旧的创建/列表 API。这个关闭态符合当前证据边界：不能把旧 `display_type=1` 当作已经审核公开，也不能把旧请求字段原样接入。P1-17 保持未完成，先冻结独立反馈域 contract。

本审计只覆盖电子锦旗、表扬信及其非支付反馈记录，不触碰支付、医保、收银台、退费、账单支付或支付相关 HIS 回写。

## 3. 放行前必须冻结的 contract

至少需要确认：

1. 患者 owner、代填人授权和真实就诊/encounter 引用如何由服务端生成与校验；
2. 医护目录和科室目录来源，名称与内部 ID 的一致性及失效规则；
3. 表扬信与锦旗的内容长度、敏感词/内容安全、附件类型和病毒扫描规则；
4. 创建幂等、并发、超时重试、草稿/审核中/通过/拒绝/撤回状态；
5. `public` 是否需要人工审核、公开字段脱敏、访问受众、撤回和缓存失效；
6. 患者本人历史记录与公开记录是否分开读模型，医护/运营审核权限如何隔离；
7. 内容保留/删除、审计日志字段，以及空、拒绝、超时、重复和非 owner 样例；
8. staging、DevTools、真机和生产同版本的真实链路验收证据。

新 API 不应暴露旧 `patient_name`、`patient_id`、`visit_record_id`、`department_name`、`medical_staff_id` 或可任意输入的旧 `display_type` 作为权威业务事实；应只接受服务端可校验的内部患者/就诊引用和意图字段。

- P1-17 保持未完成，不接入旧创建/列表 API，不导入旧四条表扬信和四条锦旗历史记录；
