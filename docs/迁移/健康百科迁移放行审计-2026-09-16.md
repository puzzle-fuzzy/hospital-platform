# 健康百科迁移放行审计（2026-09-16）

## 结论

P1-12 具备真实旧数据源和新端工程骨架，但还不能进入 staging 或患者端发布。旧服务确实提供健康百科目录、按人群/科室/部位/症状查询疾病以及疾病/药品详情；新端已经有独立的版本化 bundle validator、staging 单事务导入器、published-only repository、API contract 和小程序读页面。当前阻塞点是真实源快照质量、临床审核 bundle 和后续发布/撤回/真机证据，不是继续补一个页面或把旧正文直接复制过来。

本项只处理健康知识只读内容迁移。健康自测、风险评估、BMI/血压临床规则、报告解读以及支付/医保能力不由本审计解锁。

在当前仓库执行：

```text
pnpm health:source:audit
```

结果为 `sourceValid=true`、`publishable=false`、`strictPassed=true`（非 strict 模式），源元数据为：

- `system=legacy-hospital`；
- `exportedAt=2026-09-08T17:30:51.978Z`；
- `mappingVersion=legacy-health-knowledge-v1`；
- `publicationState=not-approved`。

聚合规模为 15,668 条条目：人群 7、科室 17、部位 17、症状 5,911、疾病 8,509、药品 1,207；另有疾病详情 8,509、药品详情 1,207、疾病关系 16,259、部位-症状关系 5,910、症状-疾病关系 19,776。

质量摘要为：疾病-药品重复名称组 6、可点击但无药品 ID 的关系 0、需确认的首尾清理字段 10、旧正文控制字符 115、忽略旧字段 1、忽略旧来源 1。`pnpm health:quality:findings` 只输出 JSON 路径、数组索引和数量，未输出正文或名称；当前定位报告显示控制字符分布在疾病预防文本和多条药品说明字段中。

```text

```

## 3. 当前新端代码状态

### 3.1 已具备的迁移骨架

- 新 API 保留健康百科只读路径，使用 camelCase opaque ID、最多 10 个症状、认证后再做参数检查，见 `apps/api/src/modules/knowledge/index.ts:29-43,49-221`；
- API 服务层读取发布内容并只记录版本、数量和固定错误原因，见 `apps/api/src/modules/knowledge/service.ts:210-258`；
- MySQL repository 只选择当前生效的 `status='published'` 版本，并在两个版本窗口重叠时 fail-closed，见 `packages/persistence/src/mysql-health-knowledge-repository.ts:305-351`；
- bundle validator 拒绝未知字段、错误类型、跨类型关系、可点击药品缺少 ID、没有完整详情集、未带时区时间和隐藏控制字符，见 `packages/domain/src/knowledge-import.ts:94-271,780-817`；
- staging 导入命令先校验 bundle，再要求 `DEPLOY_ENV=staging` 和显式确认，并在一个事务内写入，见 `packages/persistence/scripts/health-knowledge-bundle-import.ts:20-25,58-80,95-180`；
- 只读 bundle check 已存在：`packages/domain/scripts/health-knowledge-bundle-check.ts:22-85`，命令为 `pnpm --filter @hospital/domain knowledge:bundle:check -- <bundle.json>`，不连接数据库或 Provider；
- 小程序搜索和详情页只消费带 publication 元数据的安全读模型，见 `apps/miniprogram/src/pages/health-knowledge-search/health-knowledge-search.ts:37-101`、`apps/miniprogram/src/pages/health-knowledge-detail/health-knowledge-detail.ts:46-143`。

### 3.2 当前仍然关闭的事实

`apps/api/src/app.ts:254-278` 虽然挂载健康知识只读模块，但默认 repository 没有有效 published 内容时会返回稳定的内容不可用错误；相关 app 测试已验证未审核/未发布时 fail-closed，见 `apps/api/src/app.test.ts:640-697`。当前没有 `.local/health-knowledge/reviewed-bundle.json`，只有 `.local/health-knowledge/legacy-source-snapshot.json`。

把旧源快照直接交给 bundle check 的实际结果是：

```text
ok=false
error.code=invalid-bundle
error.path=bundle.schemaVersion
```

这说明源快照和正式审核 bundle 是两种不同输入，不能通过改名、复制或手工修改 publication 状态绕过审核。

## 4. 审核队列和放行门

执行 `pnpm health:review:queue` 与 `pnpm health:remediation:ledger`，均返回 `publishable=false`，未解决门数量为 6：

1. 源快照质量：重复关系、控制字符、清理字段和未定义来源待处理；
2. 临床内容审核：源状态仍为 `not-approved`，不能由工程工具推断医学正确；
3. 版本与发布元数据：缺正式 bundle、`reviewerRef`、带时区 `reviewedAt`、生效窗口和免责声明；
4. staging 事务导入：未通过 bundle check 和责任确认，不连接 staging；
5. 发布与撤回演练：未验证同版本读取、重叠窗口、撤回和缓存/患者端收敛；
6. 真机只读验收：未形成页面结果、客户端 requestId、服务端 traceId 和内容版本的同链证据。

## 5. 处理决定

- P1-12 保持未完成，不复制源快照，不生成伪造审核 bundle，不打开患者端内容发布；
- 现有导出、质量定位、review queue、bundle check、staging 事务导入和 published-only 读模型保留，已具备继续迁移的工程入口；
- 下一步输入必须来自内容责任人：完成 133 条质量告警处理、重新导出并做脱敏复核，再提供独立临床审核 bundle；
- 只有 bundle check、staging 导入/回滚、发布/撤回/重叠窗口演练、API 同版本查询和真机证据齐备后，才考虑修改患者端 gate；
- 当前审计没有修改健康内容数据库、旧服务、线上配置或支付/医保代码。

## 7. 顺序复核补充（2026-09-17）

本轮重新逐项核对旧小程序 `health_encyclopedia.vue`、`search_result.vue`、`disease_detail.vue`、`drug_detail.vue` 与当前健康百科、症状查询、疾病详情和药品详情页面：

- 旧疾病详情的概述、病因、症状、检查、预防、治疗字段，当前新端已按白名单字段展示为连续详情区块；疾病详情中的药品入口也已覆盖。旧端病因页中的示例比例/机制文案不是可靠内容源，不迁移。
- 本轮没有发现可在无审核 bundle、无质量清理和无发布证据前安全新增的功能缺口。继续不导入旧百科数据、不生成 published 版本、不开放患者端内容发布。

因此 P1-12 的剩余工作仍是内容质量处理、内容责任/临床审核、staging 发布/撤回/重叠窗口演练和真实内容验收，不把静态页面及本地回归测试记作内容迁移完成。
