# 临床只读四条线并行迁移工作板（2026-08-25）

> 本文用于把仍未迁移的临床相关入口拆成可以并行推进的独立队列。
> 它不是接口实现文档，也不授权把旧 Provider URL、`patId`、住院号或医生快照
> 直接放入新 API。没有正式材料时，页面继续进入统一状态页，旧服务、旧数据库、
> 旧 Redis 和线上旧进程保持不变。

## 1. 为什么要拆成四条线

旧端把门诊病历、住院信息、我的医生和电子导诊单都放在“就诊/健康”入口下，
但它们对应的事实来源、患者授权和数据保留规则不同：

| 队列 | 旧端线索 | 首个安全目标 | 不能复用 |
| --- | --- | --- | --- |
| A：门诊记录 | `out-visit-records` | owner-scoped 门诊就诊记录目录 | 报告目录、预约历史、诊断正文 |
| B：住院 episode | 住院患者与住院日费用接口 | 当前患者可访问的住院 episode 摘要 | 门诊 `patientId`、门诊费用、第一条住院记录 |
| C：医生关系 | 医生快照与关注关系 | 受控医生目录的只读列表 | 旧客户端快照、患者提交的医生名称/ID |
| D：电子导诊/问诊 | 预约历史复用和外部入口 | 先确认会话/导诊单来源，再做只读目录 | 预约记录冒充导诊单、任意 WebView、实时队列 |

四条线共享“平台会话 + 内部 `patientId` + 低敏日志”原则，但不共享业务模型。
一个队列被 Provider 阻塞时，其他队列仍可继续完成材料登记、字段白名单和验收准备。

## 3. 每条线统一的实现阶梯

任何一条线都必须按以下顺序推进，不能从页面或旧接口转发开始：

```text
材料登记与 SHA-256
  -> 请求/响应/空/拒绝/超时样例
  -> owner 与患者映射
  -> 字段白名单和禁止字段
  -> adapter 与错误归一化
  -> domain 只读不变量
  -> persistence（只有需要快照或短期引用时）
  -> Elysia API
  -> 原生小程序页面
  -> Pino 日志和敏感字段测试
  -> 内网、公网、开发者工具、真机证据
```

其中任意一层缺失，状态只能是“材料已登记”“代码已实现”或“待验收”，
不能写成“已迁移”。HTTP 200、空列表、测试 fixture 和状态页都不能单独构成业务完成。

## 4. 四条线必须坚持的业务不变量

### A：门诊记录

- 客户端只能提交内部 `patientId`；Provider 患者号和门诊记录号由服务端映射。
- 目录和正文是两个权限层；目录返回的公开摘要不能自动获得正文权限。
- 详情必须使用短期 opaque 引用，并重新校验 owner、当前患者、会话代际和 TTL。
- 诊断、身份证、卡号、联系方式、正文 XML/JSON 和附件 URL 默认不进入公共响应或日志。

### B：住院 episode

- 住院 episode 是独立临床事实，不能由门诊患者有记录推导出来。
- 存在多次住院或多条在院记录时，服务端必须返回可解释的选择结果，不能静默取第一条。
- 在院、出院、取消入院、结算中和未知状态必须有明确枚举；未知值不能显示为“住院中”。
- 住院费用必须单独定义金额单位、时间区间、分页、总额守恒和最终结算状态，不能复用门诊费用模型。

### C：医生关系

- 医生目录事实与“我的医生”关系事实分开存储、分开失效；关系不能承载医生名称/头像快照作为权威资料。
- 关注/取消关注是命令，不使用 GET 删除；重复关注必须由 owner + 医生引用的唯一约束保证幂等。
- 客户端不能提交医生姓名、科室名称或 Provider 医生号作为关系依据。
- 医生离职、科室变更或目录下线时，关系应进入可解释的失效状态，而不是继续展示旧快照。

### D：电子导诊/问诊

- `requestChannel`、预约记录和电子导诊单不能凭旧页面命名或默认值互相推导。
- 实时叫号、队列、取药/检查执行状态必须有独立实时或查询 contract，预约摘要不能冒充。
- 外部问诊/客服只能使用 allowlist、短期会话和明确回跳；不恢复万能 WebView 或长期 ticket。
- 问诊正文、医护备注、模型建议和内部风险信息不能进入患者端公共响应。

## 5. 日志与验收最低标准

四条线统一使用组合根注入的 Pino logger，至少要能按同一链路关联：

```text
微信页面 requestId
  -> Elysia traceId / requestId
  -> 业务域事件
  -> Provider requestId（如存在）
  -> 最终状态或明确失败原因
```

允许记录：业务域、操作名、内部资源引用、患者作用域哈希、是否可重试、耗时、
Provider requestId 和固定错误码。禁止记录：姓名、身份证、卡号、Provider 患者号、
医生联系方式、医疗正文、原始请求体和 Provider 原始报文。

每条线都要分别验证成功、合法空结果、未登录、非 owner、Provider 拒绝、超时、
会话切换和重复读取。真机业务证据必须与同一候选的页面 requestId 和服务端日志配对，
不能用另一条线的预约/报告请求代替。

## 6. 当前停止条件

在材料到达前，本板只允许新增审计、contract 草案、字段白名单、测试矩阵和状态页文案：

- 不注册 `/api/v2/medical-records`、住院、医生关系或问诊写入路由；
- 不新增 Provider 兼容转发，不把旧 `patId`、`patInHosId` 或医生 ID 暴露给小程序；
- 不把报告、预约历史或门诊费用的空结果复制成临床域成功；
- 不打开患者新增绑定、二维码、支付、医保或 HIS 回写 gate；
- 不修改另一会话负责的众阳预约适配器。

收到任一域的正式材料后，只推进该域的 `documentId -> contract -> adapter`，
其余三条线继续按材料状态并行，不因为单域实现而改变其他域的开放状态。
