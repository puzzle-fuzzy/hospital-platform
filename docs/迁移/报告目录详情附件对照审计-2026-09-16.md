# 报告目录、四类详情与附件对照审计（2026-09-16）

## 结论

本次只审计非支付临床只读能力，不涉及支付、医保、退费、收银台、账单支付或支付相关 HIS 回写。
旧服务源码证明报告目录确实读取 LIS、PACS、ECG、PEIS 四类来源，且有真实 LIS 详情和报告解读调用；但
旧服务的 PACS/ECG/PEIS 详情并没有独立 Provider 详情调用，非 LIS 详情依赖客户端完整快照。当前新端已经
建立了更安全的 server-side 读模型、短期引用和附件代理，但这只能算静态代码具备，不能算四类报告业务已经迁移。

当前 P1-08 保持未完成，原因是：

1. 本轮只找到了旧服务源码和本仓库本地 fixture，没有找到当前 release 对应的四类报告 Provider 脱敏请求/响应原文、
   同链服务日志、可核验的生产报告数据或真机报告页面证据。
2. `.env` 和 `.env.prod` 中 `ZHONGYANG_REPORT_DIRECTORY_READY=false`、`ZHONGYANG_REPORT_DETAIL_READY=false`；
   本轮未打开 gate，也未发起真实报告 Provider 请求。
3. PEIS 的完整身份证号、院区号和患者归属授权没有 Provider 合同证明；附件源 URL、重定向、短期授权、content type、
   过期和下载失败也没有真实资源证据。
4. 当前代码对 imaging/ecg/peis 生成通用详情，是受控目录行回查的实现，不是旧端已经证明的独立详情迁移；在合同确认前
   不应把它宣传为“旧详情已迁移”。报告解读、分享和自动复诊仍保持独立关闭态。

因此本轮不删除已有安全代码、不修改旧项目、不改变配置，只补充证据边界和验收条件。

## 3. 四类字段和行为差异

### 3.1 LIS

旧端有目录和真实详情请求。新端目录映射 `testList/reportTypeName/sampleClassName`、`reportTime`、异常标志和
`pdfUrlList`，LIS 详情映射检测项名称、结果、单位、参考范围和有限异常枚举，具体见
`packages/adapters/src/zhongyang-reports.ts:658-716,1004-1087`。

仍需确认：目录与详情的报告号是否稳定一致、详情返回是否回显请求的报告号、目录与详情标题/时间的关联、`pdfUrlList`
是否是可下载资源、资源是否带过期签名，以及 Provider 的成功/合法空/拒绝/超时包络。没有这些事实，不能打开 LIS 详情 gate。

### 3.2 PACS

旧端目录字段至少使用 `stuBodypart`、`modality`、`reportAuditTime`、`reportId`、`finding`、`conclusion` 和图片/PDF 路径；
旧端没有独立详情调用。新 adapter 在 `zhongyang-reports.ts:719-837` 把这些字段投影为通用详情，并将附件源地址只留在服务端。

这不是“PACS 详情已从旧端迁移”的证据。必须先确认报告正文和影像资源是否属于同一授权主体、资源 URL 的 origin/TTL/重定向规则、
图片和 PDF 的 content type，以及患者 A/B 和切换患者时的拒绝证据。

### 3.3 ECG

旧端目录使用 `diagnosis`、`diagnoseTime`、`ecgReportId` 及指标字段，详情页没有独立 Provider 详情实现。新 adapter 在
`zhongyang-reports.ts:839-917` 映射 HR、PR、QRS、QT、QTc、轴、医生、诊断和可选 PDF。

必须确认 `diagnoseTime` 的业务含义、ECG 报告号与 PDF 的关联、指标单位/精度、业务拒绝与合法空结果包络，以及资源授权。当前不应
因为有通用详情 schema 就将 ECG 详情宣称完成。

### 3.4 PEIS

旧端在 `report_query.vue:444-457` 从客户端患者对象取得完整身份证号，并用环境变量或默认 `10389001` 作为 hospitalId；这既是旧端事实，
也是不能直接复制的隐私风险。新端 `service.ts:404-457` 要求服务端身份和患者档案解析成功、身份证与 HIS 患者号一致、院区号来自配置，
adapter 在 `zhongyang-reports.ts:1387-1409` 才组装 POST body。

新端 `mapPeis` 在 `zhongyang-reports.ts:920-985` 可静态投影套餐、时间、总检医生、完成状态和 PDF，但旧端详情没有真实实现。必须先取得
PEIS 正式授权、身份证最小使用范围、院区号责任、返回字段脱敏和错误语义；当前配置未打开，不能把 PEIS 目录或详情当作可用业务。

## 5. P1-08 完成门槛

按以下顺序单独验收，不把报告目录、详情、附件、解读和分享合并成一个“报告完成”状态：

1. 取得 LIS/PACS/ECG/PEIS 正式请求、响应、鉴权、字段、空结果、业务拒绝、超时和分页/时间边界材料，并登记版本/指纹。
2. 使用专用只读账号，以患者 A、患者 B 和无映射患者完成四类目录；每次记录平台 requestId、服务 traceId、Provider requestId，
   并核对患者归属、窗口内时间、窗口外结果、重复号、错误包络和日志脱敏。
3. 目录稳定后单独验收 LIS 详情：引用 owner/patient/TTL、报告号关联、详情字段、检测项上限、空详情、过期和 Provider 拒绝。
4. 若业务方确实需要 PACS/ECG/PEIS 详情，先为每类取得独立详情 contract；不得把目录回查或旧端本地快照当作授权证明。
5. 单独验收附件：允许 origin、未允许 origin、重定向、HTTP 错误、空 body、错误 content type、超 20 MiB、短期过期、患者切换、
   小程序打开失败和服务端低敏失败日志；不得把 Provider URL 或报告原始号放入公共响应、storage 或日志。
6. 完成当前候选 API、DevTools 生成包和微信真机的同版本验证后，才由业务方决定是否在 staging 打开目录 gate；详情和附件仍需独立放行。
7. 报告解读、分享、复诊必须分别取得医疗内容/受众/免责声明/审计、短期分享会话和预约关联 contract；本项不自动实现。

在上述证据齐全前，状态固定为“代码已具备、Provider/公网/真机/生产待实证”，不把 HTTP 200、空列表、页面可进入或本地 fixture 写成业务完成。
