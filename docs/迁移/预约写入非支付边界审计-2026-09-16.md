# 预约写入非支付边界审计（2026-09-16）

## 结论

新端已经具备预约占位、服务端锁号、预约创建、取消和 owner-scoped 详情的代码骨架，但 P1-05 仍不能关闭。当前代码和单元测试只能证明平台边界设计存在，不能证明当前 Provider 接受该请求编排，也不能证明 Provider 超时、重复、占用、取消和最终状态已经闭环。

本审计只检查“非支付预约动作”与支付边界的分离；不打开、不修改、不验收支付、医保、退款或 HIS 支付回写。

## 新端代码核对

### 已实现的服务端边界

- HTTP 路由在 `apps/api/src/modules/appointments/index.ts:100-160,234-255`；默认缺依赖时由 `apps/api/src/app.ts:141-156` 返回 `dependency-not-configured`，不会误调用真实 Provider。
- 小程序只提交 `patientId`、opaque `scheduleId`、`sourceSerialNumber` 或服务端 `holdId`：`apps/miniprogram/src/services/api-client.ts:2786-2831`；确认页 `apps/miniprogram/src/pages/confirm-registration/confirm-registration.ts:161-249` 以同一幂等键重试，并在写入成功后才跳转后续页面。
- `AppointmentWriteService.hold` 在 `apps/api/src/modules/appointments/write-service.ts:445-554` 重新读取有效排班快照、当前患者映射、号源和实际费用后保存 60 秒占位；客户端不能传 Provider `sourceId`、患者号或金额。
- `AppointmentWriteService.register` 在 `:556-760` 做 owner/患者/hold/过期/幂等校验，检查活动预约后才调用 Provider 创建，并把 Provider 预约映射落库；详情从 `:343-443` 的 owner-scoped 本地记录读取。
- `AppointmentWriteService.cancel` 在 `:762-838` 通过服务端保存的 Provider 映射调用取消，并采用条件状态更新；取消前还会检查活动的支付关联，但本审计不修改或验证该支付边界。
- Provider adapter 在 `packages/adapters/src/zhongyang-appointment-writes.ts:448-604,733-842` 重新读取号源、服务端拼装锁号/预约/取消请求，校验响应中的 Provider ID，并不把这些 ID返回小程序。持久化表和 owner+patient 外键见 `packages/persistence/migrations/0024_appointment_writes.sql:1-55`、`0028_appointment_provider_ids.sql:1-4`、`0032_appointment_writes_owner_patient_fk.sql:66-74`。

### 当前明确的缺口

1. **费用合同阻塞预约占位**：`hold` 必经 `getFactRegisterFee`（`write-service.ts:504-518`）；adapter 当前只发送 `hisScheduleId`、`patId`、`requestChannel=3`（`zhongyang-appointment-writes.ts:606-643`），而项目契约记录 Provider 还列出了未确认的 `registerSource`。在不猜该值的前提下，不能声称占位能在当前 Provider 环境完成。
2. **旧端与新端渠道仍需当前 Provider 确认**：旧确认页费用读取实际为 `requestChannel=4`，新写入 adapter 的锁号、费用、预约和取消固定为 `3`（`zhongyang-appointment-writes.ts:18-29`）。Provider 门户文档和旧页面运行值存在差异，必须用当前环境逐端点请求/响应冻结，不能盲改。
3. **锁号生命周期未知**：旧页面声明了锁号 API但未实际调用证据；新端将锁号放入 hold 流程并本地保存 60 秒，但没有当前 Provider 的锁号成功、重复锁定、占用冲突、自动释放、显式释放和过期响应样例。
4. **Provider 未确定状态未闭环**：`create` 或 `cancel` 请求超时/连接断开时，当前代码没有凭 Provider 查询把本地记录推进到确定状态的实证链路；不能把异常当失败后安全重试，也不能把 HTTP 200 直接当作最终业务完成。契约文档要求 `awaiting_confirmation`，但当前候选没有当前 Provider 最终状态查询和补偿证据。
5. **重复预约匹配范围需要业务确认**：`listActive` 只回传 `providerAppointmentId`、患者号、科室名、日期和状态（`zhongyang-appointment-writes.ts:645-731`）；服务层按患者、日期和科室名判断重复（`write-service.ts:630-649`），未按医生、排班或号源精确匹配。现有数据库索引也按 `work_date + department_name` 建立（`0024_appointment_writes.sql:46-48`）。这可能是医院“同日同科室仅一条”的业务规则，也可能误拦同科室不同医生，必须拿到旧系统/院方规则后决定，不能凭猜测放宽或收紧。
6. **测试仍未覆盖完整状态机**：`packages/adapters/src/zhongyang-appointment-writes.test.ts` 已新增 4 项本地 fake-response 测试，覆盖大整数 ID、锁号请求形状、创建字段、取消映射和患者资料解析；连同 `apps/api/src/modules/appointments/write-service.test.ts:1-86` 共 5 pass，adapter typecheck 和新增文件 Biome 检查通过。它们仍未覆盖 Provider 正式 envelope、冲突、TTL/释放、幂等、超时和未确定状态，不能证明写入链路已验收。
7. **运行门禁仍关闭**：`infra/systemd/api.env.example:103-106` 将 `ZHONGYANG_APPOINTMENT_WRITES_READY=false`，配置状态由 `packages/config/src/index.ts:653-669` 独立计算。不能因为代码路由已注册就把写入称为可用。

## P1-05 关闭前的最小验收

只在授权的 staging/受控环境执行，并且单独记录本次候选版本：

1. 取得锁号、实际费用、执行预约、取消和预约查询/详情的当前 Provider 请求/响应，冻结渠道、必填字段、金额单位、锁号 TTL、释放、成功包络和业务失败包络；不把旧页面 payload 或门户条目当作完整运行合同。
2. 用脱敏测试患者完成：可用号源占位→创建预约（Provider `isPay=0` 的非支付创建阶段）→平台详情；再验证同一幂等键、不同 payload 冲突、重复号源、已占用号源、过期 hold、Provider 超时和未知最终状态。不能触发真实支付、医保或退款。
3. 验证取消成功、重复取消、已完成/停诊/不可取消、Provider 超时和活动支付关联的 fail-closed 行为；支付关联只验证既有边界，不修改支付模块。
4. 验证 Provider request ID、平台 trace、数据库 `hold/registration` 记录三方可关联，并确认 Provider 患者号、号源号、预约号、身份证、手机号和原始响应不进入小程序、公共 API 或普通日志。
5. 为服务层和 adapter 补充不依赖真实 Provider 的请求形状/失败状态测试，再用真实受控样例完成公网、开发者工具和真机验证；在此之前保持 `ZHONGYANG_APPOINTMENT_WRITES_READY=false`。
