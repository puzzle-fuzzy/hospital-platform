# 外部入口与通用 WebView 二次验证（2026-09-16）

## 结论

本次重新核对旧端通用 `webview.vue` 的动态 URL/path、ticket 交换和多 audience 承载，以及互联网医院固定 H5 入口；同时验证新端智能导诊、智能客服和互联网医院的边界。旧通用 WebView 实际把客服、导诊、患者绑定/解绑混在同一 URL/ticket 链路，完整 URL 可由路由传入；互联网医院则是另一固定地址。新端已禁止通用 URL、动态 path、旧 ticket 和平台 token 外传，智能导诊使用原生接口，客服/互联网医院分别使用固定 HTTPS 地址，但业务域名、外部主体、会话/回跳和真机证据仍未确认。P1-20 继续保持未完成。

本项只涉及智能客服、智能导诊、互联网医院及通用 WebView 外部边界，不修改旧服务、旧数据库、Provider、线上配置或支付、医保、混合支付、自费支付、退费、收银台及支付相关 HIS 回写代码。

## 1. 旧服务真实行为复核

旧 `/Users/yxswy/Documents/GitHub/hospital/hospital-app/src/pagesB/health/webview.vue:17-27,50-82` 以 `VITE_AI_WEBVIEW` 为基础地址，读取路由 `path` 或完整 `url`，先调用 `POST /system/auth/ticket`，再把 ticket 追加到最终 WebView URL。完整 URL 会 `decodeURIComponent` 后直接使用；同一个页面还依据 URL 内容修改标题。因此智能客服、`outpatient-guide`、患者绑定/解绑共用通用 URL/ticket 交换器，没有独立 audience、origin/path allowlist、短期 opaque 会话或回跳 contract。最终 URL 还会打印日志，见同文件 `:79-82`。

旧互联网医院是独立固定 H5，见 `/Users/yxswy/Documents/GitHub/hospital/hospital-app/src/pages/hospital/hospital.vue:13-29`：

```text

```

旧代码追加时间戳刷新，但当前仓库没有足以证明小程序业务域名配置、外部登录、回跳、退出或最终业务状态的证据。

- `apps/miniprogram/src/pages/smart-customer/smart-customer.ts:1-30` 只使用固定 `https://html.ydrj.top`，切回页面时追加时间戳，不接受路由 URL/path，不请求旧 ticket。

新端已完成的是“危险通用入口不回迁”的代码边界；固定 H5 能否在微信环境打开、外部主体如何登录/返回以及绑定/解绑是否完成，仍未验收。

## 4. 分层验收状态

| 外部能力 | 新端代码状态 | 未完成事实 |
| --- | --- | --- |
| 智能客服 | 固定 HTTPS WebView | 业务域名、主体会话、退出/回跳、真机 |
| 互联网医院 | 固定 HTTPS WebView | 业务域名、外部登录/回跳、失败/退出、真机 |
| 智能导诊 | 原生文字/语音页面 | 模型/知识版本、风险分流和真机验收 |
| 患者绑定/解绑 | 不再由通用 WebView 承载 | 外部主体、授权、短期会话、最终绑定事实 |
| 旧通用 URL/ticket | 未迁移且保持禁用 | 不能恢复动态 URL/path 或旧 ticket |

## 5. 放行前必须取得的 contract

客服、导诊、互联网医院、患者绑定/解绑必须分别确认主体、origin/path allowlist、业务域名、一次性短期 opaque 会话、授权/回跳/退出、失败和撤销、审计和保留规则。必须分别取得 DevTools、真机和生产同版本证据，不能以 URL 能打开、WebView 没报错或 ticket 生成成功代替最终业务完成。

## 6. 处理决定

1. P1-20 保持未完成，四类外部能力不共用通用 WebView contract。
2. 保留新端固定 audience/固定 HTTPS 边界，不恢复任意完整 URL、动态 path、平台 token 或旧 `/system/auth/ticket`。
3. 待各外部主体分别提供 allowlist、会话、回跳、退出和审计材料后，再分别实现和验收。
