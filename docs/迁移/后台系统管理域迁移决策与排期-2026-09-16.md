## 结论

P3-01 的“旧模块盘点、迁移决策和实现排期”已完成；后台系统管理域本身尚未完成迁移。本记录只覆盖旧 `module_system` 的非支付管理能力，明确区分“旧路由存在”“当前有兼容代理”“新 API/管理端已实现”三种状态。医保/支付管理入口不纳入本次实现和验收，也没有修改相关代码。

## 2. 当前新代码对照

### 2.1 API

`apps/api/src/modules/system/index.ts:1-14` 只有 `GET /system/ping`，且注释明确它只证明进程和路由响应，不探测依赖或业务状态。

患者端 `apps/api/src/modules/auth/index.ts:12-48` 只有微信登录和 `/me`，服务的是小程序 owner session，不是旧后台的用户/角色/菜单管理 API，不能用来替代后台 RBAC。

新 API 的日志模块 `apps/api/src/modules/admin/logs.ts:169-218` 已提供受令牌保护的日志查询、内部 ingest 和详情读取；它只返回安全元数据，不是旧 `/system/log` 的完整 CRUD/导出迁移。日志原文读取和受控解析仍按现有日志规范单独处理。

### 2.2 管理端

`apps/admin/src/server.ts:572-624` 当前路由只有健康检查、后台认证兼容、日志列表/详情/原始日志和范围外管理入口；认证实际代理旧 `/system/auth/captcha/get`、`/system/auth/login`、`/system/auth/logout`，见同文件 `:271-295,517-535,584-598`。`apps/admin/src/App.tsx:607-691` 的管理菜单只有两个入口，其中范围外入口不纳入本次迁移。

## 3. 实现排期

排期只作为后续实施顺序，不表示当前代码已经完成：

1. **A0：责任和边界冻结**——确认后台 owner、账号来源、RBAC 角色/权限矩阵、组织/岗位字典责任人、审计/保留和下线策略；同步排除支付/医保管理入口。
2. **A1：后台认证和最小权限**——在不破坏现有兼容代理的前提下，冻结后台 session、刷新、退出、CSRF/来源、密码策略和每个 API 的权限检查；先做只读健康检查。
3. **A2：用户、组织和权限基础**——按 `user → dept/position → role → menu` 依赖顺序设计 domain、persistence、API 和管理端页面；先灰度只读，再启用写入。
4. **A3：字典、参数和公告**——只迁移有当前消费者和责任人的条目；参数敏感值不得进入前端，公告必须有发布、撤回、审计和公开读模型。
5. **A4：日志和运营审计收口**——将旧日志列表/详情/导出与新安全元数据、受控原始 trace 读取逐项对照；补权限、分页、过期和导出审计。
6. **A5：逐模块验收和下线**——每个模块分别补代码、运行环境、Provider（如适用）、管理端、失败/空/拒绝/超时、审计和生产证据；证据齐全后再决定旧路由保留、兼容期或下线。

## 4. 完成标准与当前阻塞

此决策项完成只代表盘点和排期已记录；真正实施必须至少具备：旧接口逐项映射、字段和权限 contract、数据库迁移/回滚、管理端页面、RBAC、审计、空/拒绝/超时测试、候选构建、staging 和生产验收。当前缺少后台业务 owner、生产使用清单、角色/权限矩阵、数据保留策略和可用 staging 账号，因此不提前创建用户/角色/菜单等管理 API，也不把旧系统路由存在写成迁移完成。

本记录没有修改旧服务、数据库、Provider、线上服务或支付/医保/收银台代码。
