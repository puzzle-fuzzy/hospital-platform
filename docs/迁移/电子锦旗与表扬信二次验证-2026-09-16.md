# 电子锦旗与表扬信二次验证（2026-09-16）

## 结论

本次重新对照旧端电子锦旗、表扬信的页面入参、客户端接口和旧 Python 服务校验，并按不迁移旧历史的决定实现新服务功能。旧服务确实可创建和查询两类记录，但客户端可提交患者、就诊、科室和医护快照，服务端只有当前用户 ID 校验；没有就诊归属、审核公开、脱敏、撤回或幂等 contract。新端不接旧 API、不导入旧历史；新提交由服务端校验平台患者/预约归属并进入 `pending_review`，不把旧 `display_type=1` 当审核通过。

### 1.3 旧 Python 校验边界

旧模块在 `/Users/yxswy/Documents/GitHub/hospital/app/api/v1/module_convenience/__init__.py:3-19` 挂载两类路由。schema 接受患者、就诊、科室和医护快照及 `display_type`，只做类型、长度、日期和 0/1 约束，见 `commendatory_letter/schema.py:11-46`、`silk_banner/schema.py:10-44`、公共字段 `base.py:7-28`。

服务层创建时仅校验 `auth.user.id == data.user_id` 后新增，列表也始终先注入当前用户 ID 再查询；表扬信见 `/Users/yxswy/Documents/GitHub/hospital/app/api/v1/module_convenience/commendatory_letter/service.py:30-76`，电子锦旗见 `/Users/yxswy/Documents/GitHub/hospital/app/api/v1/module_convenience/silk_banner/service.py:24-68`。没有服务端就诊 owner 校验、医护目录校验、审核状态、公开读模型、撤回或幂等键。因此相同请求可重复创建，客户端传入的名称/ID也没有被证明互相一致。

### 1.4 “公开列表”与“我的记录”的范围核对

旧端没有发现跨用户公共查询接口。电子锦旗列表页虽然页面标题和入口文案带有“电子锦旗/公开”语义，但调用 `GET /convenience/silk-banner/list` 时只传月份、分页参数，旧服务仍在服务层强制追加 `user_id=auth.user.id`；赠送记录页另外传 `patient_id`，但仍受同一用户过滤。表扬信列表复用同样的当前用户过滤。由此可确认：旧 `/list` 是登录用户自己的记录查询，不是已审核的公共投影；旧 `display_type=1` 仅是创建时由客户端提交的展示标志。

因此新端将“我的记录”实现为 owner-scoped 新服务查询是范围等价的安全迁移；“公开”区域不能直接复用该查询，也不能把旧记录或旧展示标志当作公共数据。公共展示仍需独立的审核状态、脱敏字段、访问受众、撤回和缓存失效 contract，当前保持关闭。
