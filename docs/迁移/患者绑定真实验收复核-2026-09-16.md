# 患者绑定真实验收复核（2026-09-16）

## 结论

P1-01 仍未完成，当前保持绑定能力的安全关闭态。本次复核确认新端已有一条受 owner、幂等和配置门禁约束的服务端链路，但仓库测试只能证明平台代码边界，不能替代当前机构 Provider、旧服务用户授权、真机和生产验收。

本次没有调用众阳、旧服务认证或生产接口，没有改变任何支付、医保、收银台、账单或支付相关 HIS 回写代码与配置。

## 旧服务可迁移事实

- 旧客户端 `hospital-app/src/api/modules/ZY.ts:17-75` 只声明患者档案查询、建档和绑卡调用；它没有提供命令幂等、最终确认、owner 绑定或失败补偿语义。
- 旧页面 `hospital-app/src/pagesB/patient/patientAdd.vue:81-111,199-256` 把查档、建档和绑卡串在一次提交中；查档异常会继续走建档，建档后再绑卡。页面还把证件号、固定卡类型和卡号假设混在一起，不能作为新端字段 contract。
- 旧页面的协议勾选和普通用户资料副作用也没有版本化同意、独立授权或患者档案更新 contract；这些边界继续由 `docs/迁移/患者绑定契约草案.md:104-129` 约束。

因此，本次没有为了“补齐旧页面”直接复制旧接口或把旧端异常分支迁移到新端。

## 新端代码核对

- 小程序 `apps/miniprogram/src/pages/patient-binding/patient-binding.ts:110-163` 只提交展示姓名、手机号、身份证号、同意事实和旧服务登录码；它不提交 `openid`、`unionId`、Provider 患者号或 Provider 地址。
- API `apps/api/src/modules/patients/index.ts:31-96` 从当前会话解析 owner，绑定和同步要求受限的 `idempotency-key`；患者目录 GET 也不接受客户端 owner 参数。
- 服务 `apps/api/src/modules/patients/binding-service.ts:183-323` 先校验身份证、同意和 owner，再通过旧服务授权链核对 unionId，调用 Provider gateway，最后用独立的同步幂等键刷新目录。目录确认失败只重试只读同步，不重复建档或绑卡。
- Provider adapter `packages/adapters/src/zhongyang-patient-binding.ts:10-24,205-295` 将档案查询、建档和绑卡路径分开，并要求 `orgId`、`hospitalId`、当前机构卡类型和真实 `cardNo`；不再把身份证号当作医疗卡号。
- 配置门禁 `packages/config/src/index.ts:568-603,1090-1097,1139` 要求绑定 gate、目录 gate、HTTPS Provider 地址、机构/院区/卡类型及旧服务认证地址同时满足；缺少任何一项时不得误开写入。
