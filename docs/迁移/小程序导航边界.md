# 小程序入口与共享底栏门禁

## 目的

迁移过程中页面数量会持续增加。页面“已经登记”不代表业务已经完成，但至少
不能出现注册页面缺少源文件、固定入口指向 404，或把四个主 Tab 当普通页面压入
页面栈的问题。

本项目最终使用微信原生 `tabBar`，四个主入口固定为：

- 医疗服务：`pages/index/index`
- 就诊：`pages/consult/consult`
- 互联网医院：`pages/hospital/hospital`
- 我的：`pages/my/my`

主 Tab 之间必须使用 `wx.switchTab`。普通业务页才使用 `wx.navigateTo`；不能用
`navigateTo`、`redirectTo` 或 `reLaunch` 打开主 Tab，否则会让底栏出现重复实例、
选中态丢失或页面生命周期闪动。

## 原生导航栏标题唯一来源

每个页面的 `navigationBarTitleText` 是该页面唯一的页面标题。微信原生导航栏已经
展示了这个标题，内容区不得再次绘制同名的页面标题、Hero 标题或页面头标题。
例如 `电子导诊单` 页面只能在原生导航栏显示“电子导诊单”，内容区不能再放一个
同名的 `consult-intro-title`。

这条规范固定适用于所有小程序页面：

- 页面 JSON 负责页面标题；页面 WXML 只负责业务内容、说明、患者信息、卡片标题、
  记录标题、空状态和操作标签。
- 页面级标题包括 Hero/Intro/Header 中概括整个页面的同名文字；这类文字必须删除，
  不能通过换 class、加粗或换一层容器继续保留。
- 与页面标题同名的业务动作标签可以保留，例如“意见反馈”页中的“意见反馈”功能卡片；
  它是可点击动作名称，不是页面头标题，必须保持在卡片内部并有明确交互语义。
- 医院名称、当前就诊人、业务分组、记录标题和错误/空状态说明不是页面标题，可以正常展示；
  但不能为了视觉排版把页面标题再复制成这些字段。
- 新增或修改页面时，先检查对应的 `navigationBarTitleText`，再检查 WXML 的首屏
  Hero/Intro/Header；禁止只看截图而忽略原生导航栏已经提供的标题。

当前已按此规则清理：电子导诊单、电子锦旗、表扬信、我的医生、添加就诊人。验收测试
会扫描页面 JSON 与 WXML 的同名文字；如果新增同名内容，必须明确证明它是业务动作标签并登记
例外，否则测试直接阻断。

## 就诊人与院区共享上下文

门诊病历顶部的“就诊人 + 当前院区”两行效果是患者范围页面的统一组件，不允许各页面
继续复制一套选择器 markup、颜色、间距或加载文案。统一组件为
`components/patient-hospital-context/patient-hospital-context`，当前复用页面包括：

- 电子导诊单、门诊缴费、报告查询、我的问诊、我的挂号；
- 住院信息查询、住院缴费、入院预问诊、出院随访、风险评估；
- 底部 Tab 的就诊页，以及作为视觉基准的门诊病历页。

组件的展示数据由 `services/patient-hospital-context.ts` 维护在
`App.globalData.__hospitalPatientHospitalContext`。首次进入当前小程序会话时只执行一轮
当前用户与当前就诊人读取；页面切换时组件只订阅已有快照，并通过 single-flight 复用在途
请求，不因新页面实例再次请求 `/me` 或 `/patients`。患者选择事件会同步刷新所有已打开的
组件实例，真实账号切换会清理旧快照后重新读取；自动 token 恢复的中间态不清空界面。

视觉上组件必须是患者范围页面滚动容器的第一个子节点，直接贴住内容顶部并占满左右宽度；
页面自身的 `padding` 只能作用于后续业务内容，不能包住或推开这两行“就诊人/当前院区”区域。

这项复用只统一“当前作用域是谁、院区是什么”的展示和切换入口，不代表各页面的病历、报告、
费用、预约或住院业务数据已经统一缓存。各业务列表仍必须按自己的 contract、患者 opaque
标识和会话代际校验读取；共享快照也只存在当前小程序进程，退出/重启后必须重新验证，不能
作为持久化医疗数据。

## 不可变跳转契约：智能陪诊固定进入“就诊”Tab

首页右侧的“智能陪诊”快捷入口是一个 action-only 入口，代码动作名固定为
`companion`。它的目标已经明确且不可重新解释：用户点击后必须切换到底部原生
Tab 的“就诊”页面，固定路径为 `/pages/consult/consult`。

这条规则是页面跳转契约，不随陪诊服务是否完成迁移而变化：

- 生产代码必须调用 `switchToPrimaryTab(SMART_COMPANION_PRIMARY_TAB)`，底层使用
  `wx.switchTab`；不得使用 `wx.navigateTo`、`redirectTo`、`reLaunch` 或自行拼接路径。
- `SMART_COMPANION_PRIMARY_TAB` 必须保持为固定字面量 `/pages/consult/consult`，并且
  必须继续与 `app.json` 中文字为“就诊”的 Tab 对应。
- 禁止把智能陪诊改到 `/pages/feature-status/feature-status?feature=companion`、
  `/pages/smart-guide/smart-guide`、`/pages/consultation/consultation`，也禁止新增
  `smart-companion` 独立页面来替代该入口。
- `/pages/smart-guide/smart-guide` 是“智能导诊”的独立入口；
  `/pages/consultation/consultation` 是“我的问诊”次级页面；两者都不是智能陪诊的目标。
- 陪诊实时消息、预约历史、叫号队列等外部能力仍需独立 contract，但这些能力未完成时，
  也不能把固定导航改成状态页。后续若要开放真实陪诊能力，必须先更新本节、常量、入口测试和
  页面 contract，不能只修改首页分支。

因此，“智能陪诊 -> 底部就诊 Tab”属于冻结的硬规则；任何导航修改都必须同时检查
`apps/miniprogram/src/pages/index/index.ts`、`patient-navigation.ts`、对应测试和本文档。

## 机器门禁

```powershell
pnpm miniprogram:navigation:audit
```

该审计只读取 `apps/miniprogram/src/app.json`、页面源文件、Tab 图标和 TypeScript
中的字面量导航调用，检查：

1. `app.json` 注册页面是否都有 `.json`、`.ts`、`.wxml` 和 `.wxss`；
2. 四个 Tab 是否唯一、已注册、使用原生 `tabBar` 且图标真实存在；
3. 固定字面量 URL 是否指向已注册页面；
4. 主 Tab 是否只由 `switchTab` 打开，普通页面是否误用 `switchTab`。

## 页面滚动边界

所有已注册页面都必须在页面 JSON 中设置 `disableScroll: true`，并让根节点使用显式的
`scroll-view`。四个主 Tab 使用 `tab-page-scroll`，其它业务页使用统一的
`secondary-page-scroll`；级联科室、日期选择和弹层列表可以在内部保留独立的固定高度滚动。

这样微信页面层不会再与业务内容层竞争滚动位置，底部原生 TabBar 也不会因为页面整体滚动
而漂移或闪动。`tools/miniprogram-navigation-audit.mjs` 和小程序验收测试会同时检查这条
规则，新增页面若退回页面级滚动会直接阻断检查。

动态 URL 由具体导航服务的单元测试负责；本门禁不把 `feature-status` 的业务状态
误判为已完成。Provider、支付、临床审核和患者绑定仍由各自 contract 门禁控制。

统一状态页的 `feature` query 只接受 `feature-navigation.ts` 中的固定 key；缺失、
非法或已过期的 key 会进入“服务入口不可用”专用状态，不会默认显示门诊病历或其它
具体业务。这样入口参数错误不会污染业务统计、日志分类和用户反馈，也不会触发任何
Provider、旧缓存或支付调用。

## 与全量迁移的关系

这是一层入口覆盖护栏，不是业务完成证明。旧端 64 个页面仍以
`legacy-page-catalog.ts` 为逐页事实源；没有正式 contract 的页面继续落到统一状态
页。只有 contract、adapter、领域不变量、日志、自动化测试和真实链路证据齐全时，
才可以把状态页替换为真实业务页面。
