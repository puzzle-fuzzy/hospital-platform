# 支付最终性微调记录（2026-09-02）

## 结论

截至本轮校对，新项目仍没有可以对用户宣称的“支付成功”闭环。

最近日志文本中的几个“成功”只说明请求或阶段性动作成功：

| 证据 | 实际含义 | 是否最终支付成功 |
| --- | --- | --- |
| `apply-pay-settle` 外层 `success=true/code=0000`，`settleStatus=1` | 云健康结算单已创建，仍等待支付 | 否 |
| `pre-order` 外层成功，`payRecord.status=1` | 支付流水已发起 | 否 |
| 6201 返回 `payOrdId/payToken` | 医保费用上传并取得后续凭证 | 否 |
| 6202 外层成功，`ordStas=1` | 医保订单处于预结算/中间阶段 | 否 |
| 6201 与 6202 的 `payOrdId` 关联一致 | 两次医保调用属于同一订单 | 否 |
| 6301/6302、云健康 `insur/settle`、HIS `isSettle=1` | 本次文本未出现 | 缺少最终成功证据 |

本轮没有启动旧项目，也没有调用真实医保、微信支付或 HIS。

## 本轮已微调

1. `packages/domain/src/ports.ts` 为医保结算证据增加 `source`、`providerStatus`、`finality`、`authoritative`。外部 `success` 不再单独构成成功证据。
2. `packages/domain/src/payment-order.ts` 新增医保证据对账方法：
   - 金额不一致进入 `awaiting_confirmation`；
   - 6202/6301 的处理中或后置候选状态只能进入待确认；
   - `paid` 证据必须来自 Yunhealth/HIS；
   - 最多推进到 `insurance_settled` 或 `cash_pending`，不能直接推进到 `completed`。
3. `packages/adapters/src/legacy-fsi-contract.ts` 新增 `ordStas` 安全分类：0/1/2 为 `processing`，3/4/5/6 为 `settlement_candidate`，7–13 为 `cancelled`，14–16 为 `failed`，其他为 `unknown`。`settlement_candidate` 是刻意设计的非终态名称。
4. `packages/adapters/src/legacy-fsi-gateway.ts` 在 6202/6301 返回中带出上述分类，供后续编排决定继续查单还是进入后置接口。
5. `apps/worker/src/medical-insurance-reconciliation-worker.ts` 新增医保查单补偿骨架：数据库任务 claim、固定查单幂等键、指数退避、版本栅栏和 12 次人工复核上限。医保任务表和短期凭证上下文表现已补齐；真实订单编排、Provider gateway 组合和生产 runtime gate 仍未接入，因此它没有注册到生产 `runtime`。

## 仍需完成

- 医保订单独立持久化：owner/order 归属、6201 `payOrdId`、`payToken` hash、独立密钥保护的短期凭证上下文、6202/6301 状态金额快照、6302 去重键和查单任务调度已落地；仍需接入真实订单编排。
- 6302 公网 HTTPS 回调的验签、幂等和重放；它只能作为医保后置编排输入，不能替代云健康/HIS 最终确认。
- 云健康 `2.27.2.32` 的 `insur=SUCCESS`、`settle=SUCCESS` 以及 `2.6.65.5.isSettle=1` 的正式 Node adapter/订单编排。
- 现金支付完成后的微信通知/查单、HIS 回写顺序、退款/撤销以及人工复核处理路径。
- 医保 API 和原生小程序页面的公共 contract；在上述证据链完成前，支付入口必须保持关闭。
- 正式 SM2/SM4 golden vector、部署密钥挂载、真实环境验收和真机证据。
