# 旧支付存量切换与对账策略（2026-08-31）

> 本文完成支付存量的“策略设计”项，不是支付迁移、结算或退款执行记录。当前微信支付、医保、退款和 HIS 回写继续关闭；本文不读取线上订单、不调用 Provider、不修改旧库或新库。

## 1. 已核实的事实

旧服务至少有 `mbs_medical_orders` 和 `mbs_payment_events` 两类支付事实：订单表包含机构/医院订单号、微信及医保订单号、医保 token 摘要、收费批次、就诊编号、元金额、分金额、微信交易状态、退款字段和插件回写字段；事件表包含外部事件 ID、事件类型、payload 摘要、处理标记和错误信息。

新服务把平台订单、预支付尝试、微信通知和 outbox 拆成不同事实：

- `hp_payment_orders` 需要新平台 owner、平台患者、幂等键、整数分金额、版本和明确的内部状态；
- `hp_payment_prepay_attempts` 需要关联新订单、Provider、查单状态、claim lease 和受控密文；
- `hp_wechat_payment_notifications` 只接受经过微信验签/解密的白名单通知，并按通知 ID 和交易 ID 去重；
- `hp_outbox_events` 只承载新平台事务产生的可恢复事件，不能把旧事件历史当作待执行任务重新投递。

因此，旧订单“有一行”不等于新平台能够证明 owner、患者、金额、支付最终状态或回写事实；字段同名也不能作为迁移依据。

## 2. 默认策略：不自动导入支付存量

在账户/患者映射、订单对账和 Provider 最终事实未完成前，发布单使用：

```text
paymentStockImport = blocked
legacyPaymentRead = unchanged
newPaymentWrite = fail-closed
legacyWriteBack = unchanged
```

旧服务继续按原有策略运行；新端不读取旧支付表，不把旧订单数量渲染为新订单，不把旧页面的 `isPay`、交易状态或 HTTP 200 直接转换成 `completed`。新平台只处理发布后由新 contract 创建的订单。

## 3. 存量状态分类与处置

实际分类必须基于旧订单、事件、Provider 查单和 HIS/云健康最终事实的交叉对账。不能只按 `state` 字符串猜测。

| 存量类别 | 必须同时核对 | 默认处置 |
| --- | --- | --- |
| 待支付/已创建预支付 | 新旧订单号、预支付是否真实存在、微信/医保查单、金额和 owner/患者 | 冻结在旧系统或人工队列；不创建新订单、不再次发起预支付 |
| 已支付待 HIS 回写 | 已验签通知、Provider 查单、HIS/云健康回写结果、金额守恒 | 保留在旧系统并人工对账；没有完整最终事实不得导入为完成 |
| 已完成 | 支付通知、结算结果、HIS 完成结果、退款窗口 | 只可在独立历史只读 contract 批准后展示；不重建为可操作的新订单 |
| 退款中/部分退款/已退款 | 退款申请、微信/医保退款通知、分项金额、最终退款结果 | 进入人工复核；不自动生成新退款任务，不重复调用退款接口 |
| 失败/取消/超时/未知 | 最后事件、查单结果、重试记录和是否存在资金扣款 | 以最终 Provider 事实为准；未知和证据不完整的统一隔离 |
| 重复或互相矛盾 | 各 Provider 单号唯一性、金额、时间线和事件摘要 | `quarantined`，禁止自动合并或覆盖 |

“旧记录可查询”与“新端可操作”是两件事。即使未来批准历史展示，也只能建立独立的脱敏历史视图；历史视图不能提供支付、取消、退款、重试或 HIS 回写按钮。

## 4. 不允许的直接映射

以下做法一律禁止：

- 用旧整数订单 ID 直接生成新 `order_id`，或通过订单号/时间猜测新 owner 和 `patient_id`；
- 用旧 `fee_sum_amt`、`own_pay_amt` 等元字段未经精确换算和核对写入新分金额；
- 用 `isPay`、`wechat_trade_state`、`remote_ord_stas` 或字符串“成功”直接推进新状态机；
- 用旧 payload hash 伪造新微信通知，或把旧 `mbs_payment_events` 重新塞进新 outbox；
- 把旧 `pay_token`、`prepay_id`、医保授权码、身份证、卡号或 Provider 原始响应复制到新库、日志或小程序；
- 在支付未知状态时自动关单、冲正、退款或重新发起结算；
- 因为同一用户“看起来相同”就把旧支付订单跨患者、跨机构或跨 Provider 合并。

## 5. 受控对账流程

若业务负责人最终决定保留支付历史，必须单独开受控变更窗口：

1. 导出旧表 schema、索引、字符集、订单/事件计数和时间范围；原文只进入访问受限的加密 staging。
2. 先完成账户 owner 与患者 `patientId` 映射，生成不含原始身份和订单号的脱敏摘要报告；没有唯一归属的订单不能继续。
3. 为每条候选订单整理支付方式、原始金额单位、医保/现金分项、Provider 单号、通知时间线、查单结果、HIS 回写结果和退款事实。
4. 校验金额守恒、唯一键、时间顺序、通知去重、重复订单、孤儿事件和不一致状态；所有异常进入 `quarantined`。
5. 由支付、财务、医保、HIS 和数据负责人分别批准可保留类别；工程工具不能代替业务确认。
6. 优先只生成历史归档摘要。只有正式 contract 明确允许的订单，才设计单独的迁移表/映射；不把历史订单伪装成新订单以绕过现有状态机。
7. 在 staging 用脱敏快照完成幂等重跑、查单模拟、回滚和审计核对；验证通过后才讨论生产执行。

对账报告至少保留：批次指纹、源/目标数量、按状态计数、金额总额摘要、唯一性结果、孤儿数、冲突数、人工决定、操作者、时间和回滚点。报告不得包含完整订单号、患者身份、支付 token 或回调正文。

## 6. 回滚与旧新共存

- 迁移失败或 Provider 事实不确定时，停止本批次并保持新支付 gate 关闭；不自动重试高风险写入。
- 回滚只撤销本批次的 staging/归档映射或将其置为不可见，不删除旧订单、不修改旧服务、不反向写旧表。
- 已经产生新平台支付事实的记录必须按新订单状态机和人工复核规则处理，不能用回滚脚本直接改成成功、失败或退款完成。
- 旧 Python 服务、旧支付/医保链路和新 Elysia API 在共存期分别使用各自的订单事实；禁止同一笔旧订单被两套服务同时驱动 Provider。

## 7. 当前结论

支付存量策略已经明确为“先冻结、对账、人工审批，默认不导入”，但没有任何真实订单迁移或支付业务放行。后续必须在支付最后批次中补齐真实 Provider contract、金额/状态 golden samples、通知验签、查单、退款、HIS 回写、Worker 补偿和真实环境证据；在此之前，现有支付 gate 保持 fail-closed 是正确状态。
