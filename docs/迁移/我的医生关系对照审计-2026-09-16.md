## 1. 旧服务真实行为

### 1.1 路由、输入和存储

旧服务在 `app/api/v1/module_convenience/__init__.py:5-19` 引入并挂载 `MyDoctorRouter`；路由本身在 `app/api/v1/module_convenience/my_doctor/controller.py:17-21` 使用前缀 `/my-doctor`，最终由父路由形成：

- `GET /convenience/my-doctor/list`，控制器 `controller.py:23-37` 接收分页参数和查询条件；
- `POST /convenience/my-doctor/create`，控制器 `controller.py:40-47` 接收完整的创建模型；
- `GET /convenience/my-doctor/delete?doctor_id=...`，控制器 `controller.py:50-63` 用 GET 执行取消关注。

旧创建 schema `app/api/v1/module_convenience/my_doctor/schema.py:9-22` 要求 `user_id`、数值 `doctor_id`、医生姓名、职称 ID/名称、擅长、科室位置和科室名称，头像可选。旧表 `model.py:9-23` 将这些值作为 `my_doctor` 行保存；这是一份由客户端提交的医生资料快照，不是当前医生目录的版本化事实。

旧 service `app/api/v1/module_convenience/my_doctor/service.py:16-26` 会检查 `auth.user.id == data.user_id`、按 `(user_id, doctor_id)` 查重，然后直接保存客户端提交的整份资料。列表 service `:29-64` 强制加入当前用户过滤，同时支持 `doctor_id`、`department_name` 查询以及 `page_no/page_size` 分页。取消 service `:67-88` 按当前用户和医生 ID 删除；不存在时返回异常。CRUD 的先查后删行为见 `app/api/v1/module_convenience/my_doctor/crud.py:27-49`。

### 1.2 小程序实际使用方式

旧列表页 `hospital-app/src/pagesB/patient/doctor.vue:54-131` 调用 `getMyDoctorListApi`，把关系快照映射成名片；`doctor.vue:94-105` 在缺少医生 ID 时还使用数组下标作为 ID，随后 `:123-127` 拼接旧医生详情路径。该 fallback 不能成为跨请求稳定关系标识。

旧客户端接口定义在 `hospital-app/src/api/modules/user.ts:38-110`：创建请求提交 `user_id`、`doctor_id`、姓名、职称、擅长、位置和科室；列表支持分页参数；取消仍是 GET 删除。旧医生详情 `hospital-app/src/pagesB/hospital/doctor_card.vue:278-306` 查询当前医生未来排班，实际传入 `requestChannel: "4"`、`scheduleType: 1`、医生 ID 和日期窗口。关注前会在 `:364-382` 读取旧关系列表，关注动作在 `:384-449` 再次提交用户 ID 和完整客户端快照；取消在 `:405-423` 传用户 ID 和医生 ID 调用 GET 删除。

因此旧端可被源码证明的事实是“用户级关系 + 客户端快照 + 当前排班详情 + 4 渠道后续请求”，不能从页面文案或 `doctor_id` 字段推导医生当前在职、科室有效、头像可用或关系仍然有效。

## 3. 尚未闭环的迁移差异和决策

### 3.1 旧 21 条关系不能自动导入

现有受控库存审计 `docs/迁移/旧便民来源审计-2026-08-26.md:60-80` 记录旧 `my_doctor` 共 21 行，但旧 `system_users.openid` 到新 owner 的桥接成功数为 0；`docs/迁移/旧便民与健康历史处置-2026-08-31.md:9,28` 也明确旧快照不能证明当前医生有效性，当前策略是不导入新关系表。

本轮没有新增数据库读取、没有改写旧库，也没有生成导入脚本。当前正确的静态决策是：**不把 21 条旧快照关系伪装成新用户关系，不把状态页文案或旧记录数量当作迁移成功**。如果业务要求保留历史，必须另立受控流程，至少提供旧账户到新 owner 的唯一映射、冲突/删除/回滚规则，以及当前医生目录的逐条复核；在这些材料到达前，P1-07 不得勾选。

### 3.2 当前关系快照仍有失效/新鲜度差异

旧列表本来就展示 `my_doctor` 快照，旧详情则重新请求未来排班；新端关注时从当前排班确认字段，但 `list` 和 `get` 只读取 `hp_my_doctors`（`service.ts:111-164`），不会在每次读取时重新校验医生目录。详情页在没有当前排班时仍优先使用已关注快照（`my-doctor-detail.ts:163-173`），这可能展示旧姓名/科室而同时显示“未来七天暂无排班”。

这不是可以凭空修掉的字段问题，需要业务/Provider 先决定：目录失效是否隐藏关系、保留历史但标记失效，还是每次列表刷新目录；医生离职、科室变化、头像撤回和目录版本如何落库；医护侧是否可以看到用户关系。材料未确认前保持当前安全行为，不将快照升级为权威医生资料。

### 3.3 Provider 排班渠道与来源尚未证实

旧医生详情的实际源码传 `requestChannel="4"`（`hospital-app/src/pagesB/hospital/doctor_card.vue:285-295`）。新端关注调用 `AppointmentService.listSchedules`（`apps/api/src/modules/my-doctors/service.ts:184-192`），而预约 adapter 的 `/schedulings` 请求在 `packages/adapters/src/zhongyang-appointments.ts:1184-1219` 固定 `requestChannel="3"`；项目 Provider 材料在 `docs/Provider契约-v1.md:64-67` 也按门诊微信 3 描述，但这仍不能替代当前候选版本的逐请求证据。

此外，旧端有独立的 `scheduling-doctors` 调用，新端是从 `/schedulings` 聚合医生卡片；需核对当前响应是否稳定包含医生 ID、姓名、职称、简介、擅长、照片和科室位置，及空排班时能否仍查询有效医生。没有 Provider 原始请求/响应和院方确认前，不改成 4，也不把 3 宣称为已验收。

### 3.4 查询能力和数量边界未完成对照

旧端列表支持 `doctor_id`、`department_name` 和分页参数（旧 `param.py:7-16`、旧 `service.py:29-64`）；当前新端公共列表没有查询参数，service 返回 owner 下全部关系（`apps/api/src/modules/my-doctors/index.ts:34-49`、`service.ts:111-141`），小程序也没有筛选/分页控件。当前已知旧库存只有 21 行，但这不能替代长期数量上限、游标/分页或超量行为的产品合同。

本轮不擅自加入任意 `limit` 或改变 API contract；需要业务确认是否仍需旧筛选/分页。如果保留该能力，应重新定义 opaque ID、排序稳定性、最大页大小和超量 fail-closed 测试，不能简单把旧 query 字段透传给 Provider。

## 4. 需要补齐的真实验收证据

必须使用同一候选版本、同一测试机构，并把支付范围排除在外：

1. **Provider/公开链路**：在不写入预约、不产生费用的前提下，收集一次关注前的 `/schedulings` 请求/响应，记录实际渠道、日期是否包含、医生字段、空结果、医生不存在、目录超时/拒绝和 Provider request ID；若旧 `scheduling-doctors` 仍是必需来源，也必须单独核对。
2. **owner 隔离**：测试账号 A 关注医生，账号 B 列表和详情不能看到；A 重复关注不重复建行，A 取消后重试仍得到 `followed=false`；不能把 HTTP 200 或空数组当作关系成功。
3. **失效/变化**：让 Provider 返回医生缺失、停诊、科室/姓名变化、头像不在 allowlist 等受控样例，确认展示与关系状态按已批准规则处理；未有规则时保持拒绝/关闭。
4. **运行包**：以当前 `dist` 和 development 包核对页面源码来源、`/my/doctors*` requestId、服务端 traceId 和 Provider requestId；验证会话换号后旧请求结果不会回写。
5. **真机与生产**：开发者工具和真机分别完成“我的医生 → 名片 → 未来七天排班 → 有余号时段入口”的成功、空、拒绝、超时和重试；生产只读观察需有低敏日志和回滚结论，不能以状态页、单元测试或历史截图替代。
6. **存量决定**：业务负责人明确 21 条旧关系“不导入/只存档/受控导入”之一；若选择导入，先完成脱敏 staging、数量/孤儿/重复校验、owner 映射和回滚演练，再另立变更。
