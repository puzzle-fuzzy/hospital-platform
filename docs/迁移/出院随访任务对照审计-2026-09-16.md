# 出院随访任务对照审计（2026-09-16）

## 结论

旧服务确实存在出院随访的患者端表单与本地 CRUD 链路，但它把同一 `user_id + pat_id` 下的记录当成唯一记录并覆盖更新；同时，旧数据模型没有出院事件、随访任务、表单版本、提交幂等、撤回或医护读取授权。旧端还把多个专科/手术随访表固定在页面中，不能据此推断新端可以安全复制一个通用表单。

新端已经迁移八类表单目录、详情表单的输入/选项交互和本地校验，但出院事件、任务版本、答案撤回和医护读取仍是前置 contract。当前没有足够的事件来源、任务生成规则、题表版本和临床读权限证据，因此本项保持关闭，不导入旧答案、不按 `user_id + pat_id` 复用覆盖语义，也不把旧表单直接开放提交。

本审计只覆盖出院随访业务迁移，不触碰支付、医保、收银台、退费、账单支付或支付相关 HIS 回写。

### 1.2 旧 API 和服务端 CRUD

旧客户端声明：

- `GET /convenience/discharge-follow-up/list`，支持 `page_no`、`page_size`、`order_by`、`pat_id`、`table_name`，列表项含 `id`、`user_id`、`pat_id`、`table_name`、时间字段和动态字段，见 `/Users/yxswy/Documents/GitHub/hospital/hospital-app/src/api/modules/health.ts:318-352`；
- `POST /convenience/discharge-follow-up/create`，请求含 `user_id`、`pat_id`、`table_name`、序列化后的 `content`，见同文件 `:354-387`。

旧 Python 服务实际挂载列表和创建路由，见 `/Users/yxswy/Documents/GitHub/hospital/app/api/v1/module_convenience/discharge_follow_up/controller.py:18-49`。其创建逻辑为：

- 要求当前认证用户的 ID 等于请求中的 `data.user_id`；
- 只按 `user_id + pat_id` 查询已有记录；
- 找到记录就按 ID 更新，否则插入新记录；
- 列表强制以当前认证用户过滤，可再按 `pat_id`、`table_name` 过滤。

以上行为见 `/Users/yxswy/Documents/GitHub/hospital/app/api/v1/module_convenience/discharge_follow_up/service.py:12-67`。模型只有 `user_id`、`pat_id`、`table_name`、`content`，见 `/Users/yxswy/Documents/GitHub/hospital/app/api/v1/module_convenience/discharge_follow_up/model.py:9-18`；schema 允许 `content` 为数组或字符串，写入时转 JSON、读取时尝试解析，见 `/Users/yxswy/Documents/GitHub/hospital/app/api/v1/module_convenience/discharge_follow_up/schema.py:10-54`。

因此，旧服务的“最新一条”并不是按出院或随访任务确定的事实，而是按患者和表名的简化覆盖结果。多次出院、同一患者重复手术、不同随访批次或同一表单的二次回访，都可能互相覆盖。

### 1.3 旧详情页回填和提交

旧详情页按 `tableName` 动态选择不同表单组件，模板和组件分支见 `/Users/yxswy/Documents/GitHub/hospital/hospital-app/src/pagesB/health/discharge_followup_detail.vue:20-95`。提交时从路由优先取 `patId`，否则回退缓存；校验用户和患者后，将表单内容序列化为 JSON，带上 `user_id`、`pat_id`、`table_name` 调用创建接口，见同文件 `:140-199`。

详情加载时按 `pat_id + table_name` 查询；有历史记录就取 `items[0]` 解析回填，没有就显示提交入口。源码明确写着“只取当前患者、当前表名称下最新的一条随访记录用于回显”，见同文件 `:201-270`。这里没有任务 ID、出院事件 ID、表单版本、提交序号、撤回状态或防重放字段。

## 3. 放行前必须冻结的 contract

至少需要业务、临床和数据责任人共同确认：

1. 出院事件的权威来源、事件状态、时间窗口及患者 owner 映射；
2. 一次出院如何生成一个或多个随访任务，八套旧表单分别适用于哪些手术/科室/人群；
3. 任务唯一键、表单 schema/version、必填项、选项、文本长度和敏感字段规则；
4. 答案修改、替换、撤回、过期、重复提交和超时后重试的幂等语义；
5. 患者本人/代填人的授权和会话切换规则，以及医护端按任务读取的最小范围；
6. 临床审核、审计字段、数据保留/删除周期和错误信息脱敏；
7. 真实空、拒绝、超时、字段异常和重复提交样例，以及 staging、DevTools、真机和生产同链验收证据。

不能用旧端的“已完成预约”筛选直接代替出院事件，也不能把 `user_id`、`pat_id` 或旧 `table_name` 当成新端的授权凭证和任务唯一键。
