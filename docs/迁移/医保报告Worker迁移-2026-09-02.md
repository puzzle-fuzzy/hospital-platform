# 医保支付、报告与 Worker 迁移记录（2026-09-02）

本文记录本轮从旧项目向新 Node 服务端和原生小程序迁移的实际落点。旧项目
`/Users/yxswy/Documents/GitHub/hospital` 只作为源码和配置材料读取，未启动旧服务、
旧小程序、旧数据库、Redis 或医保/微信 Provider。

## 结论先行

本轮完成的是“可验证的服务端边界和迁移骨架”，不是正式医保支付已开通：

- 医保 FSI 已增加固定路由、严格 envelope、订单号和金额校验的受控 adapter；真实 SM2/SM4 实现、正式凭据、Provider golden vector、生产订单表和真实验收仍未接入。
- 报告目录继续由新 API 的只读 service 负责；LIS/PACS/ECG 的目录边界已有代码，PEIS、PACS/ECG 详情、附件授权和报告解读仍保持关闭。
- 新 Worker 继续只允许在持久化 schema、支付配置和真实回调条件同时满足后启动。当前没有证据表明旧项目存在一个独立的“报告 Worker”；报告查询是用户请求驱动的只读 API，不应为了页面迁移虚构一个后台任务。
- 微信证书目录 `/Users/yxswy/Documents/GitHub/hospital/env/wechat` 已完成只读核验，但证书和私钥没有复制到仓库、没有写入日志、没有上传服务器，也没有因此打开微信支付。

## 1. 医保 FSI 迁移关系

旧项目移动支付中心实际使用以下专用目标路径：

| infno | 旧目标 path | 新项目落点 | 当前状态 |
| --- | --- | --- | --- |
| 6201 | `/org/local/api/hos/uldFeeInfo` | `packages/adapters/src/legacy-fsi-gateway.ts` | 受控传输和费用明细守恒已实现；未接真实 crypto/provider |
| 6202 | `/org/local/api/hos/pay_order` | 同上 | 输入凭证校验、金额守恒、订单号回显校验已实现；未接订单编排/持久化 |
| 6301 | `/org/local/api/hos/query_order_info` | 同上 | 保留 0/1/2 等处理中状态；只有 3/4/5/6 才要求完整金额；未进入 Worker |
| 6203 | `/org/local/api/hos/refund_Order` | 同上 | ALL/CASH/HI 退款守恒和原结算上限校验已实现；未接退款状态机 |
| 6401 | `/org/local/api/hos/revoke_order` | 同上 | 只接受明确 `success=true`；未接撤销补偿 |

新 adapter 的固定约束：

1. `infno` 只能来自代码中的固定路由表，不能由 HTTP 参数决定 path 或 `base_url`；
2. 业务数据必须先由注入的 `LegacyFsiCryptoGateway` 封装，不能明文回退；
3. 返回内容必须验签、解密并通过业务字段校验后才能映射；
4. 6201 返回的 `payToken` 只作为 adapter 内部结果，禁止进日志、outbox 或小程序；
5. 6301 的处理中状态不填充虚假金额，只能由上层进入等待确认/继续查单；
6. relay Bearer 必须由新环境变量 `MBS_FORWARD_AUTHORIZATION_TOKEN` 注入，不迁移旧代码里的硬编码 `main-token`。

配置 gate 为 `MEDICAL_INSURANCE_READY=false`，并要求 `MBS_ENCRYPT_ENABLE=true`、
`MBS_SM2_VERIFY_STRICT=true`、HTTPS relay/target 和完整密钥材料。字段完整只代表配置
形状正确，不代表医保平台已经授权或可以真实结算。

## 2. 报告迁移关系

旧报告页合并了 LIS、PACS、ECG 和体检 PEIS 四种来源。新项目拆为服务端受控目录：

| 旧来源 | 新 API/adapter | 可迁移范围 | 暂不迁移 |
| --- | --- | --- | --- |
| LIS | `/api/v1/reports`、LIS adapter | 目录摘要；LIS 详情短期引用骨架 | 未确认字段、附件长期 URL |
| PACS | `/api/v1/reports`、PACS adapter | 目录摘要 | 详情、影像资源、下载凭证 |
| ECG | `/api/v1/reports`、ECG adapter | 目录摘要 | 详情、原始波形、下载凭证 |
| PEIS | 无 | 暂不接入 | 身份证最小使用、患者归属和字段白名单合同缺失 |
| AI 报告解读 | 无 | 暂不接入 | 模型/知识版本、医疗免责声明、审核和审计缺失 |

报告查询只接受新平台 `patientId` 和有限日期窗口；Provider 患者号及报告号只在服务端
调用帧内使用。目录未指定来源时，三路报告必须整体成功，不把某一路失败伪装成“没有
报告”。详情引用按 owner、patient 和短 TTL 绑定，不能把旧端本地 storage 中的 `pdfUrl`
或外部影像地址迁移到小程序。

## 3. Worker 迁移关系

旧项目静态代码中确认有通用任务管理/调度后台能力，但没有发现可作为生产事实的独立
“报告 Worker”。因此本轮不新增一个没有任务来源、没有 owner 归属和没有持久化计划的
报告后台循环。

新 Worker 的职责边界如下：

| 任务 | 新 Worker 状态 | 原因 |
| --- | --- | --- |
| 微信支付通知去重/订单事实 | 已有代码骨架 | 依赖 APIv3 配置、通知解密、schema 和回调验收 |
| 微信支付查单补偿 | 已有代码骨架 | 依赖 prepay attempt、订单版本和人工复核表 |
| 医保 6301 查单/6302 通知补偿 | 任务持久化已接入，Provider 循环仍受 gate | 订单/查单任务表、幂等入队、claim 租约、version CAS 和 6302 入站 contract 已落库；把入队接入真实订单编排、安全凭证读取、真实 gateway 组合和生产 Worker 注册作为下一子步 |
| 医保 6203/6401 退款/撤销补偿 | 未接入 | 缺退款/撤销状态机、幂等键和人工复核流程 |
| 报告目录刷新 | 不新增独立循环 | 当前报告是用户触发的只读请求；没有旧任务事实，也没有必要缓存临床数据 |
| 报告失败重试 | 待 Provider contract 后决定 | 不能在没有来源分页、速率限制和数据新鲜度合同前缓存或重放临床查询 |

Worker 的 preflight 会展示 `medical-insurance` 配置状态，但不会因为医保关闭而放宽
支付 Worker 的严格启动条件。正式环境仍必须保持 `hospital-platform-worker-v2.service`
停用，直到 schema、密钥、Provider 和回调证据齐全。

## 4. 还不能宣称完成的条件

- 医保：正式协议版本、双向 SM2/SM4 golden vector、密钥编码、错误码、relay HTTPS/鉴权、6201/6202/6301/6203/6401 脱敏样例和真实订单验收；
- 医保：owner-scoped 医保订单/凭证/回调/查单任务表，`payToken` hash 化和人工复核；
- 报告：三路 Provider 脱敏样例、公网 API、真实患者归属、PACS/ECG 详情资源策略、PEIS 身份合同和 AI 解读审核；
- Worker：生产 schema 应推进到 `0022_medical_insurance_query_task_version`，随后完成安全凭证读取、正式 gateway 组合、unit 发布、启动/失败/重试/manual review 日志和恢复演练；
- 小程序：医保授权回跳、现金补缴、订单终态查单、退款/异常提示的原生页面和真机证据。

在上述证据完成前，所有支付/医保写入口和 Worker provider 循环继续 fail-closed。

## 5. 支付最终性微调（2026-09-02）

依据最近一组脱敏日志，`apply-pay-settle` 的 `settleStatus=1`、预下单的
`payRecord.status=1`、6202 的 `ordStas=1` 都只表示阶段性成功，不表示最终支付成功。
6201 与 6202 的 `payOrdId` 可以证明订单关联，但仍不能代替 6301/6302、云健康后置结果
和 HIS `isSettle=1`。

本轮已在新项目补充：

- 医保证据的来源、provider 状态、最终性和权威性字段；
- 6202/6301 `ordStas` 的安全分类，3/4/5/6 明确命名为后置候选，不命名为 paid；
- 领域层的金额、最终性和状态迁移校验，未确认结果停留在 `awaiting_confirmation`；
- 不注册生产 runtime 的医保查单 Worker 骨架，包含 claim、退避、版本栅栏和人工复核上限。

具体记录见 [`payment-finality-finetune-2026-09-02.md`](支付最终性微调-2026-09-02.md)。

## 6. 续作：任务来源与回调接线（2026-09-03）

本轮继续推进 F 批次地基，不改变医保正式开关，也不调用真实 Provider：

- 查单任务端口新增按 `taskId` 幂等入队；相同任务重放返回数据库权威行，指向不同订单或调度内容发生漂移时拒绝，避免重复任务篡改查单计划。
- MySQL 和内存仓储都实现了该入队语义，并与既有 claim 租约、version CAS 一起测试；迁移目标 head 已同步到 `0022_medical_insurance_query_task_version`。
- API 组合根已实际注册 6302 通知路由；此前只构造服务但未传入 `createApp` 的接线问题已修复。医保 gateway 不在 API 进程中无效实例化，后续由 Worker/订单编排组合根负责。

下一子步按以下顺序落地：

1. 建立短期、服务端专用的 6201 凭证上下文（原文不进订单读模型、日志、outbox 或小程序；需明确加密存储/TTL/销毁策略）。
2. 实现 owner-scoped 医保订单编排：授权 → 费用来源与 6201 → 6202 → 按终态证据入队 6301 查单，并为混合支付保留现金补缴边界。
3. 在上述编排可生成任务后，把 `createLegacyFsiGateway` 和医保 Worker 接入独立 runtime gate，完成 6301/6302、人工复核、重启恢复和脱敏 Provider 回放验收。

因此当前代码已经具备“任务可持久化、可幂等入队、可恢复领取、可 CAS 更新、6302 路由可注册”的可验证基础；真实订单创建和生产查单循环仍以第 1～3 项为准，不因本轮结构测试通过而自动开启。
