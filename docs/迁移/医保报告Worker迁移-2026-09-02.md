# 医保支付、报告与 Worker 迁移记录（2026-09-02）

本文记录本轮从旧项目向新 Node 服务端和原生小程序迁移的实际落点。旧项目
`/Users/yxswy/Documents/GitHub/hospital` 只作为源码和配置材料读取，未启动旧服务、
旧小程序、旧数据库、Redis 或医保/微信 Provider。

## 结论先行

本轮已完成医保订单域、真实加密适配器、订单编排和查单 Worker 的代码接线；这不等于已经取得正式 Provider 业务验收：

- 医保 FSI 已接入固定路由、严格 envelope、真实 SM2/SM3/SM4、订单号和金额校验；正式 Provider 业务样例、真实订单终态和生产验收仍需单独取得证据。
- 报告目录继续由新 API 的只读 service 负责；LIS/PACS/ECG 的目录边界已有代码，PEIS、PACS/ECG 详情、附件授权和报告解读仍保持关闭。
- 新 Worker 对微信支付和医保查单分别执行独立的配置 gate；医保订单查单任务已经有真实任务来源、owner 归属和持久化消费端。当前没有证据表明旧项目存在一个独立的“报告 Worker”；报告查询是用户请求驱动的只读 API，不应为了页面迁移虚构一个后台任务。
- 微信证书目录 `/Users/yxswy/Documents/GitHub/hospital/env/wechat` 已完成只读核验，但证书和私钥没有复制到仓库、没有写入日志、没有上传服务器，也没有因此打开微信支付。

## 1. 医保 FSI 迁移关系

旧项目移动支付中心实际使用以下专用目标路径：

| infno | 旧目标 path | 新项目落点 | 当前状态 |
| --- | --- | --- | --- |
| 6201 | `/org/local/api/hos/uldFeeInfo` | `packages/adapters/src/legacy-fsi-gateway.ts` + `legacy-fsi-medical-insurance.ts` | 真实加密、费用明细守恒、订单编排和凭证上下文已接入；真实 Provider 业务验收仍独立记录 |
| 6202 | `/org/local/api/hos/pay_order` | 同上 | 输入凭证校验、金额守恒、订单号回显校验、订单持久化和非终态入队已接入；真实订单验收仍待取得 |
| 6301 | `/org/local/api/hos/query_order_info` | `legacy-fsi-gateway.ts` + `legacy-fsi-medical-query.ts` + `apps/worker/src/medical-insurance-order-reconciliation-worker.ts` | 保留 0/1/2 等处理中状态；只有权威终态才推进订单；owner-scoped 加密凭证、查单任务消费和 runtime gate 已接入 |
| 6203 | `/org/local/api/hos/refund_Order` | 同上 | ALL/CASH/HI 退款守恒和原结算上限校验已实现；未接退款状态机 |
| 6401 | `/org/local/api/hos/revoke_order` | 同上 | 只接受明确 `success=true`；未接撤销补偿 |

新 adapter 的固定约束：

1. `infno` 只能来自代码中的固定路由表，不能由 HTTP 参数决定 path 或 `base_url`；
2. 业务数据必须先由注入的 `LegacyFsiCryptoGateway` 封装，不能明文回退；
3. 返回内容必须验签、解密并通过业务字段校验后才能映射；
4. 6201 返回的 `payToken` 只作为 adapter 内部结果，禁止进日志、outbox 或小程序；
5. 6301 的处理中状态不填充虚假金额，只能由上层进入等待确认/继续查单；
6. relay Bearer 必须由新环境变量 `MBS_FORWARD_AUTHORIZATION_TOKEN` 注入，不迁移旧代码里的硬编码 `main-token`。

配置 gate 由 `MEDICAL_INSURANCE_READY` 控制，并要求 `MBS_ENCRYPT_ENABLE=true`、
`MBS_SM2_VERIFY_STRICT=true`、HTTPS relay/target 和完整密钥材料。字段完整只代表配置
形状正确，不代表医保平台已经授权或可以真实结算。

## 2. 报告迁移关系

旧报告页合并了 LIS、PACS、ECG 和体检 PEIS 四种来源。新项目拆为服务端受控目录：

| 旧来源 | 新 API/adapter | 可迁移范围 | 暂不迁移 |
| --- | --- | --- | --- |
| LIS | `/api/v1/reports`、LIS adapter | 目录摘要；LIS 详情短期引用骨架 | 未确认字段、附件长期 URL |
| PACS | `/api/v1/reports`、PACS adapter | 目录摘要 | 详情、影像资源、下载凭证 |
| ECG | `/api/v1/reports`、ECG adapter | 目录摘要 | 详情、原始波形、下载凭证 |
| PEIS | 无 | 暂不接入 | 身份证最小使用、患者归属和字段白名单合同缺失 |
| AI 报告解读 | 无 | 暂不接入 | 模型/知识版本、医疗免责声明、审核和审计缺失 |

报告查询只接受新平台 `patientId` 和有限日期窗口；Provider 患者号及报告号只在服务端
调用帧内使用。目录未指定来源时，三路报告必须整体成功，不把某一路失败伪装成“没有
报告”。详情引用按 owner、patient 和短 TTL 绑定，不能把旧端本地 storage 中的 `pdfUrl`
或外部影像地址迁移到小程序。

## 3. Worker 迁移关系

旧项目静态代码中确认有通用任务管理/调度后台能力，但没有发现可作为生产事实的独立
“报告 Worker”。因此本轮不新增一个没有任务来源、没有 owner 归属和没有持久化计划的
报告后台循环。

新 Worker 的职责边界如下：

| 任务 | 新 Worker 状态 | 原因 |
| --- | --- | --- |
| 微信支付通知去重/订单事实 | 已有代码骨架 | 依赖 APIv3 配置、通知解密、schema 和回调验收 |
| 微信支付查单补偿 | 已有代码骨架 | 依赖 prepay attempt、订单版本和人工复核表 |
| 医保 6301 查单/6302 通知补偿 | 订单编排、任务来源、Provider 循环和 runtime 注册已接入，仍受医保 gate | 订单/查单任务表、幂等入队、claim 租约、version CAS、6302 入站 contract、owner-scoped 凭证读取和真实 gateway 组合均已落库；剩余是生产 schema/unit、Provider 业务和终态证据验收 |
| 医保 6203/6401 退款/撤销补偿 | 未接入 | 缺退款/撤销状态机、幂等键和人工复核流程 |
| 报告目录刷新 | 不新增独立循环 | 当前报告是用户触发的只读请求；没有旧任务事实，也没有必要缓存临床数据 |
| 报告失败重试 | 待 Provider contract 后决定 | 不能在没有来源分页、速率限制和数据新鲜度合同前缓存或重放临床查询 |

Worker 的 preflight 会展示 `medical-insurance` 配置状态；微信支付和医保查单分别
fail-closed，医保不会因为微信支付尚未打开而无法运行。正式环境的 unit 是否启用，
仍必须以 schema、密钥、Provider 和回调证据齐全为前提。

## 5. 支付最终性微调（2026-09-02）

依据最近一组脱敏日志，`apply-pay-settle` 的 `settleStatus=1`、预下单的
`payRecord.status=1`、6202 的 `ordStas=1` 都只表示阶段性成功，不表示最终支付成功。
6201 与 6202 的 `payOrdId` 可以证明订单关联，但仍不能代替 6301/6302、云健康后置结果
和 HIS `isSettle=1`。

本轮已在新项目补充：

- 医保证据的来源、provider 状态、最终性和权威性字段；
- 6202/6301 `ordStas` 的安全分类，3/4/5/6 明确命名为后置候选，不命名为 paid；
- 领域层的金额、最终性和状态迁移校验，未确认结果停留在 `awaiting_confirmation`；
- 医保查单 Worker 已注册到独立 runtime gate，包含 claim、退避、版本栅栏和人工复核上限；gate 未通过时不会调用 Provider。

具体记录见 [`payment-finality-finetune-2026-09-02.md`](支付最终性微调-2026-09-02.md)。

## 7. 6301 查询适配器与凭证上下文（2026-09-03）

本轮把第 1 项继续推进到可被 Worker 直接消费的窄接口：

- `MedicalInsuranceCredentialContext` 现在在同一 AES-GCM 密文载荷中保存 `payToken` 和 6301/6401 所需的 `orgCodg`、`idNo`、`userName`、`idType`；公共 handle、订单读模型、日志和 outbox 仍不含这些原文。
- `createLegacyFsiMedicalInsuranceQueryGateway` 通过订单的 `ownerUserId`、订单号、用途和 TTL 读取活动凭证，再调用固定的旧 FSI 6301 路由；查询参数不从 task、URL 或小程序传入。
- 6301 没有金额时沿用已落库支付订单金额作为对账基线；6301 的 3/4/5/6 仍映射为 `settlement_candidate`，不会被提升为 `paid`。取消/失败状态才映射为明确失败证据。
- `MedicalInsuranceReconciliationWorker` 已收窄为只依赖 `query` 能力；新订单域由 `MedicalInsuranceOrderReconciliationWorker` 消费 owner-scoped 查单任务，避免把 6201/6202/6203/6401 的写操作错误接入查单循环。

对应测试覆盖了凭证字段完整传递、处理中状态、候选状态、无凭证 fail-closed、任务重试和权威终态回写。真实 Provider 业务验收、生产 schema/unit、医保授权回跳、现金补缴情形和 6203/6401 补偿仍需在可回滚发布批次中完成。
