# 医保关单上下文修复

当 `2.6.33` 返回已有支付流水正在进行中，但新服务订单没有保存完整关单上下文时，禁止直接猜测
`businessId / payingId / tradingId`，也禁止手工调用 2.6.65.6。先从保留的服务端原始日志或众阳运维侧
取得并交叉核对完整上下文，再使用 worker 的受控维护命令补录密文。

## 修复前检查

必须同时确认以下事实属于同一个平台医保订单：

- 2.6.65.1 响应中的 `businessId`；
- 2.6.65.2 响应中的 `payingId` 和 `tradingId`；
- `hospitalId`、Provider 患者号和 `tradeOrderIds`；
- 证据来源是服务端原始日志或众阳运维侧查询，而不是客户端上报值。

如果缺少任一字段，停止修复并转人工处理。不能用平台 `business_id`、6201 的 `payOrdId` 或 2.6.33
的 `outTradeOrderId` 代替这三个 Provider 关单标识。

## 执行方式

修复命令从标准输入读取上下文，避免把 Provider 标识放进命令行参数、shell 历史或进程列表：

```bash
printf '%s' '<仅在受控服务器内准备的 JSON>' | \
  pnpm --filter @hospital/worker medical-insurance-context-repair \
  --order-id '<平台医保订单号>' --confirm
```

JSON 形状如下，示例值仅用于说明字段，不代表真实订单：

```json
{
  "businessId": "provider-business-001",
  "businessCode": "provider-business-code-001",
  "hospitalId": "provider-hospital-001",
  "patientId": "provider-patient-001",
  "tradeOrderIds": ["provider-trade-order-001"],
  "payingId": "260650000000001",
  "tradingId": "260650000000002",
  "evidenceSource": "provider-log"
}
```

命令只允许为原来没有上下文、且尚未完成或取消的订单补录；已有密文上下文不会覆盖，已完成或已取消
的订单会拒绝。命令不访问 Provider、不改变订单状态，只写入现有的加密上下文。

补录成功后，再由支付小程序重新执行专用关单流程。若 2.6.65.4 查到已支付、2.6.65.11 或
2.6.65.6 返回不确定结果，订单继续进入人工复核，不得重复重建支付。
