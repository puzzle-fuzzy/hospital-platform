# 医保退费流水号超长的修复与受控恢复

## 流水号约定

山西医保接口规范 v1.3.35 的 6203 输入表 272 规定 `appRefdSn` 最长 40 字符。

平台内部 `refundNo` 仍为 `RFMI` 加 48 位 SHA-256 十六进制摘要，共 52 字符。它同时参与平台幂等、微信退款号、查询及任务关联，不能为修复医保字段而重写历史内部编号。

6203 的外部 `appRefdSn` 由不可变内部编号确定性派生：平台生成的 `RFMI` 加 48 位摘要取前 40 字符，即保留 `RFMI` 加 36 位摘要；已在 40 字符内的历史编号原样保留。其它超长格式拒绝发送。该映射规则应保持稳定，同一退款记录的后续受控调用必须使用同一个外部流水号。适配器对实际发送的 `appRefdSn` 执行非空及不超过 40 字符的校验，空格也计入长度。

## 旧失败单的恢复前提

普通 Admin 点击、查单和 Worker 不会重新提交失败的 6203。不能直接修改退款状态、删除旧单、重写内部退款号，或改幂等键制造新单。

恢复前逐项核查：

1. 从原始请求及返回日志确认拒绝原因确为 `APP_REFD_SN` 超长。`360221` 是数据库类错误码，单独这个码不足以证明可重试。
2. 核对目标退款号、原 Provider 请求号、记录版本、原支付订单及 ALL 四项金额。读取同订单的全部医保和微信退款记录，排除其它成功、处理中、未知或人工补退事实；与渠道核对尚无实际退款。
3. 确认执行窗口内没有其它入口并行操作同一订单。单条退款记录的 CAS 不能代替全订单的互斥控制。
4. 备份目标退款记录及审计证据，确认修复后的运行包及运行配置。授权资料只在现有服务端解密调用栈中使用，不导出到文件或终端。

## 受控执行

`MedicalInsuranceRefundService.recoverRejectedAppRefdSn()` 只供已授权的运维调用，不注册普通 HTTP/UI 入口。输入包括原 `refundNo`、`expectedVersion`、`expectedProviderRequestId`、操作者、请求上下文，以及明确的 `confirmedRejection: "APP_REFD_SN_TOO_LONG"`。

该入口只接受固定 Admin 幂等身份下的遗留 52 字符 ALL 失败单：医保状态 `failed`、医保业务结果为空、错误码 `360221`；有现金时微信状态必须为 `requested` 且保持原微信退款号、该订单没有微信退款记录。缺少按订单查账能力、审计能力或原授权上下文时拒绝执行。

执行保留原内部退款号及幂等身份，先以记录版本进行严格 CAS 领取 `processing`，仅领取成功的一方可发送一次 6203。CAS 冲突禁止出站。医保 `SUCC` 后继续原微信现金退款流程；医保明确失败停止微信，`EXP` 或网络未知进入人工复核。医保成功而微信失败时，整笔记录及审计都不能标为成功。

领取后进程中断或结果未知时，不可用旧错误信息再次重放。应依据新请求日志、渠道状态及台账人工核对。执行后检查两腿状态、原微信商户退款号及审计记录；微信非终态沿原查单任务收敛。

本地 mock 测试只能验证长度、幂等、状态守卫和并发控制，不证明真实渠道已完成退款。
