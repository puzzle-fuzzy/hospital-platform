# ADR 0005：医保支付统一核心，业务入口保持分开

## 状态

实施中（2026-09-04）。本次只统一订单事实、微信医保下单类型和 6202/6301
公共编排；门诊 6201 的 provider 费用事实仍须以已确认的众阳合同接入，未凭空
补写未知字段。

## 决策

采用“支付能力统一，业务入口分开”：

| 层 | 统一内容 | 保持分开的内容 |
| --- | --- | --- |
| 小程序/API 入口 | 不合并页面，不让预约页面承载门诊账单 | 挂号入口、门诊费用入口、取消/退款入口 |
| 医保订单 | `businessType`、`orderType`、`businessId` | 挂号的 `appointmentId` 与门诊的费用记录事实 |
| 支付编排 | 6202 结算、6301 查单、CAS 状态更新、查单任务、微信现金支付确认 | 各业务如何取得真实 6201 费用明细 |
| 微信 adapter | 共用新版 `/v3/med-ins/orders`，`order_type` 从订单事实传入 | `RegPay` 与 `DiagPay` 的业务事实来源 |
| 日志 | 同一组 `traceId`、`providerRequestId`、业务类型字段 | 业务名称和事实 ID 按入口填写 |

这样既符合文档中“挂号/诊间按支付类型区分”的业务关系，又不会把门诊费用
伪装成预约记录。

挂号写入已经通过独立的预约命令入口承载：先由 `AppointmentWriteService` 完成
号源锁定、预约登记和取消，再由医保核心处理支付；目录/历史 service 不承载这些
副作用。门诊目前只开放已核对的费用读取入口，不能因为共享医保核心就虚构门诊
预约上下文或 6201 入参。

## 日志约定

医保支付事件至少带以下低敏字段：

- `event`：请求、完成、查单和失败阶段；
- `traceId`：平台请求链路；
- `ownerUserId`、`orderId`：服务端关联键；
- `businessType`：`registration` 或 `outpatient`；
- `orderType`：`RegPay` 或 `DiagPay`；
- `businessId`：服务端业务事实引用；
- `providerRequestId` / `providerRequestIds`：众阳或微信请求关联号。

日志禁止写入 `authCode`、`payAuthNo`、`payToken`、身份证号、医保卡号、费用
原始明细和微信调起参数。provider 原始响应只在 adapter 内按字段白名单解析。

## 当前明确不做的事情

1. 不恢复旧版 `payinsurance/unifiedorder`；当前微信支付仍走新版 v3 adapter。
2. 不把 `WECHAT_MEDICAL_INSURANCE_ORDER_TYPE` 作为全局配置；业务类型由订单事实决定。
3. 不为了“统一”让门诊费用复用预约 `AppointmentMedicalInsuranceContext`。
4. 当前门诊模块仍只有已经核对的 2.6.33 费用只读能力；拿不到门诊 6201 正式字段合同前，门诊支付写入保持 fail-closed。

## 上线前检查

1. 在目标数据库执行 `0034_medical_insurance_business_key.sql`，确认 schema readiness 通过。
2. 确认线上旧订单的 `business_type/order_type/business_id` 回填结果，再启动新 API。
3. 观察服务端日志中同一 `traceId` 是否能串起授权、6201、6202、微信下单和 6301。
4. 门诊入口接入前，补充门诊真实 6201 费用明细、参保信息和授权解析合同；材料缺失时不要用挂号样例替代。
