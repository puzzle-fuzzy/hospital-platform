# ADR 0004: 健康知识内容与临床安全边界

## 状态

已接受，Phase 8A contract/domain/persistence 预注册阶段；版本化 schema 已部署，但健康知识 API 尚未挂载，旧库正文也尚未导入新 schema。

## 背景

旧项目的 `module_knowledge` 同时包含健康百科、疾病/药品详情、健康贴士和自测评分，
其中一部分文本会被用户理解为医疗建议。它不能像普通字典表一样直接复制：旧字段没有
统一的内容版本、审核人、来源和生效时间，也没有证明旧自测分值仍适用于当前医院业务。

## 决策

### 1. 健康知识是“已审核的只读内容”，不是诊断服务

第一阶段只允许发布服务端已审核的内容读模型：

- 疾病、药品、部位、人群、科室和症状只作为知识检索/阅读资料；
- API 响应必须携带 `contentVersion`、`reviewedAt`、`sourceLabel` 和固定免责声明；
- 不返回 provider 患者字段，不接收患者病历，也不根据用户症状自动生成诊断结论；
- “建议就医”“急症提示”等文案必须是审核内容的一部分，不由 API 或模型临时拼接。

### 2. 内容必须可追溯、可下线、可回滚

目标 MySQL 内容表至少需要以下控制字段：

| 字段 | 约束 | 用途 |
| --- | --- | --- |
| `content_id` | 平台内部稳定标识 | API 只暴露内部 opaque 引用 |
| `content_version` | 正整数或不可变版本号 | 客户端反馈和缓存关联具体版本 |
| `status` | `draft/published/withdrawn` | 只有 `published` 可进入患者端读模型 |
| `source_label` | 非敏感来源说明 | 显示内容出处，不伪造权威机构 |
| `reviewed_at` | 必填时间 | 证明内容曾被审核，不代表永久有效 |
| `reviewer_ref` | 服务端内部引用 | 不返回个人隐私，支持后台审计 |
| `effective_from/to` | 可选时间窗口 | 支持未来发布和紧急下线 |
| `updated_at` | 必填时间 | 缓存失效和变更追踪 |

发布状态、审核信息和正文必须在同一持久化事实中可查询。日志只用于定位发布流程，
不能作为“内容已发布”的唯一依据。

### 3. 患者端只读，后台编辑另设权限边界

患者端目标路径为 `/api/v1/knowledge/*`，只注册 GET；内容创建、审核、发布、撤回和
批量导入属于未来独立 Admin API，不能复用患者端 session，也不能把后台 repository
直接暴露给小程序。

患者端接口必须经过 response schema 白名单映射，而且 repository 返回值在 service 边界
还要做一次运行时校验和重新投影。TypeScript 类型不能证明 MySQL 行、回放数据或未来
任务实现真的安全；疾病详情可以包含正文段落，但不得顺带返回原始数据库字段、编辑人、
内部审核备注、未发布版本或管理端操作信息；详情返回的 opaque id 还必须与请求路径一致。
读模型损坏必须整批 fail-closed，不能过滤坏行伪装成空目录或成功结果。

### 4. 自测评分必须版本化并经过临床复核

旧项目的自测配置包含题目、分值和结果区间。新项目不得直接把旧 Python 配置复制为
生产判定规则。后续实现必须同时具备：

- `assessmentVersion` 和题目/结果配置的不可变快照；
- 对题目 id、答案范围、必答项和分值溢出的严格校验；
- 临床/业务负责人确认记录和可撤回版本；
- 结果中的“筛查提示”与“诊断结论”明确区分，并固定就医免责声明；
- 单元测试、边界测试和人工样例复核，不能只证明代码分支可执行。

在这些证据完成前，只迁移健康百科只读目录的 contract 设计，不开放自测提交或自动
风险等级接口。

### 5. AI 导诊与知识库分离

AI assistant 只能通过独立的 gateway 读取已发布知识片段，并保留请求 trace、模型版本、
知识版本和安全策略结果。AI 输出不能反向写入知识库，也不能绕过内容审核直接成为患者端
固定知识。AI route、WebSocket、音频和报告解读另行设计，不因健康百科迁移而隐式开放。

## 非目标

- 本 ADR 不声明旧健康知识数据已经适合直接迁移；
- 不在 Docker/MySQL 未验收时使用内存数据伪装生产内容；
- 不实现诊断、处方、用药调整或急症分诊；
- 不把旧接口的 `id`、原始字段和管理状态直接透传到新小程序；
- 不因为配置存在、路由返回 200 或模型能生成文本，就宣称医疗内容已上线。

## 实施顺序

1. 在脱敏数据副本中盘点旧表、字段、内容来源和实际使用页面；
2. 由业务/临床负责人确认正文、药品信息、自测规则和免责声明的责任边界；
3. 设计并审核 MySQL migration、发布状态、版本和审计字段；
4. 先实现 domain port、TypeBox response contract、未挂载的只读 service 和 fail-closed repository；
5. 完成真实 schema migration、内容导入校验和 owner/权限测试；
6. 在 staging 验证内容版本、撤回、缓存失效和 API response 后，才注册患者端 GET route；
7. 自测与 AI 分别走独立 contract、gate、日志和人工验收，不与百科目录共用成功状态。

## 验收证据

健康知识阶段至少需要以下独立证据，缺一项都保持未上线：

| 证据层 | 证明内容 |
| --- | --- |
| 代码 | domain/contract/service 测试、响应白名单、日志脱敏和 `pnpm architecture:audit` |
| 数据 | MySQL migration、published/withdrawn 状态、版本和审核字段真实可读 |
| 内容 | 脱敏导入记录、来源、审核人/时间和撤回演练 |
| 运行 | `db:schema`、`db:integration`、`runtime:preflight` 和接口 response 校验 |
| 产品 | 小程序阅读、免责声明、过期/撤回内容不再展示 |

当前状态：已完成边界设计、TypeBox contract、domain port、固定免责声明校验、只读 service、
repository 结果运行时校验与白名单重新投影、低敏失败日志、bundle validator、带时区的导入时间校验、
版本化 schema 和 fail-closed MySQL repository/事务导入器；
真实内容导入、staging 审核/撤回证据、患者端健康知识 API 挂载和小程序页面均未因本 ADR 标记为 ready。
