# 支付运营台维护规划

## 1. 当前事实

当前 Admin 的支付数据不是一套独立的支付运营账本，而是运行时把已有订单表合并成一个低敏列表：

- 普通微信支付读取 `hp_payment_orders`，退费读取 `hp_wechat_refunds`；
- 医保 + 微信支付读取 `hp_medical_insurance_orders`，聚合退费读取 `hp_medical_insurance_refunds`；
- Admin 服务端分别读取两类订单，按 `updatedAt` 合并后展示；当前分页请求会读取覆盖目标页所需的候选记录，单次查询窗口上限为 10,000 条；
- 医保订单中的医保金额、自费金额、个人账户、基金等分项来自 6202/医保查单事实；微信现金腿由 APIv3 的支付通知或查单确认；
- 平台已经新增自己的统一支付聚合单、支付腿和追加式状态事件表。普通 `PaymentOrder` 的 API 创建、状态迁移和 Worker 状态更新，在生产 MySQL 组合根启用后会把来源订单、运营台聚合/支付腿/事件和 outbox 放进同一个事务；医保 `insert/applySettlement` 在金额事实产生时也会把来源订单更新与医保/微信两腿投影放进同一个 MySQL 事务（初始 `amounts=null` 时不伪造聚合单）。HIS 同步任务、对账差异表和 Admin 操作审计表已经有内部框架，但仍有未接入的运营动作和外部连接器。

因此，页面上的“医保 + 微信”是管理端的业务聚合视图，不代表外部存在一笔可以替代两条 provider 交易的单一交易。医保 6203 和微信 APIv3 退款仍必须保留各自的 provider 身份、请求号、状态和查单边界。

### 1.1 “医保 + 微信”名称的准确口径

- 当前业务展示沿用“医保 + 微信/医保混合支付”名称，但平台实际维护的是医保腿与微信 APIv3 现金腿两条独立事实，最后只在平台聚合单中合并计算和展示。
- 代码中的 `/v3/med-ins/orders` 只代表微信 APIv3 收款侧的既有 Provider 路由；不能据此推导出 HIS 侧存在一笔可直接覆盖医保与自费的统一退款交易。
- 退费固定由医保 6203 `/org/local/api/hos/refund_Order` 与微信 APIv3 普通退款分别处理；当前没有使用、也没有注册 `/v3/med-ins/refunds/notify`。HIS 旧微信 V2 兼容链路不作为本退费接口的替代实现。

## 2. 维护原则

平台需要维护自己的支付事实和运营状态，HIS 仍然是业务费用、就诊/挂号关联及院内结算回写的外部系统。两边通过稳定业务键和同步任务关联，不能把 HIS 的一次查询结果直接当成平台支付终态。

| 事实 | 权威来源 | 平台处理 |
| --- | --- | --- |
| 费用项目、业务单据、就诊/挂号关联 | HIS/医保业务接口 | 保存金额快照、业务引用和来源版本 |
| 医保结算金额及医保状态 | 6201/6202/6301/6302 | 保存分项、`ordStas`、请求号和最后观测时间 |
| 微信现金支付状态 | 微信 APIv3 通知/查单 | 通过通知去重和查单补偿确认，不接受前端成功态 |
| 退款状态 | 6203 + 微信 APIv3 退款/查单 | 一个聚合退费单，下面保留医保腿和微信腿 |
| 平台订单、幂等、重试和人工处理 | 平台数据库 | 作为运营台和 Worker 的可恢复事实 |
| HIS 回写结果 | HIS 回写接口 | 只有支付终态和金额校验通过后才执行，并记录回写状态 |

所有金额继续统一使用分；所有状态必须使用明确枚举；未知状态、金额不守恒、业务键不一致或同步版本倒退时进入人工复核，不能由页面猜测为成功。

## 3. Admin 后续应该展示什么

### 3.1 支付总览

按业务日和业务类型展示：

- 总订单数、医保订单数、普通微信订单数；
- 总金额、医保支付、微信现金、个人账户、基金和其他支付分项；
- 已完成、支付中、待确认、失败、人工复核、已退款和退款处理中数量；
- HIS 同步延迟、微信查单待处理、医保查单待处理、金额/状态不一致数量。

总览只做聚合统计，不能作为单笔支付终态依据。

### 3.2 支付订单

保留当前列表，但逐步增加以下低敏字段和筛选：

- 平台支付聚合单号、业务类型、业务单号、订单创建和最后观测时间；
- HIS 业务引用、医保 `medOrgOrd/payOrdId`、微信交易引用的受控展示；
- 总额、医保分项、微信现金、个人账户、基金及金额守恒结果；
- 支付聚合状态、医保腿状态、微信腿状态、HIS 回写状态；
- 查单次数、最近一次失败原因、下一次补偿时间、是否需要人工复核。

患者姓名、身份证、医保凭证、微信调起参数、支付原文和密钥上下文不进入普通列表。

### 3.3 单笔详情和时间线

点击订单后展示一条可审计时间线：

`HIS 费用快照 → 6201 → 6202 → 微信预下单 → 微信通知/查单 → 医保确认 → HIS 回写 → 退费`

每个节点显示来源、状态、金额、发生时间、请求号和是否可重试；原始请求/响应仍然只在受控日志入口按权限展开，不直接塞入普通详情卡片。

### 3.4 对账与待处理

单独提供待处理队列：

- 微信已支付但医保未确认；
- 医保已结算但微信现金未确认；
- 两边金额不一致；
- HIS 回写失败或版本冲突；
- 6203 返回 `EXP`、微信退款未知或两腿结果不一致；
- 任务租约过期、重试耗尽和需要人工接管的记录。

这里的操作应是“重新查单、重试安全回写、标记人工复核、查看证据”，不是直接修改订单状态。

### 3.5 退费中心

退费中心以“平台支付聚合单”为一行：

- 普通微信单展示微信退款状态；
- 医保 + 微信单展示一个聚合退费状态，并展开医保腿和微信腿；
- 页面只有一次“医保 + 微信一并退费”入口；
- 同一聚合退费单复用稳定幂等身份，禁止因为页面重复点击产生第二笔 6203 或第二笔微信退款；
- 退费完成后展示 HIS 回写/业务关闭状态，未完成时明确标记处理中或人工复核。

### 3.6 HIS 同步中心

展示同步窗口、上次成功时间、游标/业务日、成功/失败数量、积压数量和最后错误。同步中心只允许受控地执行“拉取、比对、重试”，不允许 Admin 直接编辑金额、订单状态或 provider 凭证。

## 4. 建议的数据模型

现有订单表和退款表先保留，新增平台运营层，不建议立即把所有字段硬塞进现有两张订单表。

### 4.1 `hp_payment_aggregates`

平台支付聚合单：业务类型、业务主键、患者内部引用、总金额、金额来源版本、聚合状态、HIS 同步状态、版本和时间字段。它是 Admin 一行记录的稳定主键。

### 4.2 `hp_payment_legs`

支付腿：`medical_insurance`、`wechat_cash`、`hospital_reduce` 等。保存腿类型、来源订单、金额、provider 交易引用摘要、当前状态、确认时间和版本。医保腿和微信腿永远分开存储，页面再聚合。

### 4.3 `hp_payment_events`

追加式状态事件：来源、旧状态、新状态、金额快照、请求号、幂等键、事件时间和摘要哈希。它用于详情时间线和事故追溯，不保存完整原始报文。

### 4.4 `hp_payment_sync_tasks`

同步/对账任务：来源系统、聚合单号或业务键、窗口、状态、尝试次数、租约、下次执行时间、最后错误和结果摘要。Worker 负责自动查单与补偿，Admin 只负责展示和发起安全重试。

### 4.5 `hp_payment_reconciliation_results`

保存一次 HIS、医保或微信观测与平台事实的比较结果：比较对象、状态、金额差异、状态差异、来源时间、证据引用和处理结果。对账记录不可通过页面覆盖，只能产生新的观测。

### 4.6 `hp_payment_operator_audits`

记录 Admin 用户发起的退费、查单、重试、人工复核和查看受控证据等动作：操作者、动作、目标聚合单、请求号、结果和时间。审计表不保存密码、密钥、原始医保报文或微信敏感参数。

## 5. 分阶段落地

### P0：先把现状变成可维护读模型

1. 保留现有支付和退费状态机；
2. 把当前两张订单表投影成统一的 Admin 支付聚合读模型；
3. 增加服务端分页、业务日/状态/来源筛选；
4. 先补齐订单详情和两腿状态，不开放任意状态修改。

#### P0 当前已实现切片（2026-09-20）

- Admin 历史支付接口现在返回统一分页读模型：`items`、`total`、`page`、`pageSize`；普通微信订单与医保 + 微信订单仍由服务端合并排序，页面不再把两类记录当成两个退费入口。
- 已支持服务端的来源、业务类型和精确订单号筛选；总数由两类订单仓储分别统计后合并，页面使用服务端分页，不通过前端截断最近记录伪造分页。
- 已增加业务日和支付聚合状态筛选：业务日按 `Asia/Shanghai` 自然日转换为 `[created_at >= start, created_at < end)`，状态在普通微信/医保来源仓储侧先过滤，再合并计数；`created/ pending/ paid/ failed/ manual_review` 只表示来源订单的支付状态，不能误读为退费状态。
- 为避免无界扫描，当前分页查询窗口最多读取 10,000 条候选记录；超过窗口时应先缩小业务、来源或订单号筛选，后续聚合账本和索引完成后再扩展查询能力。
- 退款记录仍按原有普通微信退费和医保 + 微信聚合退费链路读取；本切片没有新增支付状态写入、HIS 回写、6203 调用或微信退款调用。
- 当前 P0 仍未完成的部分是更丰富的低敏字段、HIS 同步状态/补偿展示和对账队列；订单详情时间线已经接入平台账本读取，但仅展示聚合单、两条支付腿和低敏状态事件。

### P1：建立平台支付聚合层

1. 新增 `hp_payment_aggregates` 和 `hp_payment_legs`；
2. 新订单创建和状态更新时同时写入聚合单和支付腿；
3. 旧订单通过一次性受控回填建立映射，回填失败进入人工复核；
4. Admin、退费服务和 Worker 全部以聚合单作为业务入口。

#### P1 当前已实现切片（2026-09-21）

- 已新增 `0052_payment_operations_ledger` 迁移，建立 `hp_payment_aggregates`、`hp_payment_legs` 和 `hp_payment_events`；迁移清单、索引和外键均纳入 persistence schema probe，未保存 Provider 原文、密钥或微信调起参数。
- 已新增 MySQL 与内存仓储，聚合单、支付腿按版本 CAS 更新，状态事件按“聚合单 + 幂等键”追加并可安全重放；Provider/HIS 引用只保存摘要哈希。
- 已实现普通微信订单和医保订单的低敏投影。医保订单会生成一个聚合单，下面同时挂 `medical_insurance` 和 `wechat_cash` 两条腿；这只是平台侧合并账本，不改变“医保 + 微信分别调用、分别确认、最后合并展示”的真实支付边界。
- Admin 支付历史在配置了平台仓储时会按当前来源订单补齐聚合账本，并返回低敏 `operationAggregateId` 供后续详情、对账和退费关联使用；投影具有来源版本和事件幂等保护。
- Admin 可从统一列表打开支付账本详情，查看一笔聚合单下的医保腿、微信现金腿和低敏状态时间线；详情读取会追加 `payment_detail_read` 审计，且不会返回患者身份、医保凭证、微信调起参数或原始 Provider 报文。
- 普通 `PaymentOrder` 已新增组合根端口：API 与 Worker 共用 domain 的确定性投影构造器，MySQL 在订单 INSERT/CAS UPDATE、聚合单、微信现金腿、状态事件和 outbox 之间使用同一事务；投影写失败会回滚来源订单状态。内存/旧测试仓储没有该可选端口时仍走原订单写入路径，因此不能把所有自定义组合根都称为原子双写。
- 医保 `MedicalInsuranceOrderRepository.insert/applySettlement` 的 MySQL 实现已在同一事务内写入金额存在时的医保腿、微信现金腿和低敏事件；内存/旧测试仓储仍可能只有来源订单能力，因此不能把所有自定义组合根都称为原子双写。医保 `hisSyncStatus=pending` 只表示平台尚未建立 HIS 同步闭环，不代表 HIS 已失败或已成功。
- 已补充受控历史回填命令 `pnpm payment:operations:backfill`：默认只做 dry-run，按 `created_at + 来源订单号` 游标分页读取两类来源订单；只有显式 `--apply --yes` 才会把低敏 aggregate/leg/event 写入平台账本。命令支持 `--source`、`--from`、`--to`、`--batch-size`，输出候选数、可投影数、已投影数、已存在/过期版本数、医保金额缺失数和受限失败清单。
- 回填只读取 `hp_payment_orders` 和不解密字段的 `hp_medical_insurance_orders`，不调用 HIS、6203、医保查单或微信 APIv3，不修改来源订单、退费台账、支付腿终态或 outbox；来源版本不前进时直接标记 unchanged/stale，重跑不会重复追加事件。
- 回填执行前必须通过 0052/0053/0054 schema readiness；本地和生产都应先保存 dry-run JSON 报告，再由维护人确认窗口后 apply。回滚采用“停止任务 + 修复来源后按更高来源版本重投影/人工复核”的补偿方式，不直接删除账本行，避免破坏审计链。2026-09-21 已在正式数据库成功执行 0052/0053/0054，并随 `4ba2e881ce59bb52fdfc5c30c48a3f824fca87fd` 发布 API/Worker；历史账本回填尚未执行，因此仍不是“历史全量回填完成”证明。

### P2：接入 HIS 同步与对账

1. 先确认 HIS 的稳定业务键、查询窗口、状态枚举、金额单位和回写接口；
2. 新增同步任务和对账结果表；
3. 只读拉取、金额/状态比对、查单补偿完成后，再开放受控 HIS 回写；
4. 所有未知、超时、版本冲突和金额不一致保持人工复核。

#### P2 当前已实现框架切片（2026-09-21）

- 已新增 `0053_payment_sync_reconciliation` 迁移，建立 `hp_payment_sync_tasks` 和 `hp_payment_reconciliation_results`；任务租约、版本、幂等键、证据摘要和比较结果均有独立边界。
- 已新增 MySQL/内存任务仓储：任务可幂等入队、按租约 claim、按版本更新；对账结果按聚合单、来源和观测键幂等追加，证据摘要变化会拒绝覆盖。
- 已新增无 Provider 的 `PaymentSyncCoordinator`：统一处理任务入队、租约结果、金额/状态比较、证据摘要和失败重试；匹配结果进入 `succeeded/resolved`，缺失、金额差异、状态差异和重试耗尽进入 `manual_review`，不会修改支付聚合终态。
- Admin 已接入同步任务运营入口：可按状态、来源、任务类型和聚合单筛选任务；对 `failed/manual_review` 任务执行“重新排队”，对待执行任务执行“转人工复核”。两种动作都写入 `sync_retry/manual_review` 低敏操作审计，并通过任务版本 CAS 避免覆盖 Worker 正在持有的租约；它们只改变同步任务状态，不改变支付聚合单、支付腿或来源订单终态。
- 当前只完成“任务与结果的持久化框架”，尚未连接 HIS 拉取、6203/医保查单或微信 APIv3 查单，也没有因本框架自动修改任何支付终态。HIS 稳定业务键、窗口、状态、金额和回写合同仍需外部材料确认。

### P3：运营闭环

1. 上线支付总览、详情时间线、对账队列和退费中心；
2. 增加 Admin 操作审计和权限分级；
3. 用受控 dry-run/apply 命令完成历史订单回填，保留报告、失败清单和来源版本；重试沿用幂等投影，回滚采用停止/修复/补偿投影，不删除审计事件；
4. 用真实 HIS、医保 6203、微信 APIv3 和公网回调分别完成验收，不能用本地测试替代资金验收。

#### P3 当前已实现切片（2026-09-21）

- 已新增 `0054_payment_operator_audits` 迁移以及 MySQL/内存审计仓储，支持按聚合单查询 Admin 查看详情、退费、查单、同步重试和人工复核等动作的低敏审计事实。
- 审计只保存动作、目标聚合单、请求引用、结果/原因和摘要，不保存 Admin 令牌、密码、密钥、医保原文或微信调起参数；相同审计 ID 的载荷漂移会被拒绝。
- 当前支付账本详情读取已经写入 `payment_detail_read` 审计；普通微信退费和 Admin “医保 + 微信整笔退费”已经写入同一聚合单的 `refund_request` 审计，医保腿与微信腿的内部调用不会重复冒充一次新的 Admin 操作；普通微信/医保退费查询也会写入 `refund_query` 审计；同步任务重新排队和转人工复核分别写入 `sync_retry/manual_review` 审计。现有 Admin 接口只有服务令牌和请求号，没有稳定的操作者身份字段，因此 `operator_ref` 暂保持空值。接入真实操作者身份前，不能把令牌摘要冒充操作人。
- Admin 页面现在统一展示支付订单、聚合账本详情和同步任务人工处理入口；同步任务操作仍是平台内部队列维护，不代表 HIS、医保或微信查单已经真实联通。
