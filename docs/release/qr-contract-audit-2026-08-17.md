# 首页就诊人二维码契约审计（2026-08-17）

> 结论：当前停止二维码业务编码。旧端实现不是可迁移的业务契约，新端继续保留入口和明确关闭态，不生成伪二维码，也不把医疗标识发送给第三方服务。

## 1. 旧端事实

旧端 `hospital-app/src/pages/index/index.vue` 的二维码逻辑：

- 从患者对象读取完整 `medicalCardNo`；
- 拼接第三方 `api.qrserver.com/v1/create-qr-code/` 图片地址；
- 在弹窗中同时展示二维码和完整卡号；
- 没有医院扫码字段定义、签名规则、用途/受众限制、有效期、撤销、防重放和扫码回执。

这只能证明旧页面曾经展示过一张由外部服务生成的图片，不能证明医院设备可以据此完成安全的患者识别。
更不能把完整医疗卡号继续放入新的 URL、日志、缓存键或小程序页面参数。

## 2. 新端当前边界

原生首页保留旧端视觉入口和二维码图标；点击后由 `onPatientQr` 根据当前是否有已确认患者展示：

- 没有患者：提示“暂无就诊人”，引导先登录并选择就诊人；
- 已有患者：提示“二维码暂未开放”，说明等待医院扫码字段和有效期协议；
- 两种情况都不发起网络请求，不读取或拼接 provider 患者号、完整卡号，不调用第三方二维码服务。

小程序验收测试同时固定了“不包含 `api.qrserver.com`”和“入口只显示未开放状态”的边界。

## 3. 正式开放前必须冻结的契约

在医院/HIS 提供书面协议和脱敏样例前，不新增二维码 API。最小契约至少需要明确：

1. 扫码用途、受众和医院设备信任边界；
2. 服务端根据当前 owner-scoped 患者映射生成的 opaque `qrToken` 或 `qrSessionRef`；
3. token 的签名、短 TTL、一次性/防重放、撤销、轮换和限流规则；
4. 小程序展示的是受控图片或受控内容，不接触完整卡号和 provider 患者号；
5. 医院扫码成功、失败、过期和重复扫码的回执状态机；
6. 生成、展示、扫码和失效事件的低敏审计日志，以及日志中禁止出现的字段；
7. 真机生成、医院设备扫码、过期、重复扫码和跨患者隔离验收方案。

## 4. 决策与下一步

本轮按业务正确性要求停止二维码实现，不用前端 fixture、随机字符串或万能转发填补缺口。二维码不能作为
预约、门诊缴费、支付或医保授权的替代入口；这些能力仍按各自 contract 和副作用 gate 验收。

后续只有在 Provider/HIS 提供上述协议、脱敏样例和测试设备后，才进入“contract → 服务端短期引用 → 小程序展示 →
医院扫码回执 → 真机验收”的完整链路。相关长期规则见 [`首页迁移说明`](../migration/homepage-migration.md)、
[`静态与关闭能力真值审计`](../migration/static-and-closed-feature-parity.md) 和 [`P0 只读业务验收手册`](p0-readonly-business-acceptance-runbook-2026-08-17.md)。
