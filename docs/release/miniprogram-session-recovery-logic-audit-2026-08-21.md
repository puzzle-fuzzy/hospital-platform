## 本轮发现的问题

小程序在 GET 读取收到 `401/unauthorized` 后允许重新获取一次微信会话。旧逻辑对第二次请求的 `401` 只向页面抛出错误，
没有清理刚刚获得的无效 token。这样页面下一次进入时仍会携带同一失效 token，容易反复出现“Invalid or expired session”，
并掩盖真正的登录恢复失败。

## 当前状态机

| 场景 | 允许的动作 | 必须禁止的动作 |
| --- | --- | --- |
| GET 首次 401，且已有并发请求换出新 token | 只用新 token、当前会话代际重试一次 | 继续使用旧 token；清理并发请求刚换出的 token |
| GET 重新登录后再次 401，token 与会话代际均未变化 | 清理这个确定失效的 token，并把会话标记为 signed out | 保留失效 token，让后续页面反复重试 |
| GET 重试期间发生新的账号切换 | 抛出当前错误，保留更新后的会话 | 清理新账号 token |
| PUT/POST/支付命令收到 401 | 不自动重放；仅在没有更新会话时清理旧 token | 用新账号重放旧请求体或幂等键 |
| 依赖、网络或 Provider 非 401 失败 | 保留会话事实，展示稳定错误码 | 把临时故障误判成退出登录或空列表 |

核心清理条件是“当前会话代际仍等于请求代际，且当前 token 仍等于请求 token”。
这两个条件缺一不可：前者防止跨账号误删，后者防止并发登录覆盖后误删新凭证。

## 实现位置和注释边界

- `apps/miniprogram/src/services/api-client.ts` 的 `requestAfterSessionRecovery` 负责二次读取失败后的精确清理；
- `requestWithSession` 仍只对 GET 允许一次受控恢复，写入、患者同步和支付命令保持禁止自动重放；
- 页面层继续通过 `session-service.ts` 消费验证状态，不直接读取 token 决定业务入口；
- 患者同步协调器继续按会话代际隔离 Promise，旧账号的异步患者快照不会交给新账号页面。
