## 2. 当前已确认的业务不变量

### 2.1 患者和会话边界

- 小程序只提交平台内部 `patientId`，不提交众阳 `patId`、卡号、身份证号、订单号或金额。
- 服务端先按当前登录用户解析 owner-scoped 的 `his-patient` 映射，再把 Provider 患者引用交给 adapter。
- 患者切换、刷新、费用状态切换和页面卸载都会使旧请求或旧卡片失去回写资格。
- 患者上下文未确认、会话代际变化或 owner 映射失效时，页面清空上一轮费用，不能把旧金额留在新患者页面。

### 2.2 状态、时间和金额

- 公共状态只有 `unpaid` 和 `paid`；服务端分别固定查询 Provider `tradeStatus=1` 和 `tradeStatus=3`。
- Provider 缺失或错配状态、未知状态、重复费用引用、非法日期、窗口外账单和越过资源上限的结果整批失败，不过滤坏行伪装成功。
- 费用 `recordId` 的服务端哈希包含 Provider 患者引用作为不可见作用域，避免不同患者返回相同费用字段时产生相同公开引用；Provider 身份字段出现空白文本时按格式异常拒绝，不静默降级为缺失。
- 服务端以 `Asia/Shanghai` 计算最近 30 个自然日窗口，不能继承 systemd 进程时区。
- Provider 元金额通过十进制整数换算为分，小程序按安全整数拆分展示，不使用浮点 `toFixed` 重新计算。
- 公共响应只暴露展示字段：记录引用、状态、科室、医生、账单时间和金额；Provider 交易号、医保金额、患者原始字段不进入客户端。

### 2.3 列表和事件

- API 返回本次已校验的完整只读快照，小程序首批只渲染 10 条；“加载更多”只展开本地快照，不冒充 Provider 分页。
- 费用卡片使用当前渲染批次的 `viewKey` 回查，不能直接相信 WXML 事件携带的状态或索引。
- 页面保留旧端的“就诊人/当前院区”两行选择区域；就诊人进入独立选择页，当前院区是已核对的单院区展示配置。
- 旧端的选择框、底部“去支付”栏和外部“药去哪取”入口没有恢复：这些入口会携带订单、医保或外部咨询语义，当前没有冻结的新 contract。

## 3. 与旧端的差异处理

旧端 `hospital-app/src/pagesB/health/outpatient_pay.vue` 将 Provider 原始 `patId`、`outTradeOrderId`、医保字段和支付参数直接组织在页面，并同时承担支付调起、医保分流、外部问诊入口和费用查询。该结构不能原样迁移，原因是：

1. 页面提交 Provider 患者号和订单号会绕过新服务的 owner-scoped 归属边界；
2. `waitPayAmount || amount` 和浮点 `toFixed` 不能作为新支付金额事实；
3. 微信支付参数、医保授权和 6202/6301 结算属于不同状态机，不能由费用列表点击直接推导；
4. 外部电子问诊入口的域名、登录态和业务归属尚未在新项目 contract 中确认。

因此当前采用“结构保留、能力收窄”：保留患者/院区选择、待缴/已缴标签、费用卡片和原有橙色提示区域的视觉层级；费用卡片点击只提示迁移状态，不发起支付或写回。

## 4. 日志和错误边界

- 服务端使用现有日志包记录 `outpatient.payment.records.requested`、`loaded`、`failed` 事件，并保留平台 `traceId` 与经过校验的 Provider request ID。
- 日志不记录 Provider 原始响应、患者原始身份字段、订单号、金额明细或错误正文；失败原因使用固定低敏枚举。
- Provider 失败、依赖未配置、患者映射缺失和会话失效在页面侧使用不同的公共文案，不把内部错误原文展示给患者。
- “服务暂未配置”不能被降级为空列表；空列表只表示一次成功且完整的查询没有记录。
