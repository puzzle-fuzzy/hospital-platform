## 1. 复核范围与结论

本次沿着下面的只读链路复核了业务身份、时间窗口、状态筛选、列表数量和错误出口：

```text
微信会话
  -> 当前 owner
  -> owner-scoped 患者目录
  -> 显式选择且临床映射可用的 patientId
  -> 预约历史 / 爽约记录 / 门诊费用
  -> 服务端和小程序两层运行时 contract
  -> 当前会话代际下的页面渲染
```

结论：没有发现可以在不扩大 Provider contract 的前提下安全修复的生产逻辑缺口，因此本轮不修改业务实现、不新增兼容字段，也不打开预约写入、全部挂号、支付、医保、HIS、二维码或患者绑定。

## 2. 患者目录映射的关键判定

当前众阳 adapter 的顺序是：

1. 校验完整目录数组的大小和 `thirdPatientId` 唯一性；
2. 校验姓名、卡号和关系等最小展示字段；
3. 对每位患者调用 `patInfosFind`；
4. 校验返回 `patId` 必须是字符串，并核对姓名和卡片归属；
5. 校验不同目录患者不能共享同一个 HIS `patId`；
6. 整批通过后才交给快照事务。

领域层和持久化层仍保留 `clinicalAccess=unavailable`，因为以下场景确实需要保留“可展示但不可进入临床查询”的状态：

- 旧历史目录记录尚未完成医院档案映射；
- 完整快照明确缺少本次 `his-patient` 引用，需要清除旧引用并阻止预约、报告和费用查询；
- 未来其它已冻结的 gateway 明确提供“患者存在但临床档案暂不可用”的正式状态。

但当前众阳目录 adapter 不能把下面的情况直接转换成 `unavailable`：

- `patInfosFind` 超时、网络错误或 5xx；
- Provider 返回非成功 envelope；
- `data` 缺少 `patId` 或 `patId` 类型错误；
- 姓名、查询卡号与档案返回不一致；
- 多个目录患者共享同一 HIS `patId`。

这些情况无法从现有 Provider 材料中区分“没有绑定”“权限过滤”“暂时故障”和“返回被截断”。若降级为不可用患者，页面会给出看似完整的目录，且可能清理或保留错误的临床映射；当前整批 fail-closed 才是安全语义。除非取得 Provider 的成功/空结果/未绑定/权限拒绝/暂时失败样例和重试约定，否则不要放宽。

## 3. 预约历史与爽约不变量

- “我的挂号”使用中国标准时间过去 90 天到未来 90 天的日期窗口，未来预约不能因为复用报告或爽约的 past-only 查询而消失。
- “爽约记录”只查询过去 90 天，并且只筛选服务端已经归一化的 `missed`；客户端不能根据 Provider 数字状态、日期或空列表自行猜测爽约。
- 当前小程序只开放已确认的在线渠道；“全部挂号”所需的 `requestChannel=4` 仍缺少独立 Provider contract，不能把渠道 3 的结果复制成全部记录。
- 服务端和小程序均整批拒绝窗口外、重复标识、非法日期或未知状态，不能过滤坏行后伪装成完整成功。
- 页面本地“加载更多”只是展开同一次完整只读结果，不是 Provider 分页，也不改变 `total` 或业务状态。

## 4. 门诊费用不变量

- 查询只接受 `unpaid`/`paid`，状态由服务端固定校验，未知状态不能被旧网关解释成已缴费。
- 查询窗口固定为最近 30 个中国标准时间日；Provider 返回窗口外账单时整批失败，不能静默过滤。
- 金额保持整数分，页面只在展示边界转换为元文本；查询和展示阶段都不创建支付订单、不调用 `wx.requestPayment`、不修改费用状态。
- 费用 `recordId` 必须来自已确认的单据/就诊/费用标识；展示名称不能生成稳定业务身份，否则后续详情、支付和对账会绑定到不可定位的伪引用。

## 6. 后续准入顺序与停止条件

下一步仍按以下顺序推进：

1. 取得当前小程序候选的真实微信登录、患者同步和至少两位患者显式切换证据；
2. 在同一 `traceId/requestId` 链上验收预约历史、爽约和门诊费用只读页面；
3. 再验收普通资料读写及 409 并发冲突；
4. 补齐报告、病历、患者绑定/新增和二维码的正式 Provider contract 后分别实现；
5. 最后专项处理预约写入、取消、微信支付、医保授权、结算、退款和 HIS 回写。

任一环节出现患者归属不一致、临床 `patId` 复用、Provider 空/异常响应无法区分、页面结果无法与日志关联，立即停止该业务域，不添加兼容分支。
