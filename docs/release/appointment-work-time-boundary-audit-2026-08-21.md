# 预约记录时间字段边界审计（2026-08-21）

> 本记录只描述新项目的代码边界和旧项目的只读字段证据，不代表众阳真实接口、微信真机或预约写入已经验收。

## 1. 发现的问题

旧项目 `hospital-app/src/api/modules/appointment.ts` 将预约记录的 `workTime` 注释为 `HH:mm`，并额外提供 `groupStart`、`groupEnd` 作为时间段来源。旧端页面先按 `workTime` 的小时计算上午/下午，再在两个组时间都存在时拼接时间段。

新项目此前只检查 `workTime` 是非空文本。这样一个绕过 adapter、旧缓存或回放网关返回的 `上午`、完整日期时间或倒序时间段，仍可能进入服务端读模型；小程序随后会对错误文本做时段推导。

## 2. 已完成的边界

- 公共 contract 新增预约时间格式：`HH:mm` 或 `HH:mm-HH:mm`。
- 时间小时限制为 `00-23`，分钟限制为 `00-59`。
- 时间段结束时间不能早于开始时间。
- 缺少 `workTime` 仍然合法，因为历史记录可能没有可展示时间。
- domain 重新投影预约记录时执行同一运行时校验，违反时以 `work-time-invalid` 整批拒绝，不能过滤坏行后伪装成完整列表。
- 小程序收到列表后再次执行同一格式校验，防御代理、旧缓存和回放数据绕过服务端 contract。
- `groupStart`/`groupEnd` 仍只能在 adapter 内归一化为公开时间文本；本次没有修改另一会话正在维护的众阳自动化文件。

## 3. 为什么不接受任意文本

`workTime` 不是备注字段，而是患者用于判断就诊时段的业务事实。将未知文本保留到页面会产生两个问题：

1. 页面可能把无法解析的时间错误显示为“晚上”；
2. 完整日期时间或控制范围外的时间无法与查询日期和旧端布局保持一致。

当前只接受已经被旧端字段定义和现有新端页面消费逻辑共同证明的格式。若 Provider 后续确认新的时间格式，应先补充真实样例、字段语义和迁移测试，再扩展 contract。
