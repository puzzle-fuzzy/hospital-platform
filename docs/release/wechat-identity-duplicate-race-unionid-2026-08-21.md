# 微信身份重复键竞争与 unionId 补全（2026-08-21）

## 结论

本轮审计发现一个真实的 MySQL 并发边界：两个微信登录同时首次创建同一个
`providerSubject` 时，先到请求可能先插入一个暂时没有 `unionId` 的身份行；后到请求
虽然已经从微信返回了 `unionId`，但它的 `INSERT` 会收到重复键错误。旧实现读取胜出行后
直接返回，可能让本次会话缺少已经可用的 `unionId`，随后患者目录同步错误返回
`patient-directory-identity` 未配置。

现在重复键分支与普通已存在分支共用同一个补全流程：

1. 只在数据库 `union_id IS NULL` 时条件更新；
2. 更新成功时返回本次确实写入的身份；
3. 更新未抢到时重新读取同一 `user_id` 的权威行；
4. 永远不覆盖已经绑定的 `unionId`，也不把候选值写入日志或响应。

这只是身份持久化并发修正，不代表微信真实授权、众阳患者目录或真机验收已经完成。

## 验证

- persistence 新增重复键竞争回归测试，覆盖“重复键 → 胜出空 unionId → 条件补全 → 权威回读”；
- 旧 Python 服务、线上配置、MySQL 数据和 Redis 均未修改；
- 真实 MySQL 双会话并发仍需在不影响旧服务的隔离窗口验证。

## 后续边界

如果真实数据库中已经存在同一 `providerSubject` 对应多个 `unionId` 的脏数据，代码不会自动
覆盖或合并；应先人工核对微信主体和身份归属，再通过受控数据修复流程处理。这个保护是故意
保守的，因为错误合并会把患者目录、报告和费用请求带到错误的 Provider 身份。
