# 新旧服务生产网络边界审计（2026-08-20）

## 1. 审计范围与结论

本次通过 SSH 做只读检查，未修改旧 Python 服务、未重启任何服务、未修改防火墙、未执行数据库写入。

当前最重要的基础设施结论是：新 API 与旧 Python 服务都从内网主机 `192.168.112.172` 访问
阿里云主机 `8.130.127.184` 上的 MySQL/Redis 公网监听端口。该拓扑目前能工作，但不符合生产环境
应有的最小暴露面，且会让数据库连接经过公网地址、NAT 或云侧策略，增加连接瞬断和排障复杂度。

这可以解释为什么本次患者目录读取出现了 `PROTOCOL_CONNECTION_LOST` 的风险背景，但当前证据还不能
把它定性为唯一根因；必须再对照阿里云 MySQL、云网络和连接空闲超时日志。

### 2.1 WireGuard 私网路径已验证

两台服务器已有 WireGuard：内网应用主机为 `10.0.0.3`，阿里云主机为 `10.0.0.1`，双方握手正常。
在新 API 所在主机上，使用当前新 API 运行时配置做了不写入的连接验证：

- `10.0.0.1:3306` 的真实 `SELECT 1` 成功；
- `10.0.0.1:6379` 的真实 `PING` 成功。

因此“新 API 改走 WireGuard 私网”具备实际连通性，不需要引入 SSH 隧道。随后尝试只切换新 API 的
两条连接配置时，服务器返回 `systemctl restart ...: Interactive authentication required`；脚本已自动
回滚 env，临时备份也已删除。当前线上仍是原公网连接配置，新 API 进程和旧 Python 服务均未受影响。

文档只保留端点、监听和状态等维护所需信息，不记录密码、连接串、access token、openid、患者标识、SQL
或第三方报文。

## 3. 为什么现在不能直接改端口或防火墙

1. 旧 Python 服务已经依赖同一公网端点；直接改 `bind-address`、关闭 3306/6379 或清空放行规则，可能让
   旧服务同时失去数据库/Redis连接，违反“旧服务持续可用”的约束。
2. 仅把新 API 改成 `127.0.0.1` 也不成立：MySQL/Redis 实际运行在阿里云主机，内网主机本地并没有同一份
   服务；如果改成临时 SSH 转发，还必须处理 systemd 生命周期、断线重连、端口冲突和旧服务共存。
3. 仅在小程序侧无限重试不能修复网络边界，反而会放大数据库连接压力；当前服务对幂等读的有限恢复和 503
   fail-closed 行为应保持不变。

## 4. 无停机收敛方案

### 阶段 A：先确认归属，不改线上流量

- 由数据库/云主机负责人确认 MySQL、Redis 是否确实只服务这两套应用，以及阿里云安全组、云防火墙、MySQL
  `max_connections`/空闲超时、Redis ACL 和审计日志的当前配置。
- 在新旧服务主机分别记录当前连接数、目标端点和 readiness；把下一次
  `PROTOCOL_CONNECTION_LOST` 与 MySQL/网络侧时间戳对齐。
- 确认是否存在可用的 VPC/专有网络地址或安全组内网地址。没有确认前，不猜测替代 IP。

### 阶段 B：先为新 API 建立可回滚的私网路径

- 优先使用云厂商 VPC/私网地址或专用安全组，让新 API 先通过私网连接数据库和 Redis；保留旧 Python 的公网
  路径不动。
- 使用独立的 `api-v2` 环境变量文件和 systemd drop-in，先只改变新 API 的连接目标；旧服务配置不改。
- 当前 SSH 用户没有 systemd 重启授权；正式切换时需要具备 systemd 管理权限的维护窗口执行一次新 API 重启，
  或由管理员代执行，不应通过强杀进程绕过权限边界。
- 正式切换使用仓库内的
  `tools/production/switch-api-persistence-to-wireguard.sh apply`；脚本会保护 env 路径和旧端口、保留 600
  回滚副本，并在 readiness 或私网连接校验失败时只回滚新 API。需要撤销时使用同一脚本的 `rollback` 参数。
- 在切换前后依次验证 `health/live`、`health/ready`、微信登录、患者目录只读和 Redis 会话恢复，并观察足够
  时间窗口；任何依赖异常都回滚新 API 的连接目标，不碰旧服务。

### 阶段 C：确认新 API 稳定后再收紧公网暴露

- 在确认旧服务也具备私网迁移方案、且有维护窗口和回滚命令后，才把 MySQL/Redis 的公网暴露收敛为云安全组
  allowlist；最终目标是只允许应用私网源地址，禁止任意公网访问。
- 防火墙规则必须先以“新增明确允许规则 → 观察 → 再收窄默认策略”的顺序进行，并保留旧服务端到端验收证据。
- 不能只用端口探测作为完成证据；必须同时有旧服务业务健康、新 API readiness、Redis session、数据库查询和
  公网 HTTPS API 的结果。

## 5. 当前业务验收影响

- 16:24 的患者目录 503 已有 `PROTOCOL_CONNECTION_LOST` 低敏日志证据；16:58 后 readiness 恢复。
- 新 API 当前不会把数据库故障降级为空患者列表，也不会自动重放患者同步写入，这个边界正确。
- 在网络边界和瞬态稳定性完成观察前，患者选择、预约后续写入、报告、门诊缴费、支付和医保继续按停止条件处理；
  支付/医保仍放到最后专项验收。

## 6. 后续执行顺序

1. 先取得云网络/数据库配置的只读事实和日志时间关联。
2. 设计新 API 独立私网连接配置并做预生产连通性验证。
3. 仅切换新 API，确认旧服务不变且两套服务均健康。
4. 观察数据库连接瞬态，再决定是否收紧公网 3306/6379。
5. 网络边界稳定后，恢复真机连接，继续患者选择、多患者切换和只读业务验收。
