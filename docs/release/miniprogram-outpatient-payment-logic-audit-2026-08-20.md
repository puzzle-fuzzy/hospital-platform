# 门诊费用只读业务逻辑审计（2026-08-20）

## 结论

本次审计确认新端门诊费用仍处于“只读查询”阶段，未打开微信支付、医保授权、支付通知、退费、结算查单或 HIS
写回。审计发现并修正了一个金额边界问题：Provider 返回的元字符串不能通过 JavaScript 浮点乘法转换为分，
小程序也不能通过 `toFixed` 重新计算金额。现在服务端 adapter 使用十进制 `BigInt` 精确计算分值，客户端使用整数
拆分展示，超过 `Number.MAX_SAFE_INTEGER` 的分值整批 fail-closed。

本次没有修改旧 Python 服务、旧端口、旧数据库数据或 Redis 数据，也没有部署线上新 API/小程序运行包；本地 `dist/`
已在提交后重新构建并通过运行包门禁。当前小程序候选以发布基线指定的 `39e2caa` 为准，旧候选只保留作历史追溯。

## 已核对的不变量

### 1. 患者归属

- API 只接受新服务内部 `patientId`，不接受 Provider `patId`、卡号或金额作为客户端输入。
- service 先按当前 Bearer 用户查找 owner-scoped 的 `his-patient` 映射，再把 Provider 患者引用交给众阳 adapter。
- 映射不存在、引用为空或越界时，在 Provider 请求前失败；页面清除上一轮患者卡片和费用列表，不保留过期金额。

### 2. 查询状态与日期

- 公共状态只有 `unpaid` 与 `paid`，Provider 查询分别固定为 `tradeStatus=1` 与 `tradeStatus=3`。
- Provider 返回的 `tradeStatus` 缺失或与本次查询不一致时，整批拒绝；`2/4/5/9` 不会被猜测成已支付。
- 服务端按 `Asia/Shanghai` 计算最近 30 个自然日窗口，不能受 systemd 进程时区变化影响。
- 账单时间严格要求 `YYYY-MM-DD HH:mm:ss` 且必须是真实日历值；客户端收到后再次校验日期和状态。

### 3. 金额

- Provider 的 `amount` 是唯一确认金额来源；旧端候选字段 `waitPayAmount` 不参与计算。
- `12.3`、`12.30` 等最多两位小数的元字符串先用 `BigInt` 精确换算为分，不经过浮点乘法。
- 缺失、负数、非十进制文本和超过 `Number.MAX_SAFE_INTEGER` 分的金额直接拒绝，不能降级为 0 元。
- 小程序以元整数和余分拼接金额标签，例如 `1234` 显示为 `¥12.34`，不再通过浮点 `toFixed` 舍入。

### 4. 页面并发与列表成本

- 页面读取前先确认当前会话和当前就诊人；患者切换、标签切换或页面卸载后，旧请求不能回写新页面。
- “待缴费/已缴费”标签把点击状态作为本次请求快照传入，避免异步 `setData` 尚未完成时查询旧状态。
- API 结果完整保存在当前只读批次中，首屏只渲染 10 条，通过“加载更多”增加本地可见项；这不是 Provider 分页，
  不能据此推导费用总数或支付状态。

## 仍然关闭的门禁

- 当前没有真实 Provider 非空费用样例、真实微信会话三层证据或真机页面验收，因此不能宣称门诊费用迁移完成。
- `wx.requestPayment`、微信支付商户签名、医保授权、6202/6301 结算状态、支付通知幂等、退款和 HIS 写回必须分别建立
  独立 contract，并经过金额、订单状态、重试和审计日志验收后才能开放。
- 旧候选二维码和开发者工具旧增量缓存不能作为当前候选证据；真机验收必须重新编译当前 `dist/`，并先核对
  `dist/build-info.json.sourceRevision=39e2caac27ec4bf569f5debc8edb47947bc398d2`。
