# MySQL / Redis 备份、恢复与 RPO/RTO 策略

更新时间：2026-08-31

## 1. 文档边界

本文固定新平台切换前必须具备的恢复策略和证据格式，不代表当前服务器已经完成备份配置或恢复演练。线上执行必须由有权限的运维人员在受控窗口完成，并记录真实命令输出、时间、实例标识和审计单号；不得把凭据、患者数据或完整连接串写入仓库。

## 2. 数据分级与恢复原则

| 数据 | 存储 | 恢复原则 | 不能做的事 |
| --- | --- | --- | --- |
| 用户、患者关系、普通资料、报告引用、支付订单、预支付、通知和 outbox | MySQL | 以数据库备份和 binlog/PITR 为最终恢复事实；恢复后必须先做 schema probe、数量/关系校验和人工放行 | 不能用 Redis 快照或应用日志重建订单、患者关系或支付事实 |
| 微信会话 | Redis | 允许过期或丢失；用户重新登录建立新会话 | 不能把旧 token、JWT 或 Redis key 当作账户连续性迁移方案 |
| 未来新增的 Redis 业务数据 | Redis | 在引入前单独登记数据分类、持久化方式、RPO/RTO 和恢复演练 | 不能因为“Redis 可重建”就默认所有 key 都可丢失 |
| 审计日志和告警记录 | 日志平台/归档存储 | 保留低敏检索字段，按合规保留期归档并验证可查询 | 不能用包含身份证、卡号、token 或 Provider 原文的日志作备份 |

## 3. MySQL 生产最低要求

正式切换前，生产运维记录必须至少包含以下事实：

1. 周期性全量备份已启用，备份加密、异地或跨故障域保存，并有明确保留周期。
2. binlog 已启用并持续归档；归档链可以覆盖从最近一次全量备份到恢复目标时间点的连续区间。
3. 备份账号采用最小权限，备份文件和密钥不进入 Git、应用日志、工单正文或小程序包。
4. 每次备份记录开始/结束时间、实例标识、备份类型、文件校验和、大小、保留截止时间和失败告警。
5. 至少恢复一份脱离生产的隔离实例，执行目标 migration head、schema probe、关键表数量、外键/唯一键、outbox 状态和支付订单状态抽样核对。
6. 恢复验证完成前，不能把 `PERSISTENCE_SCHEMA_READY` 打开，也不能让候选 API/Worker 连接恢复实例处理业务。

## 4. PITR 恢复流程

```text
发现故障/误操作
  -> 冻结受影响写入和发布切换
  -> 选择最近可用全量备份与目标时间点
  -> 在隔离实例恢复并校验备份/ binlog 连续性
  -> 运行 schema probe、关键表数量和关系校验
  -> 由数据负责人核对患者/订单/outbox 抽样
  -> 记录 RPO/RTO 实测值并审批是否切换
  -> 受控切换应用连接
  -> readiness 连续采样、日志/告警观察和业务只读验收
```

恢复期间不得直接在生产库“边恢复边猜测修复”。如果无法证明目标时间点之后的支付、通知或 outbox 事实是否完整，相关订单必须冻结并进入人工复核，不能由前端成功提示或 HTTP 200 推导最终状态。

## 5. RPO/RTO 记录模板

每次生产验收或恢复演练都必须填写真实值，不能只填写“已配置”：

| 项目 | 目标值 | 实测值 | 证据 | 责任人 | 结果 |
| --- | --- | --- | --- | --- | --- |
| MySQL 数据 RPO | 由业务/运维负责人确认 | 待演练 | 备份与 binlog 时间线 | 待填写 | pending |
| MySQL 服务 RTO | 由业务/运维负责人确认 | 待演练 | 隔离恢复和切换时间线 | 待填写 | pending |
| 最近一次全量备份 | 按保留策略 | 待读取 | 备份系统记录 ID | 待填写 | pending |
| binlog 连续归档 | 连续 | 待验证 | 归档区间校验 | 待填写 | pending |
| Redis 会话恢复 | 可重新登录 | 待演练 | 新会话登录结果 | 待填写 | pending |
| 告警恢复通知 | 已配置渠道 | 待演练 | 通知/去重记录 | 待填写 | pending |

目标值必须由业务和运维负责人确认；本文不擅自替业务设定支付或医疗数据的可接受丢失窗口。

## 6. 与现有运行门禁的关系

- API readiness 通过只说明当前进程能够连接 database、Redis 和目标 schema，不说明备份可恢复。
- Worker 的 `not_configured`、`not_ready`、outbox `manual_review` 和支付查单 `manual_review` 必须继续触发人工处置，不得在恢复时清空记录来消除告警。
- 恢复后优先核对 `api-readiness-not-ready`、`outbox-stale-pending`、`payment-query-stale-pending`、`recovery-failure` 等规则；规则名称与阈值由 [`operational-alert-policy-2026-08-31.md`](operational-alert-policy-2026-08-31.md) 统一维护。
- 新旧服务共存时，恢复新库不能修改旧 Python 服务、旧数据库或旧 Redis；两套系统的恢复动作和切换审批必须分开记录。
