# 首页就诊人二维码字段与协议审计（2026-08-21）

## 1. 审计结论

本轮只读对比了旧端 `G:\\fuck\\hospital\\hospital-app\\src\\pages\\index\\index.vue` 与新端首页实现，未修改旧项目、旧服务、数据库、Redis，也没有触碰并行会话正在处理的众阳 adapter。

结论是：旧端实际生成的二维码内容是 `medicalCardNo`（医疗卡号/卡片号），不是 `patId`。旧端源码中的注释写着“只需要包含 patId 信息”，但运行代码读取的是 `patientInfo.medicalCardNo`，并把该值通过 URL 参数发送给外部 `api.qrserver.com` 生成图片。这个实现不能直接迁移到新服务。

新端继续保持二维码入口关闭是正确状态：当前只有 `patInfosFind` 返回的 `patId`、患者卡片字段和内部 opaque 患者身份证据，没有医院扫码设备所需的载荷格式、签名、受众、有效期、防重放、撤销、扫码回执或真机验收协议。不能因为 `patId` 可以用于预约等临床业务，就推断它可以作为二维码载荷。

## 2. 旧端实际行为

旧端首页存在“就诊人二维码”弹框，核心逻辑如下：

| 位置/行为 | 实际字段或地址 | 结论 |
| --- | --- | --- |
| 顶部卡片显示 | `patientInfo.patId` | 这是页面显示的身份字段，不等于二维码载荷 |
| 二维码数据读取 | `patientInfo.medicalCardNo` | 旧端真正编码的是医疗卡号 |
| 图片生成 | `https://api.qrserver.com/v1/create-qr-code/` | 卡号被交给外部第三方二维码服务 |
| 弹框下方显示 | `patientInfo.medicalCardNo` | 再次暴露卡号，且旧文案称其为 ID |
| 缺少的安全控制 | 签名、受众、TTL、防重放、撤销、扫码回执 | 不能作为医院业务扫码协议 |

因此，旧端注释“只需要包含 patId 信息”与实际代码不一致；这不是可以忽略的注释问题，而是会影响字段选型、安全评估和医院设备兼容性的事实差异。

## 3. 字段边界

### 3.1 `patId`

`patInfosFind.data.patId` 是医院/Provider 返回的临床患者引用。当前已知它可以参与预约、报告或门诊费用等 Provider 请求的患者映射，但这只能证明它在对应业务 contract 中的用途，不能证明它是扫码载荷。

新服务必须继续将它视为 Provider 侧敏感身份引用：不放入普通日志，不直接暴露到第三方二维码服务，不把它拼接成未经签名的可重放 URL。

### 3.2 `medicalCardNo` / `cardNo`

旧端二维码确实读取了 `medicalCardNo`；患者卡片列表中还存在 `cardNo`、`patCardNo` 等同类字段。它们是卡片/就诊介质标识，可能被医院扫码设备使用，但当前没有正式材料证明字段优先级、卡类型、扫码受众、是否需要前缀或是否需要加密签名。

卡号属于敏感业务标识。即使旧端曾经把它放进第三方二维码 URL，也不能据此复制该数据外发行为。

### 3.3 新端内部 `patientId`

新端内部 opaque `patientId` 只用于 owner 归属、患者选择、会话代际和 stale 判断。它不是 Provider 的 `patId`，也不是医院卡号；不得为了“先让二维码显示出来”而把三者互相替换。

## 4. 当前新端处理

新端 `apps/miniprogram/src/pages/index/index.ts` 的 `onPatientQr` 只在页面已有本轮确认患者时显示“二维码暂未开放”，否则提示先登录并选择就诊人。它不生成图片、不调用 `api.qrserver.com`、不拼接 `patId`/卡号，也不把敏感字段写入客户端日志。

现有小程序验收测试已锁定以下边界：

- 二维码入口必须依赖已确认的患者对象，不能只依赖缓存 ID；
- 页面明确显示二维码暂未开放；
- 运行包不包含 `api.qrserver.com`、`medicalCardNo` 等旧端外发路径；
- 首页展示不泄露身份证、手机号、姓名与卡片身份组合。

## 5. 正式开放前必须冻结的协议

只有在医院扫码端或 Provider 提供正式、可追溯的 contract 后，才可以进入二维码实现。至少需要取得并记录：

1. 载荷字段：是卡号、患者临床引用、一次性 token，还是服务端短期 opaque code；字段是否需要前缀、版本和医院标识。
2. 安全保护：签名/加密算法、密钥归属、密钥轮换、受众绑定、有效期、时钟偏差、重放检测和撤销策略。
3. 业务归属：扫码设备如何确认医院、院区、窗口或工作人员，如何避免把一个患者码用于另一个 owner 或医院。
4. 交互协议：扫码后是设备轮询、服务端回执、WebSocket 还是一次性确认；成功、已使用、过期、撤销、无权限和重复扫码的错误语义。
5. 数据边界：小程序展示什么、日志如何脱敏、二维码服务是否必须内置生成、是否禁止第三方图片服务和外链。
6. 验收材料：脱敏的成功/失败/过期/重放样例、医院真实扫码设备验收、微信真机页面、HTTP traceId/requestId 与服务端低敏日志三层配对，以及可回滚开关。

缺任一项时，保持入口关闭，不添加兼容转发，不把 `patId` 或卡号直接编码成二维码，不修改旧服务来“借用”旧行为。

## 6. 下一步

当前二维码不进入实现队列。下一步应从众阳/医院设备侧获取二维码正式协议，并单独建立 provider intake、字段差异表和安全评审；协议冻结后再按 `contract → adapter → API → 小程序 → 测试 → 真机/设备验收` 顺序推进。预约、门诊费用和报告等已具备只读基础的业务继续按各自 contract 独立推进，不复用二维码字段。
