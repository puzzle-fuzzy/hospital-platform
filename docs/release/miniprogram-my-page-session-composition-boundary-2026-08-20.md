## 发现的问题

“我的”页面不是一次请求，而是按顺序组合三类事实：

1. `/me`：证明当前页面加载周期对应的 owner；
2. `/me/profile`：普通资料展示增强；
3. `/patients`：当前 owner 的就诊人目录和临床可用性。

原有 API 客户端已经能保护单个请求：如果请求完成前会话代际变化，旧响应不会交给调用方。但页面层仍可能遇到这样的时间线：

```text
/me 以账号 A 成功
  -> 个人资料请求期间账号切换为 B
  -> 资料错误被当作可降级增强并吞掉
  -> /patients 使用账号 B 成功
  -> 页面出现 A 的 owner 证明和 B 的患者目录混合快照
```

这不是普通网络错误，也不能用“当前仍有 token”判断安全；token 存在只说明设备上有凭证，不说明本次 `/me` 证明与后续目录属于同一会话代际。

## 本次规则

- `/me` 成功后重新记录当前会话代际。这样首次 GET 触发安全会话恢复时，恢复后的代际可以作为本轮起点。
- `/me/profile` 和 `/patients` 必须与该起点保持同一代际；代际变化时停止本轮组合，不继续启动或提交后续数据。
- 资料读取期间发生代际变化时，不能把错误降级为普通资料不可用后继续读取患者目录。
- 患者列表 Promise 完成后、`setData` 之前再次检查代际，防止在响应完成和页面回写之间发生账号切换。
- 会话组合失效只清理页面派生资料和患者数量，设置为“验证中”，不自动重放当前页面加载；用户下拉刷新后必须重新走完整 `/me → 资料 → 患者目录` 顺序。
- 只保存代际数字，不保存或记录 access token、openid、unionid、身份证号、医院卡号或 Provider 患者号。
