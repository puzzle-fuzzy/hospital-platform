# 患者医院档案映射冲突修正（2026-08-21）

## 结论

本次修正只涉及新项目 `hospital-platform` 的患者目录持久化边界，不修改旧 Python 服务、旧服务数据库数据、线上配置或 Provider 自动化获取代码。

复核发现 `hp_patient_provider_references` 同时约束了两件不同的事实：

- `(owner_user_id, patient_id, provider_name, reference_kind)`：同一内部患者在同一能力下只能有一条外部引用；
- `(owner_user_id, provider_name, reference_kind, provider_patient_id)`：同一用户、医院和用途下，一个外部患者号只能归属于一位内部患者。

原来的 `ON DUPLICATE KEY UPDATE` 无法区分这两类重复。当历史失效患者仍占用相同 HIS `patId` 时，新的目录同步可能把重复键静默吞掉，事务继续成功，但新患者没有对应的临床映射。这会让后续预约、报告或门诊费用查询得到“临床不可用”，却丢失了真正的数据冲突原因。

## 修正规则

1. 首次写入使用普通 `INSERT`，不再对两套唯一约束做无条件 upsert。
2. 发生重复键后，按当前内部患者的完整主键 `FOR UPDATE` 查询：
   - 当前主键存在且外部患者号相同：视为同一请求重放，保持幂等；
   - 当前主键存在但外部患者号不同：只更新当前患者的映射；若二级唯一约束再次冲突，则返回映射冲突；
   - 当前主键不存在：说明重复来自另一位患者，返回 `patient-directory-reference-conflict`，禁止合并或覆盖。
3. `patients.upsertFromDirectory` 使用事务包住患者主表和能力专用引用表，冲突时回滚整条单患者写入，避免留下“目录已更新、临床身份缺失”的半状态。
4. 内存仓储增加同样的外部身份索引，并在完整快照写入前使用副本预检；冲突不会因为测试实现没有数据库事务而留下部分快照。
5. API 返回 502 和固定中文文案；不向小程序暴露患者 ID、HIS `patId`、约束名称或 MySQL 原始错误。

## 验证证据

- persistence：92 pass / 0 fail，覆盖 MySQL 同一患者幂等更新、跨患者冲突回滚、连接申请瞬态错误，以及内存单条/完整快照冲突前的部分更新保护。
- API：201 pass / 0 fail，覆盖稳定错误码、公开文档和错误处理。
- 小程序：197 pass / 0 fail，覆盖错误码文案映射、运行包门禁和现有患者流程。
- 真实 MySQL 历史数据冲突、真实 Provider 患者同步、生产部署、微信真机和预约/报告/门诊费用业务仍未在本记录中宣称完成；必须在新候选部署后按三层证据重新验收。

## 后续动作

- 部署前在 staging/只读窗口核对是否存在同一 owner/provider/kind 下重复外部患者号，以及历史失效患者是否仍保留临床引用。
- 如果发现实际冲突，不直接删除旧映射或手工合并患者；先由业务确认两条档案的归属，再执行可审计的数据修复。
- 生产发布只切换新 API 服务，保持旧 Python `8001` 和旧路由不变；部署后观察映射冲突计数与患者同步失败日志。
