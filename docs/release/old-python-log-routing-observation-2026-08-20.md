## 公网入口与内网旧服务的边界复核

`test-hp.meiyi.pro` 当前解析到阿里云公网地址 `8.130.127.184`，而本次查看日志的旧服务位于
`192.168.112.172:8001`。从内网机向公网地址发送不带 Authorization、没有业务 body 的空 POST 时，入口
返回了 HTTP `401`，且内网旧服务的 6201 日志没有新增记录。这个结果只能证明该类请求在公网入口鉴权层
结束，不能推断带有效会话的 Apifox 请求也一定被拒绝；要确认具体请求是否被阿里云转发，仍需取得阿里云
Nginx/转发日志或在用户重试时同时观察两端。

因此，若内网旧服务没有出现某一次“已知带有效鉴权的 POST 6201”记录，应优先按以下顺序排查：

1. 公网入口是否收到 POST，以及入口返回的 HTTP 状态；
2. 阿里云转发是否把请求送到 `192.168.112.172:8001`；
3. 内网旧服务是否在 `info_2026-08-19.log`、`all.log` 或轮转后的 worker 文件中落日志；
4. 只有出现 `service.py:forward_6201` 后，才继续判断医保上游超时、验签或业务响应问题。

## 原因判断

旧项目的 `app/core/logger.py` 为 `all.log` 和 `error.log` 配置了自定义按时间轮转的文件 handler，
同时旧服务以 `--workers 4 --preload` 启动 Gunicorn。preload 会让 master 中已经打开的 handler
被 worker 继承；自定义 `doRollover()` 又会关闭、移动并重新打开文件。多进程在同一组 handler/文件
上轮转时，部分 worker 仍持有已移动或已删除 inode，导致文件名、打开的文件描述符和实际写入位置不一致。
本次 `/proc/<worker>/fd/12` 与 `/proc/<worker>/fd/13` 的 `(deleted)` 证据直接复现了这一点。

所以旧服务当前存在以下可观察现象：

- 同一次请求可能出现在 `all.log`、日期轮转文件或某个已被轮转但仍被 worker 持有的 `(deleted)` 文件中；
- `all.log` 不是旧多 worker 服务的完整日志索引；
- `error.log` 也不能替代完整请求日志，只能作为错误级别的一部分观察来源；
- 日志文件中出现超时，只能证明某次外部请求超时，不能单独证明医保业务最终状态。

## 新服务的边界

新 Elysia 服务不依赖旧项目的 `all.log` 查业务链路。新服务使用 Pino 输出结构化 JSON 日志，
由 `requestId`、`traceId`、业务事件和低敏内部引用关联请求；生产环境通过 systemd/journald 统一收集，
再使用与 release 一致的聚合工具生成安全摘要。新增业务必须同时核对 HTTP 响应、页面结果、业务持久化状态
和同一时间窗口的结构化日志，不能用单个日志文件或单个 200 响应替代业务验收。

## 旧服务后续建议

旧服务日志治理应作为独立维护窗口处理，不与新业务迁移混做。推荐后续按以下顺序评估：

1. 让 Gunicorn worker 输出 JSON 或文本日志到 stdout/stderr，由 systemd/journald 负责收集和轮转；
2. 若必须保留文件日志，改为单一日志写入进程或 `QueueHandler`/`QueueListener`，禁止多个 worker 独立轮转同一文件；
3. 在变更前保留旧 `8001` 的健康检查、`6201/6202` 低敏计数和公网回归证据；
4. 变更后验证旧服务仍可用，再逐步迁移日志查询脚本，不把旧日志文件直接接入新服务的业务审计链。

在没有单独变更窗口和回滚证据前，不应为了让 `all.log` 看起来完整而重启或改动旧服务。
