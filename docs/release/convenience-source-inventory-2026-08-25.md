## 为什么不能直接迁移

旧便民表使用旧平台数值 `user_id`、`patient_id`、`pat_id`、`visit_record_id` 和
`doctor_id`，部分表还保存患者姓名、科室、医护姓名、问卷答案或头像 URL。它们与新端
opaque `userId`、`patientId`、`doctorRef` 并非同一身份体系；直接复制会产生跨账号可读、
旧患者号泄露、历史记录错误归属和医疗内容未经审核展示等风险。

旧端还有以下不能照搬的语义：

- 风险评估、入院预问诊和出院随访可能按同一患者覆盖旧记录，缺少版本、任务、生效和撤回事实；
- “我的医生”保存的是客户端快照，不能证明医生当前在职、科室有效或头像 URL 仍安全；
- 表扬信和电子锦旗有公开展示字段，必须单独确认脱敏、审核、撤回和文件安全；
- 旧接口存在用 GET 执行删除/取消关注等命令语义，新端不能复用。

## 广度优先后的正确顺序

1. 先建立旧身份到新 owner/patient/doctor 的只读映射报告，映射失败的历史行标为
   `legacy_unresolved`，不进入患者端；
2. 为每个业务定义独立的只读 read model 和历史记录展示策略，不共用一个宽泛的
   `convenience` 响应；
3. 问卷类先完成题目/结果版本、适用人群、免责声明、审核人和撤回语义；
4. 医生关系先取得受控医生目录，再实现 owner-scoped 查询；
5. 表扬信/锦旗先完成审核、公开范围、图片/文件安全和撤回，再考虑历史数据导入；
6. 只有只读历史展示在 staging 通过 owner 隔离、脱敏和空/拒绝/暂时失败验收后，才替换对应
   状态页；提交、覆盖、取消、公开和删除写入继续单独排在后面。

本轮没有增加便民路由或导入旧正文，避免“数据库有数据”被误判为业务已迁移。
