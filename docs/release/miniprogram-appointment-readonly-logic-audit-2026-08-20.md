# 预约历史与爽约只读逻辑审计（2026-08-20）

## 当前结论

当前服务端 `0e360d3` 与发布基线指定的小程序候选 `6252ea4` 的“我的挂号/爽约记录”只读逻辑通过本轮代码与测试复核，未发现需要放宽边界或修改业务语义的问题。本轮没有调用真实 Provider、没有写入数据库/Redis、没有打开预约写入、支付、医保或 HIS。

## 已确认的不变量

| 业务边界 | 当前正确行为 |
| --- | --- |
| 患者归属 | API 只接受平台内部 `patientId`，服务端再按 owner + `his-patient` 映射取得 Provider 引用；小程序不提交 HIS `patId`。 |
| 我的挂号窗口 | 中国标准时间当前日前后各 90 天，包含过去记录和未来预约。 |
| 爽约窗口 | 只查询过去 90 天，并且只筛选服务端已归一化的 `status="missed"`。 |
| 在线标签 | 固定已确认的 Provider `requestChannel=3`，只排除明确 `cancelled`；未知状态不猜测。 |
| 全部挂号 | 需要独立 `requestChannel=4` 合同，目前标签保留视觉位置但点击只提示迁移中，不复用渠道 3 结果。 |
| 上游响应 | HTTP 200 但业务失败包络、非法日期、未知状态、越界记录、重复预约号或超出资源上限均整批 fail-closed。 |
| 页面并发 | 患者切换/刷新时清空旧记录；页面请求代际、患者选择和渲染 `viewKey` 同时有效后才允许回写。 |
| 大结果集 | 服务端返回完整已验证只读结果，小程序首批渲染 10 条，“加载更多”只展开本次已取得的数据，不伪装 Provider 分页。 |
| 未迁移入口 | 详情、取消/退号、预问诊、预约写入和费用支付均给出明确迁移/关闭状态，不拼接索引或猜测业务引用。 |

重点覆盖：

- 预约历史和爽约的中国标准时间窗口；
- owner-scoped 患者映射和 HIS 引用不混用；
- Provider 业务失败不能降级为空列表；
- 记录状态、日期、展示字段和总数的一致性；
- 旧请求/旧患者事件不能回写新页面；
- 双标签不伪造“全部渠道”；
- 大列表本地渲染窗口不改变业务总数。

## 中文注释与停止条件

服务端 `apps/api/src/modules/appointments/service.ts` 已解释日期窗口、患者映射、Provider 二次校验、快照持久化与失败日志为什么必须分层；小程序 `appointment-records.ts` 和 `missed-appointments.ts` 已解释会话证明、患者卡片与记录的原子回写、状态派生和本地渲染批次。未来新增预约写入时，不能直接复用这些只读 service 或排班快照，必须另建 command contract、幂等、最终状态和支付/医保边界。

当前开发者工具二维码还没有产生新的手机会话，因此以下仍未完成：

3. 真机“我的挂号/爽约记录”页面与 HTTP `traceId/requestId` 的同链证据；
4. `requestChannel=4` 全部挂号的正式文档、字段/状态/排序/分页和失败语义。

在这些证据到齐前，不能以模拟器、历史 release、单个 HTTP 200 或空列表宣称预约业务真实验收完成。
