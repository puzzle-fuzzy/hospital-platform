# Medical Insurance Contract v1

本文档把旧项目的医保移动支付中转协议收敛成新仓库可以审计的 contract。
它不是医保平台已接通、已授权或已完成真实结算的证明；是否发起真实调用仍由部署环境的
`MEDICAL_INSURANCE_READY`、全部密钥、HTTPS 上游和 schema gate 同时决定。

## 已确认的旧链路

旧项目 `G:\fuck\hospital\app\api\v1\module_common\mbs_fsi\service.py` 中，
6201、6202、6203、6301、6401 使用移动支付中心专用 path，并将业务 payload 直接放在
`data` 节点；它们不应错误地套用通用 FSI 的 `infno/msgid/input.data` 外层。旧项目的
中转服务还可能重复包裹 `data`、`output` 或 `body`，新 contract 只允许展开有限层数，
避免无限递归吞掉异常响应。

| infno | 新仓库 path 常量 | 业务含义 | 关键权威结果 |
| --- | --- | --- | --- |
| 6201 | `/org/local/api/hos/uldFeeInfo` | 费用明细上传 | `payOrdId`、`payToken` |
| 6202 | `/org/local/api/hos/pay_order` | 医保支付下单 | `feeSumamt`、`ownPayAmt`、`psnAcctPay`、`fundPay` |
| 6301 | `/org/local/api/hos/query_order_info` | 结算结果查询 | 结算状态和同一组金额 |
| 6203 | `/org/local/api/hos/refund_Order` | 医保退费 | `refStatus` |
| 6401 | `/org/local/api/hos/revoke_order` | 费用上传撤销 | `success=true` 与 message |

## 金额和订单不变量

- provider 的元金额只能以字符串解析为整数分，禁止 JavaScript 浮点四舍五入；
- 6201 明细 `detItemFeeSumamt` 必须合计到 `medfeeSumamt`；如果三项费用分解同时存在，也必须再次守恒；
- 6202/6301 必须满足 `ownPayAmt + psnAcctPay + fundPay = feeSumamt`，并且返回 `payOrdId` 必须匹配请求/已落库订单；
- 6203 的 `ALL` 必须逐项等于原始结算，`CASH` 只能退现金，`HI` 不能带现金，任何分项都不能超过原始结算；
- `payToken` 是 provider 凭证，只能在 adapter 到持久化 mapper 的窄边界内使用，落库时只能保存 hash，日志、outbox 和小程序响应禁止出现原文；
- 6202/6301 的金额是服务端事实来源，客户端提交的金额不能覆盖已经落库的结算结果。

## 密码边界

旧项目使用 SM2withSM3 签名、SM4-ECB/PKCS7 加密以及由 `appId/appSecret` 派生的 SM4 key，
部分签名实现通过 JPype/BouncyCastle 运行。2026-09-02 已从正式规范
[`迁移/医保FSI接口规范整理-2026-09-02.md`](迁移/医保FSI接口规范整理-2026-09-02.md)
（来源 documentId `shanxi-medical-insurance-spec-v1.3.35-20260528`）确认：SM4 为 ECB/PKCS7、
签名拼接为参数 ASCII 升序 `k=v&…&key=appSecret`（`signData`/`encData` 不参与）、SM4 密钥由
`appId` 加密 `appSecret` 派生（取前 32 位、底层用前 16 位）、移动支付 `version=2.0.0`。
新仓库当前只提交了纯 contract 和金额验证：

1. 仍需获取签名 golden vectors、SM2 userId、密钥编码格式和错误码表（协议版本与 SM4 padding 已由上述规范确认）；
2. 再选择经过验证的 Node/Bun crypto 实现或保留一个最小 sidecar，不在没有向量的情况下凭印象重写密码学；
3. crypto adapter 必须先验签再解密/映射，严格模式下验签失败不得放行；
4. 生产 adapter 接入前要做双向向量测试、脱敏审计日志、超时/重试/idempotency 和真实 staging 回放。

当前组合根已提供真实 `MedicalInsuranceGateway`：
`legacy-fsi-medical-insurance.ts` 负责授权解析、1101、众阳费用/编码前置查询以及
6201/6202/6301 的完整编排；`legacy-fsi-gateway.ts` 负责固定路由、严格 SM2/SM4
封套和响应验签。未满足配置或 schema gate 时仍注入 fail-closed gateway，不发送真实医保请求。

6301 查询的 0/1/2 等处理中状态可以没有金额；新 adapter 会保留订单号和状态，
由上层映射为等待确认，而不会用旧订单或客户端金额补齐一份“已结算”结果。

## 支付最终性约束

本轮最近日志进一步确认：`apply-pay-settle` 的 `settleStatus=1`、预下单
`payRecord.status=1` 和 6202 的 `ordStas=1` 都只是阶段性成功。新端将 FSI 状态
分类为 `processing`、`settlement_candidate`、`cancelled`、`failed` 或 `unknown`；
其中 3/4/5/6 只能进入后置编排候选，不能直接映射为 `paid`。

领域层只有在金额守恒、来源权威且收到 Yunhealth/HIS 的 `paid` 证据后，才允许把医保阶段
推进到 `insurance_settled` 或 `cash_pending`。这仍不等于业务订单 `completed`；后者还需要
现金支付（如有）和 HIS 回写。未确认、金额不一致或证据来源不足时统一进入
`awaiting_confirmation`。本约束的实现和测试见 [`docs/迁移/支付最终性微调-2026-09-02.md`](迁移/支付最终性微调-2026-09-02.md)。

## 日志边界

医保 adapter 只能记录 `traceId`、`providerRequestId`、`infno`、状态、耗时、重试次数、
订单内部 ID 和金额摘要。不得记录原始请求、`payToken`、身份证/姓名、签名原文、SM2/SM4
密钥、`encData` 或完整 provider 响应。具体输出仍统一走 Pino，遵循 [日志规范](日志规范.md)。

## 6201/6202 的服务端前置数据源（2026-09-03 依链路流向图补齐）

旧端实测链路揭示：启动医保下单编排前，以下四项数据必须由服务端取得并映射，
它们与 `appId/appSecret`、SM2/SM4 密钥同属硬前置，缺任何一项都不能调 6201：

| 前置 | 旧端来源 | 用途 |
| --- | --- | --- |
| 医保授权号 | 腾讯 `userQuery/50010828`（relay → wecity） | 6201/6202 的 `payAuthNo` |
| 参保信息 | FSI 1101（relay → 通用 FSI） | `psnNo`、`insutype`、真实 `insuplcAdmdvs`、可选 `ecToken` |
| 结算主单 | 众阳 2.6.65.1 `apply-pay-settle` | 费用明细的真实 `businessId` 与 `tradeOrderIdList` |
| HIS 费用明细 | 众阳 2.27.2.27 `out-insur-settle-infos`（gpsrmyy） | 6201 `feedetailList` 清单来源 |
| 医保科室码 | 众阳 2.1.9 `base-common/v1/depts` | 6201 `caty`；映射由服务端持有，不下发小程序 |
| 医保医师码 | 众阳 2.1.13 `base-common/v1/users` | 6201 医师编码 |
| 个账使用标志 | 众阳 2.6.33 `outpatient-child-payment-records` | 决定 6202 `acctUsedFlag` |

授权链路目标为腾讯医保测试中台（`mip-user-query` 经中转 forward → wecity），
该 relay 目标已在 `infra/生产链路拓扑.md` 登记。以上七项已加入
`tools/migration-boundary-catalog.mjs` 中 insurance gate 的 `requiredMaterials`。

实现约束：服务端从已绑定微信身份和已预约记录重新解析患者，不接受小程序提交的费用、
医保号、科室医保码、医师医保码或 `acctUsedFlag`；授权上下文和 6201 `payToken` 只进入
独立 AES-GCM 密文仓储，并按 owner、订单、用途和过期时间读取。6201 成功后必须拿到
真实 `mdtrtId` 才允许 6202；6202 的账户标志冻结到订单，6301 只复用已保存凭证查单。
