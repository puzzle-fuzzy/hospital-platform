# 旧仓库凭据撤销与轮换 Runbook

> 本文只规定处置顺序和验收证据，不包含、请求或复制任何密钥值。它适用于旧仓库曾跟踪环境文件、微信支付证书、医保/Provider 配置或小程序私有配置的情况。没有对应管理员批准时，不执行历史重写、证书吊销、旧服务重启或环境文件替换。

## 1. 触发条件与停止线

只要凭据文件曾进入远程历史、构建产物、聊天记录、日志、备份或不受控人员可读的目录，就按“可能已暴露”处理；不能因为当前文件已删除或新仓库 secret audit 通过，就把它降级为安全。

以下任一项未确认时，停止继续扩散或发布：

- 代码托管项目的可见性、fork、镜像、构建日志和访问审计没有负责人确认；
- 微信 AppSecret、微信支付 API 密钥/证书、医保或 Provider 凭据的持有者和有效期不明确；
- 旧 Python 服务与新 API 的配置归属、更新时间和回滚点没有登记；
- 轮换后的低风险验证无法证明旧值失效、新值生效且日志不泄露秘密。

## 2. 负责人和证据登记

在受限变更单中登记以下元数据，禁止登记秘密原文、完整连接串、token 或 PEM 内容：

| 责任方 | 必须确认 |
| --- | --- |
| 代码托管管理员 | 项目可见性、历史 refs、fork/镜像、访问日志和后续历史处置方案 |
| 微信小程序管理员 | AppID 所属环境、AppSecret 轮换时间、旧值失效证据 |
| 微信支付管理员 | API 密钥、商户证书、回调配置和旧证书失效证据 |
| 医保/Provider 管理员 | 凭据种类、授权范围、有效期、撤销和新值生效证据 |
| 旧服务负责人 | 旧 `.env` 更新、旧 Python 重启窗口、`8001` 连续可用证据 |
| 新平台负责人 | `shared/api.env` 更新、schema/config gate、API readiness 和回滚证据 |
| 安全负责人 | 最小权限、保留期限、审计记录和异常响应结论 |

每个凭据只记录一个不可逆的配置指纹或版本号，并绑定操作者、时间、环境和变更单；指纹不能由原始秘密直接打印到普通日志。

## 3. 撤销与轮换顺序

1. **冻结扩散**：暂停把旧环境文件、PEM、构建包和日志复制到新仓库、工单、聊天或临时目录；保留必要的只读审计摘要。
2. **先在平台侧撤销/轮换**：由对应管理员在官方控制台或 Provider 管理端创建新凭据并使旧凭据失效。AppID 不是秘密，但 AppSecret、微信支付 API 密钥、商户证书私钥、医保/Provider token 必须分别处理。
3. **更新旧服务受控配置**：通过服务器既有秘密通道更新旧 Python 的环境配置，不把值放入 shell 历史、systemd 命令行、Git 或日志；只在批准窗口重启旧服务，并核对旧 `8001` 和旧业务负责人要求的健康检查。
4. **更新新服务受控配置**：更新 `/home/ps/code/hospital-platform/shared/api.env` 或正式秘密管理系统，保持文件权限 `600`；重新执行配置 preflight 和 readiness，不自动打开支付、医保、退款或 HIS Worker。
5. **清理代码托管暴露面**：先保存平台侧审计证据，再由管理员决定项目改为私有、撤销 fork/镜像访问、清理构建日志和是否按代码托管平台流程重写历史。历史重写不能替代凭据轮换，也不能由应用发布人员单独执行。

不得使用 `git reset --hard`、删除整个仓库、`FLUSHDB`、清空日志或直接覆盖旧 release 来“清理”暴露面；这些动作会破坏回滚和审计事实。

## 4. 轮换后验收

每类凭据分别形成以下低敏证据：

- 旧值被平台标记为 revoked/expired，且新值的版本或指纹与环境一致；
- 旧服务和新服务启动日志只显示环境名、配置 gate 和 readiness，不显示秘密；
- 微信登录、微信支付、医保或 Provider 验收只使用批准的最小测试主体，保存 request/trace 关联和结果摘要，不保存授权码、token、身份证、卡号或原始报文；
- 新服务 `database/redis/schema` ready，旧 Python `8001` 仍监听；
- 失败时只回滚服务版本或配置版本，不回滚已撤销的秘密，不继续使用旧凭据；
- 变更单包含操作者、时间、配置指纹、验证结果、异常和后续清理责任人。
