# 医保 + 微信 APIv3 退费流程

更新时间：2026-09-21

## 1. 当前真实支付模型

当前项目使用的是“医保支付 + 微信 APIv3”两条真实支付腿的聚合模型：

1. 医保订单的收款侧可按现有微信 APIv3 `/v3/med-ins/orders` Provider 路由创建/查询；这里的“医保混合”只是收款产品名称，平台账本和退费仍按医保腿、微信现金腿分别保存和确认，不代表退费时存在一个由 HIS 代替微信处理的“V2 医保混合退款”接口。
2. 医保金额通过医保 6203 退费。
3. 微信自费金额使用同一笔 APIv3 微信自费 `out_trade_no`，通过微信 APIv3 普通退款 `POST /v3/refund/domestic/refunds` 原路退回。
4. 平台新增一条聚合退费记录，将 6203 和微信退款的状态、请求号、退款单号关联起来；两条外部交易仍然分别以各自 provider 的真实身份存在。

因此，当前实现不是“医保自费混合支付退款由 HIS 用微信 V2 一次完成”，也不依赖 HIS 提供微信 APIv3 医保混合退款。HIS 侧的旧微信 V2 兼容代码不参与本退费主链路。

## 2. 外部接口边界

医保 6203 的固定请求地址来自现有 adapter 合同：

```text
POST /org/local/api/hos/refund_Order
```

代码位置：`packages/adapters/src/legacy-fsi-contract.ts` 的 `LEGACY_FSI_ROUTES["6203"]`。适配器会校验 `payOrdId`、`appRefdSn`、`refdType`、`appRefdTime`、四项金额守恒，以及 `ecToken/payAuthNo` 二选一；响应只接受 `SUCC`、`FAIL`、`EXP`。

微信 APIv3 普通退款的固定请求地址来自现有 adapter：

```text
POST /v3/refund/domestic/refunds
GET  /v3/refund/domestic/refunds/{out_refund_no}
```

代码位置：`packages/adapters/src/wechat-pay.ts` 的 `REFUND_PATH` 和 `REFUND_QUERY_PATH_PREFIX`。退款请求使用原订单的 `out_trade_no`，平台生成稳定的 `out_refund_no` 并以同一退款单号查单/幂等。

当前仓库没有使用 `/v3/med-ins/refunds/notify`，也没有把它注册成回调地址。当前退费闭环依赖 6203 返回结果和微信 APIv3 退款请求/查单结果；微信回调仍只按现有支付通知模块处理。后续如果 Provider 合同明确要求新的医保退款通知接口，必须作为独立合同补充验收，不能从当前代码推导。

## 3. 平台接口

```text
POST /payments/medical-insurance/orders/{orderId}/refund
```

请求头必须包含已认证会话和 `idempotency-key`。请求体：

```json
{
  "refundType": "ALL",
  "reason": "患者申请退费"
}
```

金额规则：

- `ALL`：不提交金额，按订单原始四项金额全额退费。
- `CASH`：只提交 `refundFen`，只能退原微信自费金额。
- `HI`：只提交 `personalAccountRefundFen` 和/或 `fundRefundFen`，不能带现金金额。

客户端不能提交 `payOrdId`、`out_trade_no`、`payAuthNo`、`ecToken`、6203 原始报文或微信商户退款号；这些字段全部从服务端订单、加密授权上下文和服务端生成的退款号中取得。

Admin 使用同源代理 `/api/refunds/medical-insurance`，后端受独立 `X-Admin-Refund-Token` 保护。Admin 不提交 `refundType` 或任何分项金额，只能发起固定的 `ALL` 整笔退费；服务端以订单号生成稳定的 Admin 幂等身份，因此医保腿和微信腿不会被页面拆成两个按钮或两次操作。

## 4. 执行顺序与状态

```text
校验已完成支付订单
    ↓
持久化聚合退费记录（同订单 + 幂等键）
    ↓
6203 退款
    ├─ FAIL → failed，不调用微信退款
    ├─ EXP/未知 → manual_review，不盲目调用微信退款
    └─ SUCC
          ↓
    有现金段 → 微信 APIv3 普通退款/同退款号查单
          ↓
    两腿成功 → succeeded
    微信处理中/未知/异常 → processing 或 manual_review
```

`EXP` 或网络未知结果不会自动重复提交 6203，因为当前 6203 合同只有请求响应，没有可安全推导的独立退款查单端口；这类记录必须人工依据 provider 请求号和业务台账处理。微信未知结果则复用同一个 `out_refund_no` 查询，不生成第二笔退款。

数据库迁移 `0051_medical_insurance_refunds` 新增聚合退费台账；微信现金腿继续使用既有 `hp_wechat_refunds`，并保留微信 APIv3 的金额并发保护。

## 5. 当前验证边界

已完成本地类型检查和单元测试，覆盖：6203 成功后微信 APIv3 成功、同幂等键不重复调用、6203 `EXP` 进入人工复核且不继续调用微信退款。尚未执行真实医保 Provider、真实微信商户、HIS 生产写回、公网回调或真实退款资金验收；代码测试不等于真实资金退费成功。
