# 医保 + 微信 APIv3 退费流程

更新时间：2026-09-22

## 1. 当前真实支付模型

当前项目使用的是“医保支付 + 微信 APIv3”两条真实支付腿的聚合模型：

1. 医保订单的收款侧可按现有微信 APIv3 `/v3/med-ins/orders` Provider 路由创建/查询；这里的“医保混合”只是收款产品名称，平台账本和退费仍按医保腿、微信现金腿分别保存和确认，不代表退费时存在一个由 HIS 代替微信处理的“V2 医保混合退款”接口。
2. 医保金额通过医保 6203 退费。
3. 微信自费金额使用同一笔 APIv3 微信自费 `out_trade_no`，通过微信 APIv3 普通退款 `POST /v3/refund/domestic/refunds` 原路退回。
4. 平台新增一条聚合退费记录，将 6203 和微信退款的状态、请求号、退款单号关联起来；两条外部交易仍然分别以各自 provider 的真实身份存在。

因此，当前实现不是“医保自费混合支付退款由 HIS 用微信 V2 一次完成”，也不依赖 HIS 提供微信 APIv3 医保混合退款。HIS 侧的旧微信 V2 兼容代码不参与本退费主链路。

## 2. 外部接口边界

医保 6203 的固定请求地址来自现有 adapter 合同：

```text
POST /org/local/api/hos/refund_Order
```

代码位置：`packages/adapters/src/legacy-fsi-contract.ts` 的 `LEGACY_FSI_ROUTES["6203"]`。适配器会校验 `payOrdId`、`appRefdSn`、`refdType`、`appRefdTime`、四项金额守恒，以及 `ecToken/payAuthNo` 二选一；响应只接受 `SUCC`、`FAIL`、`EXP`。

微信 APIv3 普通退款的固定请求地址来自现有 adapter：

```text
POST /v3/refund/domestic/refunds
GET  /v3/refund/domestic/refunds/{out_refund_no}
```

代码位置：`packages/adapters/src/wechat-pay.ts` 的 `REFUND_PATH` 和 `REFUND_QUERY_PATH_PREFIX`。退款请求使用原订单的 `out_trade_no`，平台生成稳定的 `out_refund_no` 并以同一退款单号查单/幂等。

当前仓库没有使用 `/v3/med-ins/refunds/notify`，也没有把它注册成回调地址。当前退费闭环依赖 6203 返回结果和微信 APIv3 退款请求/查单结果；微信回调仍只按现有支付通知模块处理。微信官方开发指引明确允许未收到退款回调时按商户退款单号主动查单，因此 MVP 以现有 Worker 和 Admin 主动查单收敛，不新增退款回调、回调存储或另一套状态机。后续如果 Provider 合同明确要求新的医保退款通知接口，必须作为独立合同补充验收，不能从当前代码推导。

## 3. 平台接口

```text
POST /payments/medical-insurance/orders/{orderId}/refund
```

请求头必须包含已认证会话和 `idempotency-key`。请求体：

```json
{
  "refundType": "ALL",
  "reason": "患者申请退费"
}
```

金额规则：

- `ALL`：不提交金额，按订单原始四项金额全额退费。
- `CASH`：只提交 `refundFen`，只能退原微信自费金额。
- `HI`：只提交 `personalAccountRefundFen` 和/或 `fundRefundFen`，不能带现金金额。

客户端不能提交 `payOrdId`、`out_trade_no`、`payAuthNo`、`ecToken`、6203 原始报文或微信商户退款号；这些字段全部从服务端订单、加密授权上下文和服务端生成的退款号中取得。

Admin 使用同源代理 `/api/refunds/medical-insurance`，后端受独立 `X-Admin-Refund-Token` 保护。Admin 不提交 `refundType` 或任何分项金额，只能发起固定的 `ALL` 整笔退费；服务端以订单号生成稳定的 Admin 幂等身份，因此重复点击或请求超时后重试仍关联同一条聚合退费和同一微信商户退款单号。

Admin 查询使用 `GET /api/refunds/medical-insurance/{refundNo}`。当医保腿已经成功且微信现金腿仍为 `requested/processing/unknown` 时，该接口会主动查询微信 APIv3，再返回更新后的聚合状态；列表和结果弹窗的“查询退费/查询最新状态”按钮每次都发起服务端请求，不读取 `localStorage`、`sessionStorage` 或上一笔订单的按钮状态。同一订单已有聚合退费或微信现金退款占用后，列表不再提供新的整笔退费动作，只保留本次退费的查单入口；未发生退费且金额仍完整可退的订单继续保留 Admin 退费入口。

HIS 按外部规定另提供两条独立入口：`/api/v2/his/medical-insurance-leg-refunds` 只发起医保 6203，`/api/v2/his/wechat-leg-refunds` 只发起微信 APIv3 普通退款。两条单腿各自使用独立退款单号、幂等键、查询和日志状态；医保成功不代表微信成功，微信成功也不代表医保成功。HIS 必须分别保存、补偿和对账。原 `/api/v2/his/medical-insurance-refunds` 聚合接口继续保留，用于兼容不要求拆分的调用方；同一订单不能在聚合入口与单腿入口之间混用。

除上述按平台 `orderId` 的兼容入口外，HIS 还可以使用 `/api/v2/his/medical-insurance-leg-refunds/by-pay-ord-id` 提交已确认的医保 `payOrdId`，或使用 `/api/v2/his/wechat-leg-refunds/by-out-trade-no` 提交已确认的微信原支付 `outTradeNo`。两个外部号都只作为服务端查找键：平台命中订单后仍以规范 `medicalOrderId` 保持退款号、幂等和台账关联；HIS 不能提交金额、授权、`out_refund_no` 或任何支付凭证。详细签名和重试契约见 [`HIS退费接口接入说明.md`](HIS退费接口接入说明.md)。

为支持 HIS 结算后按平台订单号发起兼容退费，平台在 `2.27.2.32` 的 `outNetworkSettleMain.settleBackNo` 传入同一笔 `medicalOrderId`。HIS 应将其保存为平台 `orderId`；它仅用于平台关联，不能替代医保 `payOrdId`、微信 `outTradeNo`、退款单号或 HIS 负结算关联字段。

同一根平台订单在自费支付登记阶段，平台调用 `2.27.2.29` 时必须将 `medicalOrderId`（平台 `orderId`）传入请求字段 `thirdPartPayRecordId`。HIS 应保存该关联值，但不得将它作为调用医保或微信退费入口的参数，也不得用它替代 `payOrdId`、`outTradeNo`、平台 `refundNo`、微信 `out_refund_no` 或其他退款单号。`2.27.2.29` 的 `thirdPartPayRecordId` 回执仅表示支付登记成功，平台持久化后将其作为成功断点避免重放该登记调用；它不产生退款身份，也不改变两条退款腿各自的查找、幂等和对账规则。

## 4. 执行顺序与状态

聚合接口的顺序保持为：

```text
校验已完成支付订单
    ↓
持久化聚合退费记录（同订单 + 幂等键）
    ↓
6203 退款
    ├─ FAIL → failed，不调用微信退款
    ├─ EXP/未知 → manual_review，不盲目调用微信退款
    └─ SUCC
          ↓
    有现金段 → 微信 APIv3 普通退款/同退款号查单
          ↓
    微信受理/处理中/未知 → processing + 后台查单任务
    两腿成功             → succeeded
    微信 CLOSED/ABNORMAL → manual_review
```

HIS 单腿接口不使用上述串行编排，而是分别执行：

```text
医保单腿接口  → 读取 6202/授权事实 → 6203 → 医保退款单号/状态
微信单腿接口  → 读取微信现金事实   → APIv3 普通退款 → 微信退款单号/状态
```

单腿之间不做隐式回滚；一条失败或未知时，另一条已经成功的结果必须保留，并进入 HIS/平台人工对账和补偿流程。

`EXP` 或网络未知结果不会自动重复提交 6203，因为当前 6203 合同只有请求响应，没有可安全推导的独立退款查单端口；这类记录必须人工依据 provider 请求号和业务台账处理。微信未知结果则复用同一个 `out_refund_no` 查询，不生成第二笔退款。

微信现金腿进入非终态后会写入既有 `hp_payment_sync_tasks`：

- 任务键固定为 `medical_refund:{refundNo}`，来源为 `wechat_pay`，类型为 `reconcile`；重复入队返回同一任务。
- Worker 只调用 `GET /v3/refund/domestic/refunds/{out_refund_no}`，不会调用退款申请接口，也不会重放 6203。
- 前 5 次按约 1 分钟查一次，之后依次衰减到 5、10、20、30、60 分钟，再进入 12 小时长尾；最多 20 次，耗尽后进入人工复核。
- `PROCESSING` 继续排队；`SUCCESS` 同时收敛微信台账和聚合台账；`CLOSED/ABNORMAL` 保留“医保已退、微信未成功”的部分成功事实并转人工复核。
- 如果进程在“微信终态已落库、聚合台账或任务尚未更新”之间退出，下次执行直接使用已持久化终态收敛，不重复申请退款，也不为已经确认的终态再发一次微信查单。
- 如果微信已经受理但查单任务入队失败，服务端保留已落库的受理状态并返回错误；同一订单再次请求只补建任务，不会把基础设施错误伪装成渠道退款失败，也不会产生第二笔退款。

数据库迁移 `0051_medical_insurance_refunds` 新增聚合退费台账；微信现金腿继续使用既有 `hp_wechat_refunds`，并保留微信 APIv3 的金额并发保护。

## 5. 当前验证边界

已完成本地类型检查和定向单元测试，当前覆盖：

- 6203 成功后微信 APIv3 成功，以及同订单重复请求不重复调用 6203 或微信退款申请。
- 6203 `EXP` 进入人工复核且不继续调用微信退款。
- 微信 `PROCESSING → SUCCESS` 主动查单收敛、`CLOSED` 转人工复核、网络错误退避重试。
- 微信成功事实先落库但 Worker 中断后的无重复请求恢复。
- Admin 主动查询始终使用同一 `refundNo`，并刷新服务端聚合状态。
- MySQL 查单任务按 `wechat_pay + reconcile + medical_refund:` 精确领取，避免其它 Worker 误领。
