## 二、迁移的两层完成定义

### 1. 入口覆盖层

入口覆盖层要求：

- 旧页面、首页 action 和二级 action 都有明确的新端落点；
- 新端页面已在 `app.json` 注册，WXML 事件有对应 TypeScript 方法；
- 未开放能力进入固定 `FeatureKey` 和状态页，不能出现 404、无响应或任意旧 URL；
- 四个主 Tab 只由微信原生 `tabBar` 声明一次，二级页不复制底部导航；
- 加载、空结果、失败、重试和患者切换都有稳定的页面状态。

入口覆盖层已经达到当前源码基线，但它只是迁移的第一层。

### 2. 真实业务层

真实业务只有在下面链路全部具备时才可以把状态页或安全壳替换成开放业务：

```text
正式材料指纹
  -> 成功/空/拒绝/超时样例
  -> owner/患者/外部受众映射
  -> 字段白名单与禁止字段
  -> adapter
  -> domain 不变量
  -> persistence（确有必要才增加）
  -> Elysia API
  -> 原生页面状态机
  -> Pino 低敏日志
  -> 内网、公网、开发者工具、真机证据
```

任何一环缺失时，业务保持关闭；“接口能返回 200”“页面显示暂无记录”
或“旧接口可以转发”都不能替代缺失环节。

## 三、六条并行迁移线

### A：安全只读与真实取证

范围：患者目录、预约目录/历史/爽约、报告目录/受限详情、门诊费用只读、普通资料。

当前代码已经具备 owner、患者代际、字段白名单、低敏日志和页面状态基础，
下一步不是继续围绕单个卡片加字段，而是对同一候选批量采证：

1. 释放开发者工具对 `dist` 的锁，原子替换 pending 运行包；
2. 使用真机分别触发患者切换、预约目录、预约历史、爽约、报告、门诊费用和资料读取；
3. 保存页面状态、客户端 `requestId`、服务端 Pino 事件和 Provider 请求号的同链证据；
4. 如果某一条 Provider 失败，只标记该域，不阻塞其它只读域的取证。

禁止：预约下单、取消、报告附件、费用明细、支付调起和医保授权。

### B：健康内容发布

范围：健康百科分类、症状关联疾病、疾病/药品详情。

代码路由和 fail-closed 读取已就绪，但旧源快照仍有 133 条质量告警，
且没有独立审核 bundle。下一步只做：

- 处理重复关系、控制字符、清理字段和来源声明；
- 由内容责任人生成带版本、审核时间、审核主体、生效窗口和免责声明的审核 bundle；
- 只读校验 bundle，随后在 staging 做导入、重复导入、重叠版本和撤回演练；
- 再采集无 bundle、空结果、搜索和详情的真机状态。

禁止：直接把旧源快照当作正式医学内容；用健康百科数据生成诊断、用药或风险结论。

### C：临床只读契约

范围：门诊病历、住院信息、我的医生、电子导诊单。

四条线必须分别取得 Provider/HIS contract，不能共用预约、报告或门诊费用模型：

- 门诊病历：确认 `out-visit-records` 目录、正文、患者映射和字段白名单；
- 住院信息：确认独立 episode、住院患者标识和在院状态；
- 我的医生：确认受控医生目录、关系失效和展示白名单；
- 电子导诊单：确认独立来源、患者作用域、保留周期和读取权限。

某条线材料不完整时，停止该线并切换到 A/B/D/E 的其它可推进工作，
不注册一个“通用临床查询”接口覆盖四个领域。

### D：患者与便民能力

范围：新增/绑定、协议同意、地址、二维码、签名、预问诊、随访、风险自评、
健康自测、电子锦旗和表扬信。

当前共用患者写入状态机只是基础，不代表任何写入已开放。每条线仍要独立确认：

- owner、当前就诊人和患者映射；
- 同意、幂等、最终事实查询、撤回和补偿；
- 文件/图片安全和医护侧读取；
- 患者端展示字段、日志禁止字段和错误语义。

在这些材料到达前，继续保留原生安全页面和中文边界说明，不提交真实写入。

2026-08-26 服务器只读盘点已确认旧便民六张表共 42 行，但旧 `system_users.openid` 到新微信 owner
没有一行桥接成功，患者引用也为 0；直接 join 还暴露出旧新表 collation 不一致，已在新项目只读审计工具中

[`legacy-convenience-source-audit-2026-08-26.md`](legacy-convenience-source-audit-2026-08-26.md)。

### E：外部入口与实时能力

范围：智能导诊、陪诊、智能客服、我的问诊、订阅消息、云影像、报告分享/复诊。

当前外部短期会话状态机只提供共用安全基础。每个外部主体仍需确认：

- HTTPS 域名 allowlist 和外部主体；
- 受众、患者作用域、短期会话、过期、退出和撤回；
- 回跳协议、内容保留和低敏审计；
- 小程序与外部 WebView 的登录态隔离。

禁止任意 URL、长期 ticket、把本地开关当作订阅成功，或把预约历史冒充问诊/导诊记录。

### F：支付、医保与 HIS 回写

范围：预约下单、门诊/住院缴费、医保授权、微信支付、FSI 查单和 HIS 回写。

这是最后批次。只在金额单位、订单归属、状态机、查单/回调、幂等、退款和补偿

通过一个按钮直接调起支付，也不能修改旧 FSI 转发来“先跑起来”。

## 四、本轮执行方式

### 本轮横向纠偏：就诊患者卡片统一脱敏投影

在继续推进其它迁移线时，审计发现“就诊”主 Tab 的患者卡片仍把内部
`patient.id` 拼成了 `ID` 文案。这个字段虽然不是 Provider 患者号，但它是平台
内部 opaque 标识，不应进入小程序可见文本、截图或用户转发内容；这也会让首页、
患者选择页和就诊页出现三套不同的患者展示规则。

已在 `apps/miniprogram/src/pages/consult/consult.ts` 改为复用
`patient-surface-context` 的公共投影，只展示服务端已脱敏的卡号；患者 ID 仍只
留在请求作用域校验和本地选择键中。该修正不改变就诊页“实时队列/叫号仍关闭”的
业务边界，也不需要 Provider、数据库或旧服务配合。后续新增患者范围页面必须复用
同一投影，不能自行拼接 `patient.id`、Provider `patId` 或卡号原文。新增的
`pnpm miniprogram:patient-display:audit` 会在完整检查中扫描明显的患者 ID 可见
拼接模式；它是代码 review 的补充，不替代服务端 contract 和运行时校验。

每一轮按以下顺序处理，避免再次死磕单个页面：

1. 先运行全量广度、契约和只读审计，确认没有新的漏迁入口；
2. 从 A–F 中选出材料最充分的两条线并行推进；
3. 每条线最多推进到自己当前材料允许的层级，缺材料立即停在边界；
4. 把已完成的代码、未完成的业务、未验证的候选和下一份材料分别写入文档；
5. 同一轮同时补测试、中文注释、日志事件和交接记录；
6. 只提交新项目对应文件，确认旧服务、数据库、Redis 和并行会话文件没有变化后提交中文 commit 并 push。
