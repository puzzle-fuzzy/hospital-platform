## 2. 2.1.9 科室基本信息：基础目录，不等同于预约科室目录

### 2.1 已确认的文档事实

- 接口为 `GET /msun-middle-base-common/v1/depts`，用途是根据医院/院区等条件查询业务科室。
- 请求条件包含可选的 `hospitalAreaId`、`deptId`、`deptName`，并有 `invalidFlag` 启用/作废筛选语义；
  `hospitalAreaId` 的来源依赖另一个院区接口，而不是小程序自行提交的任意医院 ID。
- 输出是 Provider 基础目录对象，包含科室 ID、科室编码、名称、分类、层级、父子关系、机构/医院标识、启用状态、
  排序、房间地址和联系方式等多类字段。

### 2.2 与当前新端的差异

当前预约页面使用的是众阳 AMC 的排班科室接口：

```text
GET /msun-middle-business-amc-server/v1/schedulings/scheduling-depts
```

该接口返回的是预约可用科室白名单和后续排班查询所需的内部标识，不是 `2.1.9` 的完整基础科室目录。两者不能
互相替换，也不能因为字段都叫 `deptId` 就直接拼接使用。当前新端的预约科室目录已经有独立 adapter、日期窗口、
重复主键拒绝和只读快照边界；`2.1.9` 不应绕过这些边界成为预约入口的第二数据源。

### 2.3 当前迁移决策

- 不把基础科室全量字段放入公共 response；患者端只允许接收经过业务用途筛选的名称、展示 ID 和明确授权的状态。
- 不接受小程序提交 `hospitalAreaId`、`deptId` 或机构 ID 来决定 Provider 查询范围；这些值必须由服务端受控配置或
  已确认的机构映射产生。
- 不将 `2.1.9` 返回的 `phone`、房间地址、机构内部编码、层级和管理字段写入日志或小程序缓存。
- 若后续动态医院/院区、科室选择或支付业务确实需要它，先建立独立的目录 adapter 和机构范围 contract；不能复用
  预约 adapter 的 response 类型，也不能把它扩展成万能目录接口。

## 3. 2.1.13 用户信息：院内人员资料，不等同于患者平台用户

### 3.1 已确认的文档事实

- 接口为 `GET /msun-middle-base-common/v1/users`，用途是查询院内人员/用户信息。
- 请求可按 `deptId`、`userId`、`userCode`、`userName`、签名相关筛选、`limit`、员工类别、`pageNo` 和 `pageSize`
  等条件查询；其中 `deptId` 依赖 `2.1.9` 科室目录。
- 返回模型同时包含用户标识、科室、医院/机构、职称/岗位、人员状态、证件/医保相关字段、签名状态、角色列表、
  头像或图片引用、评分/账号状态等多类院内管理字段。

### 3.2 与当前新端的差异

新端的 `/api/v2/me` 和 `/api/v2/me/profile` 表示微信登录后平台用户及其普通展示资料；`2.1.13` 表示 Provider
侧院内人员。二者身份主体不同，不能把 Provider `userId` 写成平台 `user.id`，也不能把 `userName`、`idCard`、
`medicalInsuranceCode`、`roleList`、签名或员工状态当成患者端资料返回。

当前预约目录中的医生名称和医生标识来自 AMC 排班白名单，只服务预约只读展示；这也不等于已经迁移“我的医生”、
医生详情、关注关系或院内人员目录。用户资料接口不能绕过医生目录 contract 直接补齐这些页面。

### 3.3 当前迁移决策

- 不注册 `/api/v2/users`、`/api/v2/departments` 或任何把 Provider 用户资料透传给小程序的兼容路由。
- 不把 `2.1.13` 的分页参数和全量员工资料作为“我的医生”实现；医生关系需要单独的受控目录、owner 关系、幂等
  命令、撤销和审计 contract。
- 如果未来预约确认需要医生的展示资料，只能由预约 Provider 返回经过白名单映射的展示读模型；不允许小程序提交
  `userId` 或从客户端缓存恢复 Provider 人员信息。
- 证件、医保、签名、角色、账号状态和图片 URL 一律属于服务端内部候选字段，未经 Provider/院方确认和脱敏评审，
  不进入 domain、API、日志、数据库 schema 或小程序。

## 5. 对当前代码和迁移矩阵的影响

当前代码保持不变是有意的：

1. 患者目录仍通过平台登录用户的 owner-scoped 同步完成；不通过 `2.1.13` 查找或拼接患者身份。
2. 预约目录继续只使用 AMC 预约 adapter；不把 `2.1.9` 当成排班目录，不把 `2.1.13` 当成医生目录。
3. 普通个人资料继续由 `/api/v2/me/profile` 负责；不与院内 Provider 用户资料合并。
4. 医院列表、动态院区、医生详情、我的医生和预约写入仍按迁移矩阵保持未开放或部分迁移状态。
5. 真实 Provider、公网、真机和日志证据仍需分别保存；本次文档差异不能替代任何一层验收。

## 6. 下一步执行顺序

1. 先向 Provider/院方确认 `2.1.9` 与 AMC 目录的机构、科室主键和版本关系；没有映射证据不实现基础目录 adapter。
2. 对 `2.1.13` 只做字段白名单和权限评审，不导入全量员工资料，不先做“我的医生”页面。
3. 若确认存在当前迁移需要，先实现内部只读 adapter、脱敏 fixture、分页/缓存/失败测试，再决定是否给某个既有业务
   提供内部依赖；不新增通用公共目录 API。
4. 完成 Provider 受控只读、公网路径和真机页面证据后，才更新迁移矩阵状态；文档 `normalized` 不能升级为代码已验收。
5. P0 仍优先于新目录：先完成真实微信会话、患者失效恢复、预约历史、报告和门诊费用的分域证据；支付、医保、
   退款和 HIS 写回继续最后处理。

本记录的结论是“新增材料已完成差异核对并冻结错误复用路径”，不是“科室/用户目录已经迁移”。
