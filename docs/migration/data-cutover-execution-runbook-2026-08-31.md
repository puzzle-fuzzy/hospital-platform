# 数据切换执行与回滚 Runbook（2026-08-31）

> 本文是受控切换的操作步骤和停止条件，不是已执行记录。默认模式仍为新库冷启动；没有负责人、批准窗口、脱敏 staging、备份证据和回滚点时，禁止执行任何导出、导入、双写、停服或线上开关变更。

## 1. 适用范围与不变量

本文适用于未来可能涉及旧用户、患者关系、历史便民记录、健康内容或支付存量的切换准备。旧 Python 服务、旧数据库、Redis 和 Provider 是外部系统，除获得明确变更批准外，本流程不得修改它们。

必须始终保持以下不变量：

- 新平台的 `userId`、`patientId`、订单 ID 和 Provider 引用分层存在，不能复用旧整数 ID、`pat_id`、卡号或身份证生成新公共 ID。
- 任何迁移批次都绑定一个不可变规则版本、源快照指纹、目标候选版本和操作者；同批次重复执行必须幂等。
- 未能唯一映射 owner、患者、就诊/订单或内容版本的记录进入隔离区，不自动猜测、不展示、不驱动 Provider。
- 旧服务与新服务不得同时驱动同一个旧订单、医保结算或 HIS 回写；支付存量默认冻结，支付 gate 默认关闭。
- 原始身份、患者、支付和医疗正文只存在于受限加密 staging/归档，不进入 Git、普通日志、公共 API 或真机截图。

## 2. 角色和批准物

开始前必须登记：

| 角色 | 必须确认的内容 |
| --- | --- |
| 发布负责人 | 候选 commit、窗口、变更顺序、监控和回滚指挥 |
| 数据负责人 | 源/目标范围、脱敏方式、数量/关系/孤儿核对和保留期限 |
| 业务负责人 | 账户/患者连续性、历史可见性和各领域去留 |
| 安全/合规负责人 | 访问权限、密钥、患者数据最小化、归档和删除规则 |
| 临床/支付负责人 | 临床内容或支付存量的审核、最终事实和人工处置 |

批准物至少包括：变更单、源 schema 只读快照、候选版本、配置指纹（不含秘密）、备份/恢复证据、staging 样本、回滚点、值班联系人和停止条件。

## 3. 阶段 A：只读基线

1. 拉取目标候选并固定 commit、lockfile、API/Worker/小程序构建指纹和 migration head。
2. 运行仓库门禁：架构、contract、类型、测试、构建、secret、日志和文档审计；发布基线 audit 必须通过或由负责人明确记录阻断原因。
3. 通过只读方式记录旧 Python 端口、新 API 端口、反向代理路由、systemd 状态、MySQL/Redis readiness 和当前 schema；不打印 env 值、token 或原始业务响应。
4. 确认旧服务继续监听且新服务的健康检查不会把旧端口当成新版本；公网和内网 smoke 只访问健康/ping，不调用支付、医保、预约写入或退款。
5. 保存基线报告、命令时间、执行人和摘要 hash；发现 release 漂移、schema 漂移、配置缺失或日志异常时停止，不进入导出阶段。

## 4. 阶段 B：备份与脱敏 staging

1. 由 DBA 完成旧库和目标库的全量备份、binlog/PITR 保留确认，并在隔离环境验证可恢复；记录备份指纹和恢复时间，不把备份文件复制进 Git 或普通共享目录。
2. 以最小表/字段范围生成源快照，保持源库只读；快照包含 schema、索引、字符集、数量和必要业务字段，不复制无关密码、token、附件或完整响应。
3. 在受限 staging 内完成字段级脱敏/tokenization。需要做精确匹配的身份使用用途隔离的 HMAC/令牌，密钥与报告分离；不可逆报告不能被反推为原值。
4. 将 `system_users`、旧患者/Provider 关系、便民历史、健康内容和支付表分成不同批次；不得用一份万能脚本把它们混在一起。
5. 生成 `source-manifest`：来源范围、记录数、时间窗口、脱敏规则版本、源指纹和过期时间。所有原始 staging 文件设置最短必要保留期限和访问审计。

## 5. 阶段 C：映射与校验

按领域依次执行，不允许跳过前置映射：

1. 先完成账户 owner 映射，再做患者关系映射；只允许同一微信 AppID/环境下的唯一 Provider 身份精确候选。
2. 患者只能通过 owner + 当前 Provider 目录/档案复核进入新模型；目录 `thirdPatientId` 与临床 `patId` 按用途分离。
3. 便民历史必须逐域决定“审核后重建、只存档或不迁移”；健康内容必须有临床审核 bundle；支付存量必须有最终查单/回写/退款事实。
4. 对每个候选执行以下校验：
   - **数量**：源、候选、已映射、未匹配、冲突、孤儿和跳过数量闭合；
   - **唯一性**：owner/Provider/用途/业务主键无重复；
   - **关系**：外键、owner、患者、就诊、订单和事件关系无跨主体引用；
   - **字段**：金额单位、时间时区、枚举、版本、状态和敏感字段符合目标 contract；
   - **完整性**：没有截断、控制字符、未知状态、未审核正文或缺失必要 Provider 证据。
5. 任何失败都生成固定原因码并进入隔离，不在报告中输出原始值；只有全部规则通过的候选才能提交人工审批。

## 6. 阶段 D：幂等演练与人工审批

1. 为批次生成固定 `migrationBatchId` 和规则版本；目标写入以批次/业务键防止重复，不依赖“先查再插”。
2. 在 staging 至少执行两次完全相同的导入，比较行数、摘要、关系和目标结果；第二次必须是 replay/no-op，不能产生重复关系、订单或事件。
3. 模拟中断点：owner 映射后中断、患者映射后中断、目标事务回滚、Provider 复核超时、重复事件和回滚后重跑；每个断点都必须留下可解释状态。
4. 由对应负责人审核冲突、未匹配、敏感字段范围和公开可见性；工程工具不能把“校验通过”提升为业务/临床批准。
5. 形成 `mapping-report` 和 `approval-record`，只含批次指纹、计数、固定原因、操作者、时间和内部引用；通过前不生成线上可见映射。

## 7. 阶段 E：候选切换

只有所有批准物齐全才可进入窗口：

1. 再次确认旧服务、旧数据库和旧 Redis 的回滚点；新候选 preflight、schema 和配置 gate 全部通过。
2. 先发布目标 schema/代码，再打开明确的只读或指定领域开关；不通过环境变量临时绕过支付、医保、Provider 或审核 gate。
3. 迁移只执行已批准批次，逐批记录开始/结束、计数、失败原因和目标指纹；跨域批次之间必须重新检查 owner/患者边界。
4. 切换后只做低风险 smoke：live/ready、登录/会话恢复、患者 owner 隔离和批准的只读域。预约写入、支付、医保、退款和 HIS 回写必须另有真实 contract 和验收，不因切换成功自动打开。
5. 观察新旧服务共存、日志、告警、数据库连接和公网路由；发现重复写入、串户、schema 漂移、错误率异常或无法解释的 Provider 状态，立即停止并进入回滚判断。

## 8. 回滚步骤

1. 发布负责人冻结新批次入口，关闭新侧可见映射/开关；不继续重试未知状态或高风险 Provider 操作。
2. 将本批次目标映射置为不可用/回滚状态，保留审计记录；不删除新身份、不覆盖其他批次、不反向写旧库。
3. 让旧服务继续使用旧事实；确认旧端口、旧数据库、旧 Redis 和原公网转发恢复到切换前状态。
4. 对已经产生的预约、订单、支付通知或临床事实逐项人工对账；不能用通用回滚脚本把它们改成成功、失败、退款完成或已就诊。
5. 回滚后重新执行低风险健康检查、owner 隔离、日志/告警和旧新共存验证，生成回滚报告；没有报告不得再次开启同批次。

## 9. 完成证据与当前状态

一次真实切换只有同时具备以下证据才算完成：备份可恢复、脱敏 staging 校验通过、幂等重跑通过、负责人批准、候选/配置/schema 一致、分批结果闭合、回滚演练完成、旧服务共存正常以及公网/真机/Provider 证据可追溯。

当前本文只完成 runbook 设计，尚未执行任何真实切换；项目继续使用新库冷启动默认，支付/医保/HIS 和未取得真实 contract 的领域继续 fail-closed。
