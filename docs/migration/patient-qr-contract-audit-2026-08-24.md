# 首页就诊人二维码迁移审计（2026-08-24）

> 本文记录首页二维码的事实来源和停止条件。本轮只做旧端/新端代码审计与文档补齐，不修改旧项目，不调用真实 Provider，不打开二维码能力。

## 1. 旧端实际行为

旧端文件：`G:\\fuck\\hospital\\hospital-app\\src\\pages\\index\\index.vue`。

- 顶部卡片的二维码图标只是打开弹窗的入口，并不是二维码内容本身；弹窗通过 `patientQrUrl` 显示图片。
- `patientQrUrl` 实际读取的是 `patientInfo.medicalCardNo`，再拼接第三方 `https://api.qrserver.com/v1/create-qr-code/` URL。
- 弹窗下方显示的也是 `medicalCardNo`。
- 旧代码旁边的注释写着“只需要包含 patId 信息”，但实际变量和 URL 的 `data` 值是 `medicalCardNo`；这不能作为医院扫码协议的证明。
- 旧端还允许从 `SelCard` 缓存拼装 `patId`、卡号和患者资料。它是客户端兼容缓存，不是经过服务端 owner 校验的二维码授权载荷。

因此，当前能确认的事实只有“旧端曾把医疗卡号交给第三方二维码图片服务”，不能确认医院扫码端期待的是卡号、HIS `patId`、签名串、短期票据还是其它协议。

## 2. 新端当前边界

新端 `Patient` 公共响应只包含：

- 平台内部 opaque `id`；
- 患者展示名、关系和脱敏卡号；
- `clinicalAccess` 等业务可用性字段。

它不包含 provider 患者号、完整医疗卡号、身份证号或二维码原文。首页的 `patient-qr.svg` 目前只是视觉入口，`onPatientQr` 会先重新确认当前会话和当前患者；在没有正式二维码合同之前，页面只显示关闭提示，不生成或外发伪二维码。

## 3. 不能直接恢复旧实现的原因

1. 把完整卡号放进第三方二维码 URL 会把医疗身份字段发送给非医院服务，违反新端的最小暴露边界。
2. 直接把 `patId` 编进二维码会把 provider/HIS 标识变成可复制、可长期使用的 bearer-like 引用，且目前没有医院扫码端的验签、过期和撤销协议。
3. 客户端缓存的 `patId` 或卡号不能证明当前微信账号仍拥有该患者；账号切换、患者失效和缓存残留都会造成错绑风险。
4. 没有成功/过期/撤销/扫码归属失败/网络异常等状态合同，无法区分“没有二维码”与“二维码服务故障”。

## 4. 正式开放前必须冻结的合同

二维码要从关闭态进入可用态，至少需要医院或 Provider 书面确认以下内容：

| 合同项 | 必须明确的内容 |
| --- | --- |
| 业务用途 | 扫码方、扫码后动作、是否只读、是否允许跨设备使用 |
| 载荷 | 原始字段到底是卡号、HIS `patId`、签名票据还是一次性 token；禁止仅凭旧端注释推断 |
| 服务端生成 | 由新服务在 owner + 当前 patient 上生成，还是由医院 Provider 生成；禁止客户端自行拼接 |
| 有效期 | 过期时间、刷新规则、撤销规则和重放处理 |
| 归属校验 | 扫码方如何确认患者归属、医院/院区和业务用途，服务端如何阻止跨 owner 使用 |
| 展示安全 | 小程序不显示完整卡号/身份证；日志不记录载荷、原始 URL 或扫码结果 |
| 异常语义 | 未登录、无患者、患者不可用、过期、撤销、Provider 拒绝、网络失败分别对应的状态和文案 |
| 观测审计 | 只记录低敏 `traceId`、业务操作和结果类别，不记录二维码原文；需要可回溯的请求链 |

推荐的安全形态是：服务端生成绑定当前 owner、患者、医院和用途的短期 opaque QR token，扫码端通过正式接口换取受限结果；token 不等于 provider 患者号，不长期存储，不把原始卡号交给第三方图片服务。最终方案仍以医院扫码协议为准。

## 5. 当前决定与下一步

- 当前继续保持二维码入口关闭，不修改首页的患者读模型，不新增二维码 API，不接入第三方 QR 图片服务。
- 取得正式扫码协议和脱敏样例后，先完成服务端 contract、owner/患者绑定、TTL/撤销和日志审计，再设计小程序展示；二维码能力不能和支付、医保或患者新增绑定顺手打开。
- 本审计不涉及众阳接口自动化，也不改变当前旧 Python 服务、线上服务、数据库或 Redis。

本轮重新对照旧端源码和当前小程序运行候选，结论没有被“首页看起来有二维码图标”改变：

- 旧端 `patientQrUrl` 仍然读取 `patientInfo.medicalCardNo`，并拼接第三方二维码图片地址；旧端注释中的 `patId` 只是注释，不是扫码协议证据。

- 患者新增/绑定仍只有 `GET /patients` 与显式同步目录能力；没有注册建档、绑卡或解绑路由，不能因为旧端 `patInfosFind` 返回过一次 `patId` 就打开写入。
- 本轮没有读取真实患者、Provider 原始卡号、数据库或 Redis，也没有修改旧项目；另一个会话负责的众阳接口自动化边界保持不变。

## 8. 2026-08-26 `patInfosFind` 身份用途复核

本轮结合旧端 `src/api/modules/ZY.ts`、患者选择组件和预约/报告/费用调用链重新核对了
`patInfosFind` 的返回身份。结论如下：

- 返回的 `patId` 是 Provider/HIS 临床患者映射；新端应把它限制在服务端的
  `providerReferenceKind=his-patient` 引用中，用于需要临床映射的预约、报告和门诊费用查询。
- 旧端首页二维码的实际 `data` 来源仍是 `patientInfo.medicalCardNo`，并通过第三方二维码图片服务生成图片；旁边“只需要包含 patId 信息”的注释与实际代码不一致，不能作为扫码协议证据。
- `patInfosFind` 返回 `patId` 这一事实只能证明“档案查询获得了一个 HIS 患者标识”，不能证明医院扫码端接受该值，也不能证明它具备签名、TTL、撤销或防重放能力。
- 因此不能把 `patId` 直接加入小程序公共 `Patient` 响应、页面二维码、日志或 URL；也不能把完整 `medicalCardNo` 发送给第三方二维码图片服务。

这次复核没有读取真实患者数据、没有调用 Provider、没有修改旧项目或线上配置。二维码正式开放仍必须先取得扫码方确认的载荷格式和服务端换票协议，再实现 owner/患者绑定、短期 token、撤销、防重放和低敏审计。
