冻结入口 gate 现在还按 A–F 批次机器归类：A=3、B=0（健康内容独立审核队列）、C=4、D=12、E=8、F=7。任何 gate 缺少批次都会让 `migration:boundary:audit` 和 `migration:readiness` 失败，避免后续只更新文档范围而漏掉执行队列。

因此下一步不再继续重复加固同一页面，而是按以下并行队列推进：

1. **批次 A：安全只读真实取证。** 预约目录、预约历史、爽约、报告目录/详情、门诊费用和普通资料并行采集页面、HTTP、Pino、Provider 低敏请求号；不因空结果或依赖未配置标记成功。
2. **批次 B：健康内容发布。** 健康百科独立等待审核 bundle、质量清理、staging 导入、发布/撤回演练和真机证据，不把健康内容 gate 混入临床或患者写入。
3. **批次 C：临床只读 contract 并行冻结。** 门诊病历、住院信息、医生关系、电子导诊单分别建立字段白名单、患者归属、错误分类和脱敏样例；外部“我的问诊”属于 E，不共用 `patId` 或万能接口。
4. **批次 D：患者/便民/临床写入准备。** 患者新增/绑卡、二维码、预问诊、随访、风险评估、健康自测、锦旗和表扬信并行整理协议、版本、同意、幂等、撤回和审核清单；未冻结前保留稳定状态页。
5. **批次 E：外部入口与实时能力。** 智能导诊、陪诊、客服、我的问诊、订阅、云影像、报告分享/复诊分别冻结主体、allowlist、短期会话、受众、退出和回跳规则。
6. **批次 F：支付与回写最后单独推进。** 预约锁号、下单、支付、医保授权、1101/6201/6202/6301、退款和 HIS 回写单独建状态机，不能与门诊费用只读列表共享“成功”语义。

批次 A 的运行包锁定和服务端发布基线是“验收前置条件”，不是新的业务迁移方向；它们解除后只用于取证和发布，不会继续吞噬后续业务域的迁移时间。

2026-08-25 的广度护栏补充：所有统一状态页现在展示机器可读的准入阻塞类型，分别区分

## 三、按 A–F 批次批量推进

### 批次 A：低风险只读与静态能力

预约目录/历史/爽约、报告目录/受限详情、门诊费用只读和普通资料先完成同一运行包的
页面、客户端 requestId、服务端 Pino、Provider 请求号和患者切换证据。空结果必须是合法
空结果，不能把依赖未配置或 Provider 超时渲染成“暂无记录”；详情、附件、取消和写入仍分开验收。

### 批次 B：健康内容发布

健康百科的代码只读骨架已经存在，但必须等待独立审核 bundle：源质量清理、内容责任人、
版本/免责声明、staging 事务导入、发布/撤回演练和真机内容版本证据全部齐全后才可发布。
健康内容不等价于临床问诊、风险评估或自测结论。

### 批次 C：临床只读契约

门诊病历、住院信息、医生关系、电子导诊单四条线分别确认 Provider 身份、请求/响应/空/
拒绝/超时样例、患者 owner 映射、字段白名单和保留周期。外部“我的问诊”是短期外部会话，
归入 E，不与 C 共用临床只读模型。材料入口固定为
[`clinical-readonly-intake-board-2026-08-25.md`](clinical-readonly-intake-board-2026-08-25.md)
和 [`contract-intake-catalog-2026-08-25.md`](contract-intake-catalog-2026-08-25.md)。

### 批次 D：患者与便民写入

患者绑定、协议、地址、二维码、签名、预问诊、随访、风险评估、自测、锦旗和表扬信必须
先冻结 owner、版本化同意、命令幂等、最终状态查询、撤回、文件安全和医护读取规则。旧端
请求代码不能代替新 contract；查档异常不能降级为建档，写入超时不能自动重放副作用命令。

### 批次 E：外部入口与实时能力

智能导诊、陪诊、智能客服、我的问诊、订阅消息、云影像、报告分享和报告复诊分别确认外部
主体、域名 allowlist、短期受众会话、退出/回跳、过期/撤回和访问审计。没有这些材料时，
不恢复任意 WebView、长期 ticket 或把平台 token 交给第三方。

### 批次 F：支付与医保最后处理

预约锁号、下单、门诊/住院支付、医保授权、1101/6201/6202/6301、结算、退款、查单和 HIS
回写统一最后处理。必须有金额单位、订单 owner、幂等键、回调/查单状态机、失败补偿和真实
沙箱/生产验收；只读费用页不得直接跳入支付流程，也不能修改旧 FSI 转发来“打通”新支付。

各批次都必须完成 `contract → adapter → domain → persistence（如需要）→ API → 小程序 →
日志 → 内网/公网/真机验收`，否则继续停留在状态页或只读安全子集。

## 四、每批的完成定义

只有同时满足以下条件，才将矩阵状态从“迁移中/部分迁移”改为“已完成”：

1. 新端页面和 API contract 已注册，字段白名单与患者归属明确；
2. 成功、空结果、未授权、暂时故障和未知响应均有稳定读模型；
3. 服务端日志只记录低敏业务字段，并能用 requestId 与客户端链路关联；
4. 自动化测试、类型检查、运行包构建通过；
5. 真实环境页面、HTTP requestId、服务端日志和 provider 结果完成同链验收；
6. 文档、发布候选和旧服务共存证据同步更新。

## 五、当前明确不做的事情

- 不修改旧 Python 项目、旧 `8001` 服务、旧数据库和 Redis；
- 不因为“先全量迁移”而复制旧端 provider URL、完整身份证号、卡号、`patId` 或 token 到小程序；
- 不把状态页、Toast、空列表或本地计算结果包装成真实医疗业务成功；
- 不强制结束微信开发者工具进程，不删除被锁定的 live `dist/`；
- 不与另一会话负责的众阳自动化文件冲突。
