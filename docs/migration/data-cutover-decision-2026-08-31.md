# 数据切换策略决策

更新时间：2026-08-31

## 1. 决策结论

当前重构候选按“新库冷启动”作为默认技术策略：新端只使用 `hp_*` schema 中通过新 contract 写入或同步的数据，不在发布时自动导入旧库用户、患者关系、预约/支付存量、便民历史或健康知识历史。

这是一项保守的工程准入结论，不等同于业务负责人已经决定放弃旧存量。如果产品最终要求保留旧用户或历史业务，必须先完成本文第 4 节的专项设计、脱敏 staging 和负责人签字，然后才能把策略切换为“受控存量迁移”。

## 2. 本次核验到的事实

截至本决策日期，仓库内确认到的事实如下：

1. 新库迁移文件只创建和升级 `hp_*` 表，没有发现旧 `system_users`、`my_doctor`、`mbs_medical_orders`、便民业务表或 `knowledge_*` 表的通用 backfill 脚本。
2. 没有发现以旧 `openid`、`unionid`、`pat_id`、卡号或身份证直接生成新端 `userId`、`patientId` 的双读/双写逻辑。
3. 新端患者目录是 owner-scoped 的新读模型；Provider 标识与小程序公共 `patientId` 分层保存，不能把旧目录快照当作新端关系。
4. 支付订单、预支付尝试、通知和 outbox 有自己的状态机、幂等和人工复核边界；旧支付存量的状态不能依靠字段名称猜测迁入。
5. 健康百科已经有专用源快照和审核 gate，但没有可直接当作历史迁移结果的通用知识导入证明。

因此，在没有映射、对账和回滚证据时继续保留旧存量，会把“能登录”误认为“账户连续”、把“能看到患者”误认为“关系正确”，并可能造成订单或医疗数据串户。冷启动是当前唯一可以在不制造错绑风险的情况下发布的默认路径。

## 3. 冷启动的明确边界

- 新端首次微信登录只创建或查找新 `hp_identity_users` 记录；不从旧库复制实名资料、手机号、身份证、`openid` 或 `unionid` 到小程序公共响应。
- 新端患者关系必须通过新的患者同步/绑定 contract 建立；不能通过旧 `pat_id`、卡号或目录截图预填关系。
- 旧系统的预约、报告、费用和支付历史不因新端上线自动出现在新端；如需展示，必须先定义只读历史的权威来源、患者归属和脱敏规则。
- 新端支付、医保、退款和 HIS 回写继续保持现有 fail-closed gate；不能为了“看起来有数据”导入待支付或已支付存量。
- 旧 Python 服务和旧数据库保持原有运行策略，冷启动决策不授权停止、重启、改写或清理旧系统。

## 4. 未来改为保留存量的准入条件

只有以下材料全部完成并由业务/数据负责人确认，才允许另立变更把策略改为受控存量迁移：

1. 账户连续性映射：旧账户到新账户的唯一匹配规则、冲突处理、首次绑定、解绑、删除和回滚。
2. 患者关系映射：旧患者标识到新 `patientId`/Provider reference 的脱敏映射、重复关系和孤儿记录报告。
3. 订单对账：待支付、已支付、退款中、失败、重复通知等状态的逐笔核对、冻结和人工处置。
4. 历史业务分类：便民问卷、医生关系、表扬信/锦旗、健康知识分别决定审核导入、只存档或不迁移。
5. 迁移演练：脱敏 staging、导出快照、数量/关系/孤儿校验、幂等重跑、审计留痕、旧端只读窗口和失败回滚。
6. 运行验收：新旧服务共存期间的公网、数据库、日志、真机和 Provider 证据，且不依赖旧服务被停止。

## 5. 当前发布判断

在第 4 节完成前，发布审批单应填写：

```text
dataCutoverMode = cold-start
legacyDataImport = disabled
legacyWriteBack = unchanged
paymentStockImport = blocked
rollback = keep-legacy-service-and-database-unchanged
```

本文只固化仓库当前的安全默认策略，不把冷启动误报成存量迁移完成；账户连续性、患者映射、支付存量和正式切换窗口仍保留在 `TODO.md` 的 P0 清单中。
