# 健康知识旧库源快照审计（2026-08-25）

> 本文记录旧库健康知识快照的工程质量审计结果，不是临床审核结论，也不是患者端发布凭证。
> 快照来自新项目的只读导出流程；本轮没有修改旧数据库、旧服务、Redis 或任何线上进程。

## 1. 当前结论

当前快照只能作为“待审核迁移源”，不能直接导入 staging，也不能让患者端健康百科路由读取。

原因是快照的 `source.publicationState` 明确为 `not-approved`，且尚未具备内容责任人、审核人引用、审核时间、
固定免责声明和正式发布窗口。新端健康百科代码虽然已经具备，但服务端继续保持 fail-closed 是正确行为。

直接在快照上手工补写 `published` 或审核字段。

可重复执行聚合审计：

```powershell
pnpm health:source:audit
```

如需把质量告警作为失败条件，可执行 `pnpm health:source:audit -- --strict`；当前源快照预期会因未处理的
重复关系、控制字符和未定义来源而失败，这正是阻止它进入正式 bundle 的门禁。

### 关键业务不变量

- 同一发布窗口内所有目录、详情和关系必须使用同一个 `contentVersion`，不能拼接不同审核版本。
- 药品关系中的 `drugId`、名称和可点击状态必须同时经过引用校验；不能仅凭名称生成跳转。
- 旧正文中的控制字符、未知字段和患者敏感字段必须在正式 bundle 阶段拒绝，不在 API 层静默修正。
- `knowledge_tips` 是未定义内容类型，不得塞进疾病正文、药品说明或通用提示字段。
- 没有审核元数据时，任何 `published`、`effectiveFrom` 或患者端展示状态都不能由导入器推断。

## 5. 下一步审核队列

1. 内容责任人根据上述重复关系和控制字符报告，输出一份独立的脱敏审核 bundle；不能修改旧源快照来掩盖问题。
2. bundle 必须补齐 `publication.contentVersion`、`status`、`reviewedAt`、`reviewerRef`、固定免责声明、
   `effectiveFrom` 以及完整的疾病/药品详情集。
3. 先执行只读校验：

   ```powershell
   pnpm --filter @hospital/domain knowledge:bundle:check -- C:\path\to\health-knowledge-bundle.json
   ```

4. 只读校验通过后，仍需人工确认来源和临床审核证据，再以 `DEPLOY_ENV=staging` 和显式确认参数执行单事务导入。
5. staging 导入完成后，还要完成发布、撤回、重叠生效窗口、搜索/详情同版本读取和真机只读验收，才能考虑开放患者端。

## 6. 当前不做的事情

- 不把旧源快照复制到 `reviewed-bundle.json`。
- 不直接导入生产数据库，不手工修改发布状态。
- 不在缺少临床审核时开放疾病、药品、自测、BMI 或血压计算结论。
- 不把旧快照正文写入日志、错误响应或小程序本地缓存。
- 不因为页面和 API 已经存在，就把健康知识域标记为真实迁移完成。

正式内容导入规则详见 [`health-knowledge-import-runbook.md`](health-knowledge-import-runbook.md)。
