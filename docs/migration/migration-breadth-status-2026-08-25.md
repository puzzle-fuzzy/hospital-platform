## 3. 按业务域的推进顺序

| 批次 | 范围 | 当前动作 | 放行条件 |
| --- | --- | --- | --- |
| A | 预约/报告/费用/普通资料只读 | 先做同一运行包的页面、HTTP、服务端日志和 Provider 同链验收 | 成功、空结果、鉴权失败、超时和患者切换证据齐全 |
| B | 健康百科只读 | 页面和服务端骨架已具备，等待正式审核 bundle | 脱敏来源、内容版本、审核人、生效/撤回和 staging 演练齐全 |
| C | 门诊病历、住院、医生、电子导诊 | 先登记 Provider contract，四个域独立建模 | 请求/响应/错误/映射/脱敏样例和 owner 越权测试齐全 |
| D | 患者绑定、预问诊、随访、风险评估、锦旗/表扬信 | 继续状态页，补齐状态机和审核材料 | 幂等、同意、撤回、医护读取和审计规则齐全 |
| E | 智能导诊、陪诊、客服、我的问诊、订阅、云影像、报告分享/复诊 | 先冻结外部主体、allowlist、短期会话和回跳规则 | 外部受众、退出、撤回、保留周期和低敏访问审计齐全 |
| F | 预约写入和支付/医保/结算/退款 | 最后处理，不与只读费用页混用 | 金额守恒、订单 owner、回调/查单、补偿和真实环境验收齐全 |

每个批次都必须按以下顺序推进，不允许从页面直接调用旧 Provider：

```text
contract
  -> adapter
  -> domain 不变量
  -> persistence（必要时）
  -> Elysia API
  -> 原生小程序页面
  -> 低敏日志与 requestId 链路
  -> 内网/公网/真机验收
```

## 4. 当前候选和运行包边界

当前功能候选已经包含健康百科页面和全量入口门禁，但实际运行包仍分为：

- `functional candidate`：源码和本地测试对应的功能提交；
- `pending runtime`：等待发布到微信开发者工具的候选构建；
- `live dist`：当前开发者工具仍可能持有的旧运行包。

只有关闭开发者工具对 `apps/miniprogram/dist/` 的占用后，执行：

```powershell
pnpm --filter @hospital/miniprogram runtime:publish-pending
pnpm --filter @hospital/miniprogram runtime:verify
```

并从新的 `dist` 重新编译、扫码，才能开始这一候选的真机证据采集。发布失败时必须保留旧 live 包，不能删除或清空 `dist/`。

## 5. 给后续会话的停止条件

1. 看到 `blocked-*` 页面，不要先做假数据页面；先查对应 FeatureKey 和准入文档。
2. 看到 Provider 返回字段，不要直接把原始字段放进小程序；先做 owner、字段白名单和脱敏校验。
3. 看到“支付/医保”字样，不要复用门诊费用只读模型；支付、查单、结算和退款必须单独建状态机。
4. 看到“病历/住院/问诊”字样，不要复用预约或报告的内部引用；各域必须独立确认 provider 映射。
5. 看到页面已经能打开，不要把状态页、空态或本地 fixture 当作业务完成；必须补齐真实链路证据。
6. 修改新项目后继续使用中文 commit，并保持 `docs/obsidian/.obsidian/` 等用户本地文件不入 Git。
