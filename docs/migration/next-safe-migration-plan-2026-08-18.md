## 3. 恢复后的执行顺序

### 3.1 先恢复真机 P0 只读验收

真机重新连接新项目后，必须使用与新 API release 配对的小程序包，按以下顺序取证：

1. 微信登录，确认会话建立；
2. 首页刷新患者目录，确认当前用户只能看到 owner-scoped 脱敏读模型；
3. 进入选择就诊人页，确认切换不会把普通用户资料当成就诊人；
4. 进入“我的挂号”，确认预约历史、爽约筛选、患者信息和旧端布局；
5. 进入门诊缴费，分别观察待缴和已缴只读列表；
6. 进入普通资料页，验证性别选择器和页面返回，但本轮不点击保存；
7. 进入报告目录，记录真实 Provider 的配置状态和错误展示，不打开详情或附件。

每一步都需要同时满足页面、网络请求和服务端低敏日志三层证据。只有页面截图而没有请求/日志，不能算业务验收；
只有接口 200 而没有患者上下文和字段核对，也不能算迁移完成。

### 3.2 真机只读闭环后，再处理普通资料写入

普通资料 PUT 是低风险写入，但仍必须使用专门测试账号并具备回滚边界。执行顺序固定为：

1. 先用 GET 保存当前 `version`，确认只返回普通资料字段；
2. 提交一次最小变更，核对响应版本递增和重新 GET 的持久化结果；
3. 使用旧版本制造一次 `409 user-profile-conflict`，确认服务端拒绝覆盖新版本；
4. 检查日志只包含操作名、trace、结果和版本信息，不包含昵称、邮箱、身份证或令牌；
5. 真机确认返回“我的”页面后，才把资料写入证据记入验收文档。

不把 PUT 结果推广为头像、实名、手机号或患者档案更新成功；这些字段仍然不属于普通资料契约。

### 3.3 具备独立契约后，才继续低风险业务

以下能力按契约到达顺序推进，不按旧页面按钮数量推进：

| 候选能力 | 开始条件 | 未满足时的处理 |
| --- | --- | --- |
| 报告目录/详情 | LIS/影像 Provider 的字段白名单、患者归属、资源授权、附件短期引用和错误样例 | 目录可保留配置错误态；详情与附件保持未注册。 |
| 患者新增/绑卡 | 实名校验、卡号所有权、重复绑定、撤销、幂等和审计契约 | 继续只同步已有目录，不把“添加就诊人”伪装成成功。 |
| 患者二维码 | 医院扫码字段、签名算法、短期 TTL、撤销/防重放、扫码回执和测试设备 | 继续关闭二维码入口，不拼接卡号或 provider 患者号。 |
| 反馈/锦旗/问卷 | owner、版本、幂等、内容审核、撤回和医护侧权限 | 仅保留说明页或迁移提示，不提交旧 payload。 |
| 动态医院/院内导航 | 机构/院区版本、坐标来源、路线授权和错误语义 | 保留已核对的静态卡片/地图，不宣称动态服务完成。 |

## 4. 明确暂不执行的动作

- 不修改旧 Python 项目，不修改旧服务监听端口 `8001`，不把新端路由转发回旧 provider 以制造兼容成功。
- 不在没有 Provider 文档和测试样例时实现二维码、患者绑卡、报告附件、预约写入、取消或费用详情。
- 不因开发者工具内部错误直接改业务代码；先在真机重新验证性别选择器。只有错误稳定指向项目实现时才修复。
- 不在真机未连接时把模拟器观察标记为真机通过。
- 不打开微信支付、医保授权、医保结算、退款或 HIS 回写；这些能力必须在只读链路稳定后单独建立状态机和回调证据。

## 5. 日志与验收要求

业务日志使用现有结构化日志包和事件命名，生产聚合只能保留操作名、结果、状态码、trace 和脱敏数量等低敏字段。
原始 token、openid、完整身份证、手机号、卡号、provider 患者号和支付凭证不能写入页面日志、服务日志或验收文档。

每次候选发布必须记录：源码 commit、客户端配对版本、bundle 校验值、生产模式、MySQL/Redis/schema readiness、
公网入口、旧端口共存状态和回滚指针。业务证据必须区分“代码存在”“接口可达”“Provider 返回”“页面展示”和“真机通过”。

## 6. 当前下一动作

当前最小且正确的下一动作是：使用当前线上配套的 `13f597e` 真机包，按 3.1 顺序完成 P0 只读证据；
如果先验证本地 `37735af1`，必须先完成受控候选发布并重新生成二维码和证据清单，不能把本地构建直接当作线上验收。
在真机证据完成前继续做代码审计和文档门禁，不扩展高风险业务范围。普通资料页开发者工具错误的最终判断也绑定在这次真机复核上。
