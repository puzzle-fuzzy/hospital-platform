# 旧账户到新微信身份的连续性映射设计（2026-08-31）

> 本文完成的是账户连续性“设计”项，不是实际迁移执行记录。当前发布默认仍为新库冷启动；本文不授权连接旧库、导出真实身份、修改 `hp_identity_users`、双写或切换线上登录。

## 1. 为什么必须单独设计

旧服务的 `system_users` 把后台账号、微信身份、普通资料和实名字段放在同一张表中，已观察到的字段包括：整数用户主键、用户名、密码哈希、状态、手机号、邮箱、性别、头像、`openid`、`unionid`、身份证号、真实姓名和年龄。

新服务的 `hp_identity_users` 只保存平台内部 `user_id`、微信 Provider subject 和可选 `union_id`；普通资料单独保存在 `hp_user_profiles`，且公共 contract 不开放头像、手机号、身份证、实名或 Provider subject。两边不能通过“看起来相似”的展示字段直接合并。

如果未来要求保留旧账户，必须先把“旧账户属于哪个新微信身份”与“旧账户的普通资料是否允许迁移”拆成两个决定，并为冲突保留人工隔离区。

## 2. 来源与目标字段边界

| 旧字段类别 | 新目标 | 处理规则 |
| --- | --- | --- |
| `system_users.openid` | `hp_identity_users.provider_subject` | 仅在确认同一微信小程序 AppID/环境、值唯一且来源可信时作为精确匹配候选；不得写入日志或公共响应 |
| `system_users.unionid` | `hp_identity_users.union_id` | 仅在确认同一微信开放平台主体和绑定关系时作为辅助核对；不能脱离 AppID/主体单独匹配 |
| 旧整数 `id` | 新 `user_id` | 不复用、不直接转换；新 ID 必须由新平台生成，旧 ID 只存在于受限 staging 映射 |
| `name`、`real_name`、手机号、身份证、邮箱、头像、密码哈希 | 不自动导入 | 这些字段不能作为身份匹配键；是否迁移普通资料要另立 contract 和授权，不因账户匹配成功而自动带入 |
| `status` | 新账户准入状态 | 不能把旧后台启用状态直接解释为微信登录授权；禁用/冲突账户进入隔离队列 |

旧 `openid`/`unionid` 是受限身份数据。导出快照只能在访问控制、加密存储和最小权限环境中短暂存在；审计报告使用带用途隔离密钥的 HMAC 摘要和计数，不输出原值、姓名、手机号、身份证或密码哈希。

## 3. 唯一匹配规则

所有匹配都在脱敏 staging 中执行，禁止模糊匹配、大小写折叠、姓名拼音匹配或“手机号 + 姓名”拼接猜测。规则按以下顺序执行：

1. **微信身份精确匹配**：在同一 AppID、同一环境和同一 Provider 语境下，旧 `openid` 与新 `provider_subject` 完全相等，且两边各自唯一，生成一个候选。
2. **开放平台辅助核对**：如果第 1 步没有结果但双方都拥有经确认的 `unionid`，仅在开放平台主体、AppID 绑定和环境一致时生成候选；`unionid` 不得跨主体复用。
3. **无法精确匹配**：标记为 `unmatched`，按新库冷启动创建新账户或由业务负责人另行处理；不使用任何展示字段补匹配。
4. **任何重复或冲突**：标记为 `quarantined`，停止自动绑定。例如一个旧身份对应多个候选、一个新 Provider subject 对应多个旧用户、AppID/主体不一致、旧账户状态互相矛盾，均必须人工复核。

匹配报告至少包含：规则版本、源快照指纹、目标快照指纹、总数、唯一匹配数、未匹配数、冲突数、孤儿数和生成时间。报告不包含原始身份值。

## 4. 首次登录绑定流程

绑定流程不能让小程序提交旧 `user_id`、`openid`、`unionid`、身份证或手机号。建议采用以下受控流程：

1. 小程序仍只提交一次性微信 `code`；服务端按现有 code2session 流程取得 Provider 身份。
2. 服务端在受限映射表中按已批准的规则查找该 Provider 身份的唯一映射，检查映射版本、AppID/环境、状态和有效期。
3. 只有状态为 `approved` 且唯一的映射才允许绑定到既有新 `user_id`；绑定写入必须幂等，并记录内部审计事件。
4. 没有映射时按冷启动创建或读取新 `hp_identity_users`，不得为了“找回旧账号”继续尝试姓名、手机号或身份证匹配。
5. 映射冲突、已撤回、已回滚或校验失败时拒绝自动绑定，返回普通用户可理解的“账号需要人工确认”提示，技术原因只进入低敏日志。
6. `hp_user_profiles` 是否填充必须由独立的资料迁移 contract 决定；账户绑定成功不等于实名、手机号或头像迁移成功。

绑定状态建议使用：`candidate → approved → bound`；异常分支使用 `quarantined`，撤销使用 `rolled_back`。任何状态变更都需要版本条件，重复消息只能得到同一最终结果。

## 5. 演练、发布与回滚

### 5.1 进入生产前

- 在脱敏 staging 生成旧/新快照，验证数量、唯一性、冲突、未匹配和孤儿记录。
- 使用同一版本规则至少完成一次幂等重跑；两次摘要和计数必须一致。
- 由数据、业务和安全负责人共同确认匹配比例、冲突处置和资料迁移范围。
- 先采用旁路映射验证登录，不删除旧账户、不改旧服务、不双写敏感字段；新旧服务保持共存。
- 发布包、映射规则、审计摘要和回滚点绑定到同一候选版本。

### 5.2 回滚

- 只需将映射状态切换为 `rolled_back` 并停止新登录使用映射；不删除新 `hp_identity_users`，不覆盖新账户，不反向写旧表。
- 已按新账户产生的患者目录、预约或订单不能通过“回滚账户”自动改绑，必须按各自领域的归属和对账规则人工处置。
- 旧服务和旧数据库保持原状，回滚验证至少包含旧端登录、旧端患者关系和公网转发共存状态。
- 回滚记录仅保存内部用户引用、版本、操作者和原因，不记录原始身份值。

## 6. 当前结论

账户连续性映射规则已经形成，但实际迁移仍未获准，也没有旧/新脱敏快照和业务负责人确认。当前发布单继续使用：

```text
dataCutoverMode = cold-start
legacyIdentityImport = disabled
identityMappingExecution = pending-approval
rollback = keep-legacy-service-and-database-unchanged
```
后续若要执行，必须另提交受控变更，补齐受限 staging、真实计数/冲突报告、负责人批准、真机登录证据和回滚演练；不能把本文作为已迁移或已绑定的证明。
