## 一、这次策略调整

当前旧端扫描到 64 个页面，新端有 20 个原生页面。其余入口已经能够进入统一
`pages/feature-status/feature-status`，但其中相当一部分仍缺少 Provider、临床、支付、
患者绑定或外部入口 contract。

因此“整体迁移完备”分成两个并行层次：

1. **入口覆盖层**：旧端每个入口都有稳定页面落点、明确状态和固定 `FeatureKey`，不再出现 404、无响应或任意旧 URL 跳转。
2. **真实业务层**：只有 contract、adapter、领域不变量、日志和三层验收证据齐全，才把状态页替换为真正业务页面。

入口覆盖层不能替代真实业务层；真实业务层也不能因为一个域已经完成而阻塞其他域的 contract 收集。

## 三、当前可验收的真实范围

以下页面已经有新端代码，但“已迁移”仍要区分代码、运行包和线上业务证据：

- 首页、就诊、互联网医院入口、我的；
- 就诊人目录与切换；
- 预约目录、在线/全部预约历史、爽约记录；
- 报告目录和 owner-scoped 详情读取骨架；
- 门诊费用待缴/已缴只读列表；
- 普通个人资料 GET/PUT/版本冲突；
- 公众号说明、反馈帮助、医院静态卡片和院内静态导航；
- 健康百科目录、症状关联疾病、疾病/药品审核内容详情。

每个只读域都必须分别采集：

```text
微信页面状态
  -> 客户端 requestId
  -> Elysia/Pino 低敏事件
  -> Provider requestId/业务状态
  -> 患者切换后的 owner 复核
```

自动化测试、HTTP 200、空列表或统一状态页都不能单独构成真实业务验收。

## 四、下一批执行顺序（并行而不是串行）

### 1. A 组：一次性完成共同只读验收准备

- 预约目录、预约历史、爽约记录共用会话代际和显式患者切换门禁；
- 报告目录/详情只允许 opaque 引用，详情重试重新验证 owner、患者和 TTL；
- 门诊费用继续只读，待缴/已缴状态不能跳入支付；
- 普通资料保留 GET/PUT/409 版本语义，头像、手机号和实名资料不混入；
- 所有页面的加载、空结果、失败和重试保持固定状态容器，避免“加载中 → 空图”造成布局跳变。

### 2. B/C/E 组：材料先到先做，互不阻塞

- 门诊病历先收集 `out-visit-records` 目录 contract，再考虑正文；
- 住院信息先确认 episode 权威来源，再考虑住院费用；
- 医生关系必须先确认当前关系目录和失效语义，不能展示旧快照；
- 电子导诊单先确认 Provider 会话 owner、保留周期和患者上下文；
- 我的问诊先确认外部主体、受众、短期会话、退出和回跳，归入 E，不与 C 的电子导诊单共用模型；
- 健康百科在正式审核 bundle 到达后独立做 staging → 发布 → 撤回演练。

四条临床只读线的材料、停止条件和实现阶梯见
[`clinical-readonly-intake-board-2026-08-25.md`](clinical-readonly-intake-board-2026-08-25.md)。
其中电子导诊属于 C 的 Provider 只读入口，外部“我的问诊”属于 E；二者都不共用预约、报告或门诊费用模型。

### 3. D/E/F 组：只做准备，不伪造成功

这些工作流可以同时整理 contract、字段白名单、状态机和验收用例，但没有材料时不注册
真实 API，不让状态页退化为假列表。支付和医保仍然是最后一个业务批次，不能因“页面看起来完整”提前打开。

## 五、每个域的放行门禁

```text
正式材料指纹
  -> 请求/响应/空/拒绝/超时样例
  -> 字段白名单和禁止字段
  -> owner/患者映射与越权测试
  -> adapter
  -> domain 不变量
  -> persistence（必要时）
  -> Elysia API
  -> 原生页面状态机
  -> Pino 低敏日志
  -> 内网、公网、真机三层证据
```

任一环节缺失时，域保持 `blocked-*` 或 `partial`。这不是停止迁移，而是把多个域同时推进，
避免一个页面的细节问题占满整个项目的迁移窗口。
