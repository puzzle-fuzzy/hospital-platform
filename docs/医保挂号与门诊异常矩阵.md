# 医保挂号与门诊异常矩阵

更新时间：2026-09-21

## 1. 文档范围与当前结论

本文只覆盖医保挂号 `registration/RegPay` 与医保门诊 `outpatient/DiagPay` 的异常保护，不把普通微信自费、退费或旧服务迁移混入同一次修改。

当前正常路径由实施反馈确认为本阶段可用。本轮没有重写正常流程，而是收紧以下高风险边界：

1. 医保授权、结算和混合支付不再把 `orderId`、按钮门禁、阶段或结果保存在小程序 storage。页面每次点击都以当前 owner、业务类型、业务 ID 和患者 ID 调用 `business-recovery`，从服务端唯一活动订单重新决定下一步；旧版本医保 pending 即使仍留在设备上也会被忽略并在旧读取入口清理。医保 API 成功响应统一带 `Cache-Control: no-store`，避免网络层把旧订单状态用于下一次按钮判断。
2. 前端 `busy/paymentBusy` 只存在于当前页面和当前 Promise 执行期间，用来阻止同一次操作的瞬时连点；所有 `finally` 都会恢复按钮。医保现金查单不再复用模块级 Promise，完成页跳转门禁也收敛为当前页面实例状态。页面重开、应用被杀、换设备或上一次请求失败后，不会因上一条本地数据永久禁用授权或支付按钮；新的点击一定重新请求服务端。
3. 跨小程序回跳所必需的授权码不写 storage，也不作为可恢复缓存：发起授权时只在当前进程登记业务类型、业务 ID、患者和发起时间，回跳后仅在四者匹配时消费一次。新的授权点击覆盖旧意图；冷启动、超时、空回跳、会话变化、页面卸载或业务/患者不匹配时丢弃，不能让上一笔授权触发当前支付。
4. 6201 发出前先用订单版本 CAS 将 `created` 改为 `fee_upload_pending`，只有 CAS 胜者可以进入 Provider adapter。adapter 越过 6201 边界前保存 `submitting_6201`，回包凭证与结算上下文全部持久化后保存 `fee_uploaded`；后续请求只恢复已存事实或转人工，不重放结果未知的 6201。`pre_6201` 虽表示尚未发送 6201，但当前也不按超时自动接管：仅更新订单版本无法 fencing 仍存活的旧 adapter，贸然续跑存在两个进程随后都发送 6201 的窗口。
5. 6202 发出前先用订单版本 CAS 持久化 `awaiting_confirmation` 并创建同一订单的恢复任务。因此即使 API 在发送后、回包落库前退出，后续请求也不会以新的 `orgBizSer` 重放 6202；若四段金额尚未落库，任务先等待在途回包，超时转人工复核，不会用 6301 的医保合计猜造基金/个账分项。
6. 授权 POST 返回未知时，服务端可从已持久化授权上下文修复同一订单引用；尚未形成授权的 `created` 单在 2 分钟确认窗口内返回 `authorizationPending=true`，按钮可以再次查询但不会重新展码或再次调用 Provider。首次无单由 MySQL 事务锁定 owner 身份行后再查单和插入；确认窗口结束后的同一订单再执行版本 CAS，只有胜者能消费新的授权码。数据库时间领先 API 时仍按确认中处理。多笔活动订单、人工复核或失败状态会显式拒绝继续外部写操作，客户端不能挑一笔或清缓存后绕过。

本轮已完成源码、类型检查和自动化测试层验证，但尚未执行真实医保、微信、Provider、HIS 写入或真机杀进程测试。因此 P0-02、P0-03 仍保持未完成，不能把本文描述成生产验收结论。

## 3. 统一恢复时序

```text
点击医保授权/支付
  -> business-recovery（owner + businessType + businessId + patientId）
  -> 无活动单或同一 created 单尚无有效授权：进入医保授权
  -> authorize（本次请求幂等键；服务端复用同一业务活动单）
  -> 再次 business-recovery 获取服务端 orderId/status
  -> 6201 fees：CAS created -> fee_upload_pending
  -> 保存 submitting_6201 -> 调用 6201 -> 保存加密凭证与 fee_uploaded
  -> 回包持久化完整：本地修复为 fee_uploaded；结果未知：宽限后 manual_review
  -> 服务端 CAS 写入 awaiting_confirmation（6202 不可重放门禁）
  -> 6202 settle（仅首次持有 CAS 的请求可执行）
  -> 已有 6202 四段金额的 order_placed / awaiting_confirmation：6301 + Worker
  -> 没有 6202 四段金额的 awaiting_confirmation：短暂等待 -> manual_review
  -> cash_pending：展示 6202 权威金额；需要现金时由用户明确继续
  -> 微信服务端查单 / HIS 后置确认
  -> insurance_settled 后按服务端 orderId 进入结果页，不写本地医保结果
```

恢复入口不会调用 `/cancel`，也不会把“页面离开”当成“订单失败”。`cancelled` 订单不再作为活动订单返回；是否允许重新授权由服务端业务键查询结果决定，清除设备 storage 不能改变该结论。

## 6. 本轮代码证据

- `MedicalInsuranceRegistrationService.recoverBusinessOrder`：按当前 owner + 业务类型 + 业务 ID + 患者读取全部服务端订单，只允许唯一非取消订单继续；可从已持久化授权、6201 结算上下文和加密凭证修复本地订单行，不调用外部写接口。
- 首次订单原子 claim：MySQL 仓储在同一事务用当前 owner 的身份行 `FOR UPDATE` 串行化，再读取全部未取消业务单并决定是否插入；owner 行不存在时失败关闭，不能假装已经取得锁。不会依赖“先查后插”的应用层时间差。内存仓储和 SQL 结构测试均覆盖单一胜者，真实多进程数据库竞争仍待验收。
- 授权未知保护：新创建但尚无有效授权的订单在 2 分钟内返回 `authorizationPending`；不同客户端请求键命中该活动单时直接返回“处理中”，不会再次调用 Provider。窗口后同一订单仍先执行版本 CAS，只有胜者能接受新的授权码；数据库时间略领先时保持 fail-closed。
- `MedicalInsuranceRegistrationService.uploadFees/uploadOutpatientFees`：进入 adapter 前先 CAS 抢占 `fee_upload_pending`；并发请求只有一个胜者，其他请求只观察状态。`pre_6201` 超时不会仅凭时间和同状态 CAS 自动续跑，因为该做法不能 fencing 已经进入 adapter 的旧进程。
- `legacy-fsi-medical-insurance` adapter：6201 前保存 `submitting_6201`，6201 完成后先保存两类加密凭证和 `fee_uploaded` 上下文，再由 service 更新订单；已进入发送边界的未知结果不会自动重放。
- `MedicalInsurancePaymentCore.settle`：调用 6202 前先 CAS 写入 `awaiting_confirmation` 并持久化查单任务；`order_placed/awaiting_confirmation` 只保留同一任务，`manual_review/cancelled` 直接返回已存状态，不再调用 6202。
- API/Worker 金额门禁：没有 6202 四段金额时，API 查询不会把 6301 的医保合计猜成个人账户或基金；Worker 先等待在途回包，超时后将订单和任务转人工复核。
- 小程序挂号、门诊结算和旧医保收银台页：每次操作查询服务端订单；医保流程不写 `pendingMedicalPayment` 或 `lastMedicalPaymentResult`，旧医保 pending 在兼容读取时被清理。医保现金查单不保留模块级 Promise，每次新点击重新请求 API。普通微信自费的既有本地恢复不在本轮改造范围。
- 医保授权回跳：只用当前进程的一次性交接把外部授权码交给原业务页面，按 `businessType + businessId + patientId` 精确匹配；新点击覆盖、匹配后消费、超时、冷启动、会话变化和页面卸载均清除，不保存按钮状态或订单阶段。
- 按钮状态：`busy/paymentBusy` 仅为当前页面、当前请求的瞬时态，所有异步入口在 `finally` 恢复；跳转防重也只属于当前页面实例。失败、取消、页面重开后均可再次点击并重新查询服务端，不读取上一点击结果。
- 医保结果页：进入时先显示“确认中”，只使用路由业务键或服务端 `orderId` 查询；仅 `insurance_settled` 显示成功，不再读取最近一次本地结果，也不会把路由总额临时伪装成全额现金。

## 7. 官方规则核对

本轮实现采用以下官方规则作为边界，而不是依据客户端回调自行推断成功：

1. 微信支付客户端返回后仍需由服务端查单确认；未收到支付通知时应主动查询，重复通知必须幂等处理。[小程序支付开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012791911)
2. 医保移动支付下单结果和最终支付状态需要使用商户订单号等稳定标识查询，不能因请求超时换号重建。[医保移动支付开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4016824681)、[按商户订单号查询下单结果](https://pay.weixin.qq.com/doc/v3/merchant/4016781490)
3. 医保混合支付成功通知只是一条外部事件，仍需和平台订单、医保结算及医院后置状态做幂等收敛。[医保混合支付成功通知](https://pay.weixin.qq.com/doc/v3/merchant/4016781554)

## 8. 尚未闭环和发布门禁

## 9. 回滚原则

如果正常医保挂号或门诊路径出现回退，应整体回滚服务端业务恢复、6201/6202 守卫和对应小程序调用，不得只恢复旧前端缓存逻辑。清空患者端 storage 不能改变服务端可能正在结算或已经扣款的事实；必须先按业务键和 `orderId` 查清最终状态。
