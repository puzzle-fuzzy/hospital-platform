# 错误精准展示与数字错误码体系

## 目标与原则

双层精准，两个受众：

- **用户层**（页面横幅/错误卡）：`哪个部分出了什么问题 → 该怎么办 → 错误码 NNNNN`，三段式文案，不再共享"请稍后重试"。
- **开发者层**（遥测/控制台/实时日志）：`数字码 → 注册表条目 → 字符串码（grep 源码唯一命中）+ 遥测链（route+method → requestId → 服务端 traceId）`。用户口头报一个数字即可反查全链路。

关键决策（已确认）：数字码**用户可见**；数字码由**服务端权威分配**（响应封套新增 `error.numericCode`），客户端本地错误（网络断、微信能力、会话替换等未到服务端的失败）由客户端在保留段分配。

## 数字码分配（5 位，域分段，段内留 10 间隔）

| 段 | 域 | 示例 |
| --- | --- | --- |
| 10000–12999 | 请求层/会话/运行时 | 10100 validation，10200 unauthorized，10300 parse，10400 dependency-not-configured，10500 persistence-temporarily-unavailable，10600 persistence-invalid，10900 unknown |
| 20000–20999 | 就诊人 | 20100 patient-query-invalid，20200 patient-sync-in-progress，20300 patient-sync-stale，20400 patient-directory-snapshot-unsafe… |
| 30000–30999 | 预约 | 30100 appointment-query-invalid，30200 appointment-record-*，30300 appointment-schedule-reference-expired… |
| 40000–40999 | 报告 | 40100 report-query-invalid，40200 report-not-found… |
| 50000–50999 | 支付/缴费 | 50100 payment-order-*，50200 payment-prepay-*，50300 payment-notification-*，50400 outpatient-payment-*… |
| 60000–60999 | 健康内容/资料 | 60100 health-knowledge-*，60200 user-profile-* |
| 80000–80999 | **客户端本地保留段**（服务端永不使用） | 80100 network-failed，80200 wechat-login-failed，80300 session-changed，80400 patient-selection-*，80500 wechat-payment-*，80600 report-detail-id-missing，80700 api-base-url-*/app-not-initialized |
| 90000+ | 兜底 | 90000 unknown |

一个数字唯一对应一个**原因**；"哪个部分"由页面 surface 文案补充（同因在不同页面显示不同标题，但码相同）。

## 服务端改动

1. `packages/contracts/src/index.ts`：`ErrorResponse.error` 增加 `numericCode: Type.Integer()`（必填；部署顺序服务端先行）。
2. `apps/api/src/plugins/error-handler.ts`：新增唯一权威映射表 `ERROR_NUMERIC_CODES: Record<字符串码, 数字码>`（42 个码全覆盖）；每个 instanceof 分支和 fallback 从该表取值写入响应；查不到的未知码固定回落 90000，不回显原始字符串。
3. `apps/api/src/modules/auth/service.ts`：HttpError  throw 点不需要改构造（error-handler 按码查表）。
4. 服务端测试：`error-handler.test.ts`（36 处 code 断言补 numericCode）、`app.test.ts`、`knowledge/index.test.ts` 的封套断言更新。
5. `docs/公共API-v2.md`：错误码表加"数字码"列。
6. `tools/error-contract-audit.mjs` 扩展：服务端字符串码必须全部有数字码且唯一；文档表数字码与服务端同步；客户端注册表（见下）对服务端码的镜像数值一致；客户端本地码必须落在 8xxxx 段。同步更新 audit 自身测试。

## 客户端改动

1. **新文件 `src/services/error-registry.ts`**（核心）：
   - `SERVER_ERROR_NUMERIC_CODES`：服务端码→数字码镜像（审计强制与服务端一致；旧服务响应缺 `numericCode` 时按此回退，兼容部署窗口）。
   - `CLIENT_ERROR_NUMERIC_CODES`：8xxxx 客户端本地码。
   - `presentClientError(error, surface)` → `{ numeric, title, message, action, displayText }`：吸收现有 per-domain mapper（appointment-record-error、patient-surface-context、patient-selection-service、各页 showError 的内联映射）的文案逻辑，输出三段式 + 数字码；未注册原因回落所属 surface 的通用文案 + 90000 段码。
   - 每个条目带开发者字段：原因说明、grep 关键字（字符串码）。
2. `api-client.ts`：`ApiError` 增加 `readonly numericCode: number`（从响应 `error.numericCode` 解析，缺失时由镜像表回退，再缺失 0）；`ApiErrorDetails` 相应扩展。
3. 页面展示接线：
   - 各页 `showError` 改走 `presentClientError`；错误横幅显示 `displayText`，右下角显示 `错误码 {{errorCode}}`。
   - 4 个代表性页面（appointment-records、report-directory、profile、index）WXML 错误卡片从静态文案改为渲染动态 `{{error}}` + 码；其余页沿用横幅模式接同一函数。
   - toast 类瞬时提示保持现有文案（码进遥测，不进 toast）。
4. 遥测增强：
   - `page.action`/`page.lifecycle` 失败事件 fields 增加 `errorCode`（数字）、`errorKey`（字符串码）、`requestId`；`logClientPageFailure` 从 ApiError 提取（替换现在只记 `"ApiError"` 的 errorName）。
   - `api.request` 观测与遥测事件增加 numericCode。
   - 新增遥测种类 `error.transformed`：在现有 2 处"替换丢失原始错误"点（api-client 命令型 401 → session-changed、global-user-profile 会话代际替换）和关键吞没点（confirm-registration 就诊人上下文 catch、wechat-user-profile 授权失败、app.ts 启动失败）记录转换前的原始码——这是"转换前最后真相"。
   - 微信实时日志 `addFilterMsg(String(numericCode))`（带 try/catch 与条数上限）：公众平台"实时日志"可直接按码过滤。
5. 测试：新增 `error-registry.test.ts`（数值唯一、镜像同步、surface 文案组合、回退）；更新受影响的文案断言测试（保持现有中文文案不变，仅新增码的断言，改动最小化）。

## 风险与兼容

- **契约变更窗口**：部署顺序固定"服务端先行"；客户端对缺失 `numericCode` 的旧响应有镜像表回退，不因旧响应崩溃。
- **测试断言面**：服务端 3 个测试文件的封套断言、客户端约 12 个文案测试——保持既有中文文案不变，只增量断言数字码，控制改动。
- **未提交的并发改动**：工作区有号源功能与文档改名的未提交改动；本方案不碰 appointments 业务逻辑，仅在 error-handler/contracts 层加字段，与前者正交。
